## 0. 结论

1. **先定口径，后测数。** 本批只交付**口径**：三项指标各给「样本 / 方法 / 通过线 / 当前值 / 脚本」，**不跑实测**。
   通过线**分两层**（§1.1）：**产品线**（生成器 `dense` ≈190 元素，**阻塞发布**）与**压力线**（合成 2000+ 元素，**只记趋势、不阻塞**）。
   指标 ① 因此落成 **两行**（①-a 产品线 / ①-b 压力线），②③ 各一行、两层判据同格并列 —— 见 §1。
2. **不留裸「待测」。** 每个未测出的值都写成「待测（`scripts/xxx.mjs`）」，读者一眼知道**谁**去测、**在哪**测。
3. **不阻塞功能，阻塞 ✅。** 数字未达标**不阻塞**任何功能批开工与交付；但**阻塞** `map-window-overview.md` §1 里与性能相关能力标 ✅：
   **#4 画布内核**（视口剔除 / 无级缩放）、**#5 陆地与海岸质感**（烘焙链路）、**#13 导出**。
   理由：这三格现在的 ✅ 依据是「有守卫 + 体感流畅」，而守卫钉的是**结构**（节点数、参数、像素一致），**不是耗时**。
4. **通过线取 v1 PRD 原文，不取总览的复述。** v1 §6.1（`map-v1-prd.md:410-413`）原文是「首屏可交互（含底图）< **1s**」「拖拽 / 平移帧率 ≥ **55fps**」「缩放帧率 ≥ **55fps**」。
   后续文档把它复述成「60fps / 首屏 <2s」，两个方向都漂了（**55→60 变严、1s→2s 变松**）。本批**以 v1 原文为通过线**，`60fps` 只作**理想线**（显示器刷新上限）并列，不作判据。溯源与勘误见 §4。
5. **未纳入本轮的三条 v1 指标**（§6.1 有、本文不取）：峰值内存 < 500MB、单次交互响应 < 16ms、2000+ 元素全量就绪 < 3s。
   它们不是不重要，是**缺可比口径**（内存要算 GPU 纹理还是进程 RSS？"全量就绪"以哪一帧为界？），
   强行写进基线只会得到三行测不准的数。留在 §7 Open Questions 等裁决。

### 1.1 为什么 2000+ 只作压力线（裁定记录）

**「2000+ 元素」是压测上限，不是产品要求。** 依据是产品真实产能：
一键成图的丰度上限 `RICHNESS_TOTALS.dense = 190`（`domain/generator.ts:60-64`），且实际"只少不多"（留白 / 碰撞拒绝 / 内缩后可用面积），
手工放 2000 个素材不是用户会做的事。

所以：
- 拿 2000 元素当**通过线**，等于用**产不出来的样本**卡发布 —— 那不是验收，是自造红条。
- 但 2000 也不该被丢掉：它是**退化压力线**，用来回答"素材量翻十倍时系统在哪一档崩"。跌破 30fps 就登记退化项，让趋势可见。

> 这条裁定改变的是**判据归属**，不是测量方法：两个样本用同一套采集器、同一套分位口径，只是**结论用途不同**（拦发布 vs 记趋势）。

> **为什么帧率不用 `requestAnimationFrame` 均值**：rAF 回调**间隔**的均值会把掉帧抹平 —— 一帧 40ms 配四帧 8ms，均值仍是 16ms（= 62.5fps，"达标"），
> 但用户体感是"每秒卡一下"。`Ticker.deltaMS` 是逐帧实测耗时，取 **P50** 判「是否稳定达到 55fps」，同时报 **P95** —— v1 只写了 fps 阈值没写分位，
> 本文用 P50 对齐它的语义（"帧率"= 常态帧率），P95 留给归因：**P50 达标而 P95 掉，说明是周期性卡顿而不是整体性能不足**，这两种问题的修法完全不同。

## 2. 三项指标的可实施细节

### 2.0 样本从哪来（**这条最重要，先看**）

**两个样本，两个用途，不要混：S2 = 产品线（判发布），S1 = 压力线（记趋势）。**

- **S2（产品线，主判据）**：`seed=20260411` + 预设任选 + 丰度「繁密」（`dense`）+ 成图模式，实例数 ≈ 190。
  **这是用户真会打开的图**，也是 `RICHNESS_TOTALS.dense` 这一产品产能上限对应的形态 —— 所以**只有它进通过线**。
- **S1（压力线，只观察）**：**一键成图产不出 2000 元素**（上限 `RICHNESS_TOTALS.dense = 190`，`domain/generator.ts:60-64`，且实际"只少不多"：受留白、碰撞拒绝、内缩后可用面积约束）。
  所以 S1 必须由**脚本合成**：直接构造 `MapDocument.elements`（`types.ts:196`）2000 条，按网格错开 + 复用同一批 `spriteId`，
  **不经过** `pickTerrainSprites` / 布点循环（否则会被配额与碰撞拦掉）。合成 doc 经 `map.db` 的 `doc_json` 落一份、再开图，脚本与手工都能复现。
  S1 的结论用途只有一个：**素材量翻十倍时系统在哪一档崩**（跌破 30fps 登记退化项），不拦发布、不拦批次。
- **口径**：`2000+ 元素` 指 `elements` 长度 ≥ 2000（素材实例），**不含**区块、地名、折线、子图；但这四类的实测数量**必须一并记录**，否则两组结果不可比。
- **「标准纸」= `BASE_RECT`**：`MapCanvas/index.tsx:247` 的 `BASE_RECT`，即 `BASE_IMAGE` 的 **1024×1024 世界单位**（`sprites.ts:264-272`）。
  三脚本都从 `scene.worldRect` 读实际值并落盘（`export.ts:106`），**不按本行的数字硬编码** —— 纸张若改版，结果文件仍能自证跑在哪张纸上。
  这条对应 v1 §6.2 第 1 条「底图素材 + 标记 + 连线合计」的现行等价物 —— 连线在现行模型里是 `polylines`。

### 2.1 帧率采样点

- 采集器挂在**渲染进程内**（探针对象挂 `window.__mapPerfProbe`，仅 bench 构建注入，不进产品代码路径），
  监听 `app.ticker` 的 `tick` 事件取 `ticker.deltaMS`（Pixi v8：`deltaMS` 为该帧实际毫秒数，`deltaTime` 是 60fps 归一化倍数 —— **要 ms 不要倍数**）。
- **必记环境量**：`devicePixelRatio`（`MapCanvas` 用 `window.devicePixelRatio` 作 `resolution`，`MapCanvas/index.tsx:1262`）、窗口像素尺寸、
  缩放档位（帧率随 scale 变化，静置段固定取 scale=1）、可见元素数（视口剔除后的 `cull.ts` 输出计数）。
- **禁止**的报法：只报"平均 fps"；只报单帧最低值（噪声）；不记缩放档位。

### 2.2 首屏可交互

- **终点定义要写死**：首个 `renderer.render()` **返回之后**。不是 React `useEffect` 跑完，也不是 `onSceneReady` 回调触发 ——
  那两者发生时画布可能仍是空的（素材未上图），用户还不能操作。
- 分段三点全输出，是为了"慢在哪"可归因：`Application.init()`（WebGL 上下文 + 插件）、场景图装配（陆地烘焙 / 区块 / 素材加入容器）、首帧 render。
- **冷启动**才作数：进程新起 + 首次打开该图。二次开窗命中缓存，数字会好得离谱，单独标注不作验收。

### 2.3 4K 导出

- **当前实现下 4K 档恒为 1×1 分块**：`EXPORT_TILE_MAX = 8192`（`export.ts:33`），`longSide = 4096` ⇒ `cols = rows = 1`。
  仍然照记 `plan.cols × plan.rows`，理由有三：①脚本口径与尺寸档解耦（将来放开 8192 / 极端纸型时不用改脚本）；
  ②`tilePlan` 是导出耗时唯一的结构性变量，不记就无法解释"同一张图为什么这次慢"；③`export.ts:31` 已写明"4096 档永远不会触发切块"，本条与代码注释一致，不是新判断。
- 导出前会 `clearOverlay()`、导出后 `redrawOverlay()`（`export.ts:158 / 192`），这两步在 `finally` 里，**计入 t0~t1**，不单独扣。
- 产物字节数一并记（`bytes.length`）—— PNG 编码耗时与像素量正相关，字节数是事后判断"这台机器是不是被编码卡住"的旁证。

## 4. 口径溯源与勘误

**一句话：本模块的性能数字在文档里走过一次形变，本文以 v1 原文为准，并把漂移记在案。**

| 口径 | 数字 | 出处 | 本文采不采 |
|---|---|---|---|
| 首屏可交互（含底图） | **< 1s** | `archive/prd-map/map-v1-prd.md:410`（§6.1 表格） | **采 —— 通过线** |
| 拖拽 / 平移帧率 | **≥ 55fps** | 同上 `:412` | **采 —— 通过线** |
| 缩放帧率 | **≥ 55fps** | 同上 `:413` | **采 —— 通过线** |
| 2000+ 元素全量就绪 | < 3s | 同上 `:411` | 不采（缺"就绪"口径，见 §0-5） |
| 单次交互响应（选中/拖动） | < 16ms | 同上 `:414` | 不采（同上） |
| 峰值内存（含纹理） | < 500MB | 同上 `:415` | 不采（同上） |
| 「2000+ 元素 / **60fps** / 首屏 < **2s**」 | 复述 | `prd-map-render/map-window-overview.md:198`（§5.1 第 3 条，对 v1 §6 的**复述**） | **不采** —— 见下 |

**勘误：复述漂移的方向是双向的，不是简单"变严"或"变松"。**

- **55 → 60fps = 变严**（要求高了 9%）。危害：若按 60 判，55~60 之间的机器会被判不达标，而它其实**满足 v1 验收**。
- **1s → 2s = 变松**（要求低了一倍）。危害更大：首屏 1.5s 的实现在 60/2s 口径下"合格"，但 v1 明确要求 1s 内可交互 —— **这是会被用户感知到的退步**。
- 两个数一严一松同时出现在同一句引文里，说明那次复述不是有意的口径修订，是**转述时记错了**。

**处置（已落地）**：
1. 本文**通过线全部取 v1 原文**（1s / 55fps / 55fps），`60fps` 仅在 §1 表中作**理想线**并列，**不作判据**。
2. `map-window-overview.md` §5.1 第 3 条那处复述**已改为**「2000+ 元素同屏 / ≥55fps / 首屏 <1s」，并在句末补「（口径以 `spec/map-perf-spec.md` 为准）」，让总览**指向本文**而不是自带一份数字 —— 同一条基线在两处各写一遍，就是这次漂移的成因。
3. 后续任何文档引用性能基线，**只引用本文，不复制数字**。

## 5. 机器档位与记录纪律

**档位只用于分组，不用于判据。** 同一份结果必须能看出它跑在哪一档，禁止跨档比较、禁止只写"实测流畅"。

| 档位 | 定义 | 用途 |
|---|---|---|
| **A** | 集显轻薄本（Intel Iris Xe / AMD Radeon 集显级） | 最低目标档：**通过线按 A 档成立** |
| **B** | 独显台式 / 游戏本 | 用于判断"余量有多大" |
| **C** | Apple Silicon（M 系） | 与 A 档分开记，不与 x86 混算 |

每个结果文件**必须**含：`os.cpus()[0].model`、总内存、GPU 渲染器字符串（`WEBGL_debug_renderer_info` 的 `UNMASKED_RENDERER_WEBGL`）、`devicePixelRatio`、窗口像素尺寸、Electron 版本、`package.json` 的 `version`。
