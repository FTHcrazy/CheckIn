## 1. 执行摘要

**简述：** 为 CheckIn 小说编辑器新增「行囊」——一个独立于侧边栏、可无损唤起的常驻面板，用于随时查看与维护主角的人物属性、装备、物品和技能，并通过可配置的加成规则自动汇总出角色当前总属性。

**内容：** 一套**模块化可拼装**的角色面板系统，包含人物属性、装备栏、物品栏、技能栏四大核心模块，外加总属性汇总、境界、货币、状态效果等可选模块；作者可自定义装备部位（含槽位数量限制）、自定义量纲换算（境界/熟练度/货币），并为装备与技能编写对人物属性的加成词条。

**原因：** 系统流与网游流派的核心爽点是「数值成长」，作者写这类文时需要高频核对主角身上有什么、当前属性是多少。当前这些数据散落在正文大纲、备忘录、甚至 Excel 里，靠人肉翻找，**是该类作者最高频的中断源之一**。把它变成编辑器内一屏可达的结构化面板，直接消灭这个中断。

**面向谁：** 用 CheckIn 写小说、尤其是系统流 / 网游 / 无敌流 / 种田流的网文作者（novel 版主窗口用户）。

**成功标准：** 见 §3「成功指标」表；核心是**行囊面板的日活打开率**与**面板内编辑动作占比**（说明作者真的在用面板而不是回头翻正文）。

**时间表：** 详见 §16。MVP（P0 四模块 + 汇总 + 自定义部位）目标 3 个迭代内交付。

## 2. 问题陈述

### 当前情况

写系统流 / 网游流小说的过程，本质是在**维护一本不断变动的角色账本**：主角的等级、境界、装备、背包里的材料、技能熟练度、金币数量。作者每隔几段就得回头确认：

- 「上一章给主角的那把刀叫什么名字来着？」
- 「现在是三品炼丹师还是四品了？」
- 「背包里那颗「破境丹」吃了吗？还剩几颗？」
- 「换了这套装备后总战力是多少？我前面写的时候说是一万二，别写崩了。」

当前这些信息的载体是：正文往回翻、`Ctrl+F` 全书搜索、或者在备忘录 / Excel 里另维护一份。**这三件事都会打断写作流。**

### 关键洞察（这条决定了产品形态）

> 作者不是在「查资料」，而是在**维持写作过程中的状态一致性**。
> 因此这个面板的核心价值不是「存得多」，而是「**唤得起、看得全、改得动、不挡字**」。

「不挡字」是本需求中被明确点名的约束，也是最容易做错的地方——详见 §8.2，我们专门定义了三种不遮挡形态。

### 第二条关键洞察：主动 / 被动是**两个正交的轴**，不是一根轴的两端（v1.3）

> 需求方原话：「有些技能或者装备效果是主动的，还有些是被动的；无法差别体现主动效果和被动效果；现在只有一个佩戴和激活，两者有时候可能都会存在。」

这句话指向的是一个**建模错误**，而不是缺一个筛选项：

| 轴 | 回答的问题 | 谁有 |
|---|---|---|
| **轴 A：载体状态** | 这件东西「在不在身上 / 用不用」 | **每个载体恒有 1 个**：装备=佩戴、技能=启用 |
| **轴 B：效果性质** | 这条效果是「常驻改数值」还是「要角色主动做一个动作」 | **每条效果各有 1 个**：被动 / 持续 / 释放 |

「佩戴」和「激活」本来就是同一个轴的同构表达，把二者当成两回事、又不区分效果性质，就会出现作者描述的症状：
- 一件装备同时带「被动 +500 防御」和「主动·铁壁姿态」→ 面板把它们**糊成一堆加成**，作者分不清哪个是穿上就有、哪个要自己开
- 「释放型技能」的倍率被**错误累加进总属性**（这是会写崩数值的实质缺陷，不是观感问题）
- 想让主动部分单独生效时**无从下手**——因为只有一层开关

**解法与边界详见 §9.2.1。** 结论是给每条效果加一个 `nature` 字段分三档，并把汇总管线从「一道闸门」改成「两道闸门」。

### 影响

**受影响的人：**

| 画像 | 影响方式 |
|------|---------|
| 系统流 / 网游流作者 | 每次核对都要中断写作流，且中断的真实成本是切换耗时的数倍（含重新进入心流的时间） |
| 多角色群像作者 | 当前 v1 不覆盖，但同样痛苦且更严重（详见 §14 范围外） |
| 已经在用 CheckIn 实体面板的作者 | 现有 `EntityPanel` 只能存「实体卡片」（自由tags + 简介），**没有结构化数值与汇总能力**，正好本功能补齐 |

**问题规模（⚠️ 假设，待埋点校准）：**

| 项 | 数值 | 状态 |
|---|---|---|
| 小说窗口活跃用户中写过 ≥1 个自定义实体类型的比例 | 待测定 | 🔴 **假设**，需 §10 埋点获取基线 |
| 使用 `SupportPanel` 的频率（次/活跃日） | 待测定 | 🔴 需埋点基线 |
| 作者每千字回头翻阅 / 搜索次数 | 待测定 | 🔴 需可用性测试或埋点（编辑器 blur 事件可间接估） |

> **诚实声明：** 本节目前尚无实测数据支撑规模判断，只有需求方（本文发起人）的业务判断。
> §10 已列出需要先拿基线的埋点，请在立项评审前补齐，或用 5～8 人的小样本可用性测试替代。

### 场景示例

> 作者正在写第 137 章的高潮打斗，需要让主角用上月获得的「风雷双匕」打出一击必杀——但他记不清这把匕首的属性加成是多少、主角的境界进度是「筑基六层」还是「筑基七层」。
> 他按下 `Ctrl+Shift+B`，右侧滑出一屏面板，**正文区域自动收窄但每个字依然可见**，他一眼看到：`境界 筑基七层 7/9`、`总战力 12,480`、`武器 风雷双匕（+120 敏捷 / +15% 暴击）`。确认无误，继续写下去。**全程 3 秒，眼睛没离开正文所在的那块屏幕区域。**

## 3. 目标与成功指标

### 业务目标

1. **让 CheckIn 成为系统流 / 网游流作者的首选写作工具**
   - 当前状态：面板仅充当「写作辅助」，对网文核心品类无专项能力，痛点见 §2
   - 目标：行囊成为 CheckIn 小说版 Top 1 差异化卖点
   - 影响：该品类作者付费意愿与留存显著高于泛小说作者（🔴 假设，待验证）

2. **提升 novel 版编辑器的日活深度**
   - 目标：使用过本功能的小说作者，次月留存显著高于未使用者（目标差值待基线确定后设定）

### 用户目标

1. **唤得起**：一个动作（快捷键 / 一次点击）打开面板，不经过多级菜单。
2. **看得全**：属性、装备、背包、技能在同一屏内可见，无需切换标签页。
3. **改得动**：在面板内直接改数值、穿脱装备、开关技能，不需要打开表单弹窗就能完成 80% 的日常调整。
4. **不挡字**：打开面板时正文不被遮住，作者不必为了看数据关掉再打开。
5. **配得野**：不同小说的设定天差地别，作者能把面板改成自己小说的样子。

### 成功指标

| 指标 | 基线 | 目标 | 时间 | 优先级 |
|------|------|------|------|--------|
| **行囊面板日打开率**（当日打开过面板的活跃小说作者占比） | 待定（v1.17 无此功能） | ≥ 40% | GA 后 30 天 | P0 |
| **面板内编辑动作数 / 活跃作者 / 日**（穿脱装备、改数值、开关技能合计） | 0 | ≥ 6 | GA 后 30 天 | P0 |
| **自定义装备部位使用率**（改过默认部位配置的作品占比） | 0 | ≥ 25% | GA 后 60 天 | P1 |
| **量纲体系配置率**（至少配置过一套：境界/熟练度/货币） | 0 | ≥ 30% | GA 后 60 天 | P1 |
| 面板打开→关闭的平均停留时长 | 无 | 8～40 秒（>8 秒说明真的在看，>40 秒说明 UI 难用） | GA 后 30 天 | P2 |

**反向指标（必须监控，防止负优化）：**

- **正文字数日产出**：使用面板的作者，日产出不应低于使用前的基线水平（降幅 > 5% 需复盘是否面板打断写作流）
- **小说窗口崩溃率**：不高于 v1.17 基线
- **编辑器首次渲染耗时**：面板挂载不应拖慢编辑器首屏（Δ < 100ms）

## 4. 用户画像与用例

### 主要画像：老白（系统流作者）

| 项 | 内容 |
|---|---|
| 角色 | 兼职 / 全职网文作者 |
| 作品类型 | 系统流、网游流、无敌流、种田流 |
| 篇幅 | 单本 80～500 万字，连载周期 6 个月以上 |
| 技术水平 | 熟悉 Word/写作软件，不排斥配置，但**拒绝写代码** |

**目标：**
- 快速核对主角当前状态，不打断写作
- 让前后文的数值保持自洽，不被读者抓 bug
- 把「面板里的数值」直接变成章节里能用的文字

**痛点：**
- 数值记不住，来回翻
- 之前写了 12000 战力，后面忘了写成 15000
- 换过一次装备后，之前写的面板数据全失效

**当前工作流：** 在 Excel / 备忘录里维护一张角色表 → 写作时在窗口间来回切换 → 懒的时候就凭记忆写

### 次要画像：河豚（网游竞技流作者）
写 PK 与装备切换密集的类型。对「装备 Δ 预览」和「换装方案」需求更强（见 §6 REQ-018、REQ-032）。

### 用例

#### 用例 1：写打斗场景前核对属性（最高频，日 10+ 次）

- **用户目标：** 确认主角当前总属性与已装备武器
- **当前行为：** 往回翻章节 / Ctrl+F / 切到 Excel
- **期望行为：** `Ctrl+Shift+B` → 一屏看全 → 继续写
- **频率：** 极高

#### 用例 2：本章主角获得新装备（日 1～3 次）

- **场景：** 写完"主角获得了风雷双匕"，需要更新管包面板
- **期望行为：** 面板内点「+ 新增物品」→ 填名称、选装备类型、填加成 → 拖/选到「武器」槽位 → 自动汇总立即刷新
- **频率：** 高

#### 用例 3：设定一本新小说的装备体系（每本 1 次）

- **场景：** 开新书，需要让「戒指能戴两个」「某些小说没有坐骑位」
- **期望行为：** 装备部位管理里删除不需要的部位、把戒指槽位数改成 2、新增「灵宠」部位
- **频率：** 低但必做，**做不好会让作者直接放弃**

#### 用例 4：境界突破后批量更新（周 1～2 次）

- **场景：** 主角突破到筑基二层
- **期望行为：** 境界模块点「+」，面板自动按作者配置的阶梯进位（九层满了自动进下一阶），相关属性按作者设定的境界加成自动上涨
- **频率：** 中

#### 用例 5：写章节结尾的「收获清单」（或用 EXIT)

- **场景：** 作者想在章末写「物品一览」
- **期望行为：** 面板 → 「导出为 Markdown 表格」→ 粘贴进正文
- **频率：** 低但有惊喜感（**建议 P1**）

### Epic A：入口与容器形态

#### A-1 独立于侧边栏的一键唤起 🟦 P0

**作为** 正在写作的作者
**我想要** 用一个快捷键或一个常驻按钮打开物品行囊面板
**以便** 不用在侧边栏里翻找就能立刻看到主角状态

**验收标准（Given-When-Then）：**
- [ ] **Given** 我正处在小说编辑器任意页面，**当** 我按下 `Ctrl+Shift+B`，**那么** 面板在 ≤ 200ms 内出现在右侧
- [ ] **Given** 面板已关闭，**当** 我点击顶部工具栏的「背包」常驻按钮，**那么** 面板打开，且该按钮有明确的 active 态
- [ ] **Given** 面板处于「右侧让位」形态，**当** 面板打开，**那么** 编辑器正文区域的可用宽度减小，**但已有文字不被任何 UI 覆盖**（自动换行重排，无横向滚动条）
- [ ] **Given** 面板打开且宽度被上一次调整过，**当** 我重新打开，**那么** 记忆的宽度被恢复
- [ ] **Given** 我处于中文输入法组字过程中，**当** 我按下快捷键组合键的原始按键，**那么** 不触发面板（输入法态放行）

#### A-2 不遮挡文章内容：三形态切换 🟦 P0(Peek/让位) 🟩 P1(分离窗口)

**作为** 屏幕空间紧张的单屏作者
**我想要** 在不挤占正文的情况下临时查看数据
**以便** 我不用关闭面板就能继续写

**验收标准：**
- [ ] **Given** 默认设置，**当** 面板打开，**那么** 使用「右侧让位（reflow）」形态，正文重排而非被覆盖
- [ ] **Given** 我按住 `Alt` 并点击顶部背包按钮（或设置了 Peek 快捷键），**当** Peek 浮层出现，**那么** 它以半透明悬浮方式覆盖右侧，松手/移出后 **3 秒自动消失**，且**不写入任何布局记忆**
- [ ] **Given** 窗口可用宽度 < 1100px，**当** 面板打开，**那么** 自动降级为「临时浮层 + 半透明遮罩」，关闭后完全还原布局
- [ ] **Given** 我点击面板右上角「分离」按钮，**当** 分离完成，**那么** 内容在一个独立窗口中展示，编辑器正文**恢复满宽、零遮挡**；该独立窗口位置与尺寸被记忆
- [ ] **Given** 我关闭了独立窗口 或 再次点击面板内的「合入」，**当** 操作完成，**那么** 回到「右侧让位」形态

### Epic B：核心四模块

#### B-1 人物属性栏（M1）🟦 P0

**作为** 作者
**我想要** 自定义主角有哪些属性并直接编辑基础值
**以便** 面板能贴合我小说的战力体系

- [ ] **Given** 首次使用，**当** 我打开属性模块，**那么** 提供一套可选模板（通用 / 玄幻 / 网游），一键套用后可自由增删改
- [ ] **Given** 属性列表中存在「力量」，**当** 我点击数值直接输入 `120` 并失焦，**那么** 基础值立即生效、总属性自动重算，无需刷新页面
- [ ] **Given** 我新增了一个自定义属性「魂力」，**当** 保存，**那么** 它立即可被装备加成 / 技能加成作为目标属性选中
- [ ] **Given** 某属性已有一条加成指向它，**当** 我确认删除该属性，**那么** 相关加成词条被一并清理，并给出「将同时移除 N 条加成」的确认提示
- [ ] 属性支持分组（如「基础属性 / 战斗属性 / 生活属性」）与拖拽排序

#### B-2 装备栏与部位自定义（M2）🟦 P0

**作为** 写特定世界观小说的作者
**我想要** 自己定义有哪些装备部位、每个部位能穿几个
**以便** 「戒指能戴两个」这类设定能被正确表达

- [ ] **Given** 首次使用，**当** 我打开装备模块，**那么** 加载一套通用预设部位：武器 / 头盔 / 上衣 / 护腕 / 手套 / 腰带 / 下装 / 靴子 / 项链 / 戒指 / 饰品 / 坐骑
- [ ] **Given** 我在部位管理中选中「戒指」，**当** 把「槽位数量」改为 `2`，**那么** 装备栏该部位出现 2 个可放置槽位，且可分别穿戴不同戒指
- [ ] **Given** 我在部位管理中新增部位「灵宠」，**当** 保存，**那么** 装备栏出现该部位（默认 1 槽位）
- [ ] **Given** 「戒指」的 2 个槽位都已占用，**当** 我再拖拽一枚戒指进入，**那么** 提示「该部位已满」，并提供「替换：xxx」的选项
- [ ] **Given** 部位配置了「仅接受类型 = 武器」，**当** 我穿戴一件类型为「消耗品」的物品，**那么** 该部位不接受并给出原因为「仅接受：武器」

      一个字段连敲 10 个字算 1 处，改回原样算 0 处。实现见 `pack-dirty.ts` 的 `countNetChanges`）
- [ ] **Given** 我在输入框里逐字输入（中间态多次写库前状态），**当** 查看未保存计数，**那么** 计数**不随按键次数增长**
- [ ] **Given** 我改了某字段又改回原值，**当** 查看未保存计数，**那么** 该字段**不再计数**（净变化为零）
- [ ] **Given** 存在 3 处未保存改动，**当** 我点「保存」，**那么** **先对改动前状态生成一条盘点记录**，再提交到 SQLite，成功后头部回到「已保存」
- [ ] **Given** 有 3 处未保存改动，**当** 我点「撤销全部改动」，**那么** 二次确认后丢弃草稿、回到上次保存状态
- [ ] **Given** 面板已保存，**当** 我点「撤销到上次保存」，**那么** 从最近一条盘点记录恢复（带确认）
- [ ] **Given** 无未保存改动，**当** 我查看头部，**那么**「保存」按钮为**禁用态**（而不是显示为可点却无反应）
- [ ] **Given** 我在分离窗口中编辑，**当** 回到主窗口，**那么** 看到的是**同一份草稿**与同一个未保存计数

#### G-2 草稿持久化与关闭拦截 🟦 P0

- [ ] **Given** 我有 3 处未保存改动，**当** 应用崩溃或强退，**那么** 重开后草稿仍在，头部仍显示 `保存 (3)`
- [ ] **Given** 我有未保存改动，**当** 我关闭面板，**那么** 弹出三选一（保存并关闭 / 丢弃改动 / 取消），**默认焦点在「保存并关闭」**
- [ ] **Given** 我有未保存改动，**当** 我切换到另一章，**那么** 同样拦截，文案说明改动属于哪一章
- [ ] **Given** 我有未保存改动，**当** 我退出应用，**那么** NovelWindow 的关闭流程拦截并询问
- [ ] 「丢弃改动」为**破坏性动作**：警示色、非默认焦点

#### G-3 自动保存兜底 🟩 P1

- [ ] **Given** 自动保存开启（默认），**当** 存在未保存改动且无操作达 5 分钟，**那么** 自动提交并生成存档点，头部短暂提示「已自动保存」
- [ ] **Given** 未保存改动 ≥ 5 处，**当** 我查看头部，**那么**「保存」按钮做一次轻微呼吸提示（不循环）
- [ ] **Given** 我关闭了自动保存，**当** 存在未保存改动，**那么** 关闭拦截**仍然生效**（安全兜底不可关）

#### G-4 保存失败与逃生出口 🟦 P0

- [ ] **Given** 提交时 SQLite 或 IPC 失败，**那么** 头部出现红色「保存失败 · 重试」，**草稿原样保留**，状态回到「有未保存改动」
- [ ] **Given** 多表写入中的一张失败，**那么** **整体回滚**，不留下部分写入的中间态
- [ ] **Given** 连续失败 3 次，**那么** 提供「导出当前草稿为 JSON」，保证数据能出去

### 边缘与错误情况

| 场景 | 预期行为 | 理由 |
|---|---|---|
| **某属性的来源（装备/技能）被删除** | 该来源的加成立即失效；若该装备仍被穿戴，先自动退下再删除 | 避免汇总引用悬空；先退下再删保障数据不丢 |
| **SQLite 写入失败 / IPC 返回失败** | 面板顶部出现可重试的失败提示，本地保留编辑后的内存态并标脏 | 绝对不允许静默丢作者的数据 |
| **量纲体系被删除** | 依赖它的模块回到「未配置」引导态，**保留原始数值字段不清空** | 作者可能只是想换一套换算，数值不该丢 |
| **部位槽位数从 2 改成 1 但已穿 2 件** | 二次确认后，超出的一件自动退回物品栏 | 明确告诉作者会退回而不是消失 |
| **熟练度输入超过最大阈值** | 允许超过，显示「已超越大师（溢出）」而不是报错截断 | 网文里超越体系常态化 |
| **同时打开多个角色（未来）** | v1 直接拒绝，UI 不暴露多角色 | §14 明确范围外，模型已预留 |
| **窗口宽度极窄（< 900px）** | 面板以全屏浮层展示，提供关闭按钮 | 保证可用性优先于布局美观 |
| **有未保存改动时关闭面板 / 切章 / 退出应用** | 一律拦截并三选一（保存并关闭 / 丢弃改动 / 取消），**默认焦点在「保存并关闭」** | 不允许静默丢弃；默认停在安全侧 |
| **应用崩溃 / 强退时有未保存改动** | 草稿已写入主进程 `novel_pack_drafts`，重开后原样还在，头部仍显示 `保存 (N)` | 落库是显式的，但草稿必须扛得住崩溃 |
| **保存时多表写入中一张失败** | 整体回滚，状态回到「有未保存改动」，草稿保留；连续失败 3 次给 JSON 导出出口 | 不允许出现"表 A 写了表 B 没写"的中间态 |
| **行囊主角未绑定 R25 实体** | 境界模块提示绑定或选择「仅行囊内使用」；未绑定时**不写** `novel_links` | 静默不同步比直接报错更可怕（§9.7.5） |
| **R25 侧与行囊侧同时改境界** | 后写覆盖（last-write-wins），并提示已同步为哪一边的值 | 不静默丢弃任一方的输入 |

## 7. 非功能需求

### 性能
- 面板打开耗时 ≤ 200ms（本地 SQLite，纯 await IPC）
- 总属性汇总重算 ≤ 100ms（≤ 150 条加成条件下）
- 物品列表 ≥ 500 条时滚动流畅（建议 ≥ 200 条后虚拟滚动）
- 数据读写走既有 `novel-*` IPC 通道，主进程单事务，**避免逐字段往返**

### 可扩展性
- 数据模型必须按 `character_id` 维度设计（即便 v1 UI 只暴露主角），保证 P2 多角色无需迁移
- 加成表采用多态设计（见 §9.2），新增加成来源（如状态、称号、宗门buff）无需改表

### 可靠性
- 所有写操作主进程单事务；失败可重试，编辑态本地保留并标脏
- 面板数据随既有 novel 备份体系一同纳入，不得遗漏新表
- 盘点记录数据采用**深拷贝 JSON 存档**，与当前行数据解耦，避免历史被"当前状态"回溯篡改

### 无障碍性
- 键盘可达：所有焦点元素可 Tab；面板本身可被 Esc 关闭（接进现有 Esc 优先级链：设置 → 行囊 → 专注模式）
- 色彩对比度：数值增减的正负色不得只靠红绿区分（须配合符号 / 箭头）
- 最小字号遵循项目规范 ≥ 12px

### 兼容性
- 仅桌面端 Electron 应用（Win / macOS），**不要求移动适配**
- 分离窗口形态须在双屏、不同 DPI 场景下正确记忆恢复

## 8. 用户体验与设计

### 8.1 用户流程

```
写作中 ──Ctrl+Shift+B──▶ 面板打开（上次形态/宽度）
   │                          │
   │                          ├─▶ 查看：一屏扫属性/装备/物品/技能
   │                          ├─▶ 编辑：行内改数值 / +/- / 开关 / 穿戴
   │                          │        └─▶ 汇总实时重算（≤100ms）
   │                          ├─▶ 点某属性 ─▶ 来源明细抽屉
   │                          └─▶ 右上齿轮 ─▶ 模块管理（启用/排序/折叠）
   │                                        └─▶ 量纲设置 / 部位管理
   └────────── Esc 或 再按快捷键 ─────────┘
```

### 8.2「不遮挡文章内容」的三种形态（核心设计）

这是本 PRD 最关键的形态决策。**禁止实现成单一 overlay。**

| 形态 | 触发 | 布局行为 | 遮挡程度 | 适用 |
|---|---|---|---|---|
| **① 右侧让位**（默认） | 快捷键 / 顶部按钮 | 编辑器正文区**重排收窄**（reflow），非覆盖 | **零遮挡**，只是可用宽度减小 | 日常查看与编辑，单屏作者 |
| **② Peek 速览** | `Alt+点击` / 自定义 | 半透明浮层覆盖右侧，**3s 自动消失**，不写布局记忆 | 瞬时轻遮挡 | 只想瞄一眼某个数值 |
| **③ 分离窗口** | 面板内「分离」按钮 | 独立 Electron 窗口，可拖出主窗口 / 副屏 | **主窗口零遮挡** | 双屏作者、长期挂着比对 |

**降级规则：** 主窗口可用宽度 < 1100px 时，① 自动降级为「临时浮层 + 半透明遮罩」，关闭后完全还原。

**关键 UI 约束：** 正文自动换行由编辑器现有逻辑处理，重排后**不得出现横向滚动条**——这是「没遮挡」的可验证判据。

### 8.4 设计原则

1. **一元距离原则**：任何常用操作 ≤ 2 次点击或 ≤ 1 次按键。改数量必须能原地 +/-，不允许「点开弹窗 → 改 → 保存」。
   - ⚠️ **v1.4 边界（与新增「保存按钮」的关系）**：本条约束的是**界面操作距离**，不是**落库时机**。§8.6 的保存按钮**不要求**为了改一个数先点保存——**界面反馈始终即时**，「保存」只决定**何时写入数据库、何时生成回退点**。二者不冲突，详见 §8.6.7。
2. **数值必须有出处**：总属性必须能点到来源明细，不出现无来源的「魔数」——作者是会为自己的设定较真的人。
3. **缺席而非置置**：被关闭的模块 / 熟练度 UI 是**完全不渲染**，不是打置置色。这是P0验收点。
4. **默认值不越界**：未配置的设定（量纲 / 自定义部位）显示引导态，**不硬塞一套"通用默认值"假装已配**。
5. **错误容错优先**：任何删除、降级、退装备操作都默认保留数据，选择权给作者。
6. **改动可回退**（v1.4 新增）：任何改动已有数据的操作，都必须能回到上一个已保存状态。作者维护的是几十万字的连载设定账本，一次误操作丢失的不是"一条数据"，而是**这一章之后所有数值的正确性**（§8.6）。

### 8.6 保存、草稿与回退（v1.4 新增）

> **需求来源（需求方原话）：** 「新增一个保存按钮，防止用户误操作丢失历史数据。」

**先说清楚表面上的一处冲突，再给方案。**

§8.4 原则 1 写「不允许『点开弹窗 → 改 → 保存』」，现在又要加保存按钮 —— 看起来矛盾。**其实不矛盾，因为这两句话约束的是两件不同的事：**

| | 约束什么 | 本 PRD 的立场 |
|---|---|---|
| 原则 1 | **界面操作距离**：改一个数不该弹窗、不该多点几下 | 不变。**编辑反馈永远即时** |
| 保存按钮 | **落库时机与回退点**：什么时候写进 SQLite、能不能退回去 | 新增。**编辑不再直接落库** |

一句话：**「看到的效果」是即时的，「写进数据库」是显式的。**

**为什么必须加（不是洁癖，是真实的数据风险）：**

当前设计（含已交付原型）任何编辑即刻落库且不可撤销。作者在行囊里维护的是积累了上百章的设定账本。误删一条效果、误改一个基础值 —— **没有任何恢复路径**。而这类误操作的代价不是"丢掉这条数据"，而是"这一章之后的所有数值都不对了，且不知道从哪开始不对"。

#### 8.6.1 三态模型

面板头部右侧恒定显示保存状态：

| 状态 | 视觉 | 触发 |
|---|---|---|
| **已保存** | 灰色文字「已保存 · 2 分钟前」 | 无未提交改动 |
| **有未保存改动** | 主色按钮 **`保存 (3)`** + 未保存圆点 | 存在 N 处未提交改动 |
| **保存中 / 保存失败** | 「保存中…」/ 红色「保存失败 · 重试」 | 提交中 / IPC 或 SQLite 失败 |

#### 8.6.2 一条规则，不做例外

**所有编辑都走草稿，统一由「保存」提交。** 刻意**不做**「轻量操作即时落库、结构性编辑手动保存」的分层 —— 作者记不住哪个操作属于哪一类，会催生新的数据丢失模式（"我改了数量以为存了，其实没存"）。**一条规则的认知成本最低。**

> **⚠️ 边界的精确定义（v1.4 补，避免工程照字面实现出荒谬体验）：** 上一句里的「所有编辑」指的是**作者维护的设定数据** —— 属性基础值、装备 / 技能 / 物品及其效果词条、境界与进度、模块拼装（启用与顺序）、单位体系配置。
>
> **不**走草稿、**不**计入未保存改动的是**界面偏好**：面板形态（让位 / 速览 / 浮层 / 分离）、面板宽度、模块折叠状态、列表 ↔ 网格视图切换、主题。这些描述的是「我在怎么用这个工具」，而不是「这本书的设定」，必须**即改即存**。
>
> **反面清单（明确禁止计入未保存改动）：** 拖动面板宽度 · 折叠 / 展开模块 · 切换物品栏视图 · 折叠元素卡（点开某项看详情）。
>
> 判据一句话：**改了这个值，别人的这本书会变吗？** 会 → 走草稿；不会 → 即改即存。

| | 草稿态 | 提交后（正式数据） |
|---|---|---|
| 界面反馈 | **即时**（汇总立刻重算、Δ 立刻更新） | 不变 |
| 数据位置 | `novel_pack_drafts`（**主进程表**，编辑防抖写入） | `novel_pack_*` 正式表 |
| 回退 | 「撤销全部改动」丢弃草稿 | 「撤销到上次保存」用盘点记录恢复 |

> **草稿为什么落主进程表而不是 `localStorage`：** 行囊支持「分离窗口」形态（§8.2 形态 ③），而 Electron 中各窗口的 `localStorage` **不共享**。用 localStorage 会出现「主窗口存了、分离窗口看不到草稿」以及「在分离窗口改完、主窗口显示的还是旧值」的诡异现象。草稿必须是**跨窗口的一份**，所以放主进程。
>
> **为什么草稿不怕丢：** 草稿表只承载"还没提交的中间态"，写入频率高但语义轻；正式数据仍由「保存」这个事务提交。崩溃 / 强退后草稿仍在，作者只需再点一次保存。

#### 8.6.3 关闭与切换的拦截

存在未保存改动时，以下动作**一律拦截并询问**，不允许静默丢弃：

| 动作 | 提示 |
|---|---|
| 关闭面板 | 「有 3 处改动未保存」→ [保存并关闭] [丢弃改动] [取消] |
| 切换章节 | 同上，并在文案中说明改动属于哪一章的行囊 |
| 切换主角（未来） | 同上 |
| 应用退出 | 同上（走 NovelWindow 的 close 拦截） |

**默认焦点落在「保存并关闭」**，不是「丢弃改动」。

#### 8.6.4 保存点与回退（与盘点记录的合流）

**每次点「保存」时，先对提交前的状态生成一条盘点记录（`novel_pack_records`），再提交。** 于是：

- 「撤销到上次保存」= 恢复最近一条盘点记录
- 盘点记录列表（F-3）中多出一条 `改动前自动存档` 类型的记录
- 保留策略：自动存档类型滚动保留最近 **20 条**；作者手动标记为「里程碑」的长期保留

> 这样「保存」不只是写库，而是**产生一个可回退的版本点**。需求方说的「防止误操作丢失历史数据」，**本质要靠这一步实现 —— 只加一个按钮而没有版本点是没用的。**

#### 8.6.5 防止「忘了保存」

显式保存会引入一个新的失败模式：改了 20 处忘了点。所以必须配兜底：

- **无操作自动保存**：可配置，默认**开**，间隔 **5 分钟**。到点且有未保存改动 → 自动提交并生成存档点，头部短暂提示「已自动保存」。
- **临界提醒**：未保存改动 ≥ 5 处时，「保存」按钮做一次轻微呼吸动效（仅一次，不循环打扰）。
- 自动保存可在模块管理中关闭，但**关闭后关闭拦截仍然生效**（这是不可关的安全底线）。

#### 8.6.6 保存失败

写库失败**绝不静默**：

- 提交失败 → 状态回退为「有未保存改动」，头部出现红色可重试条，**草稿原样保留**
- 部分失败（多表写入）→ **整体回滚**，不允许出现"表 A 写了表 B 没写"的中间态
- 连续失败 3 次 → 提供「导出当前草稿为 JSON」的逃生出口（数据不能出不去）

#### 8.6.7 与原则 1 的最终确认

| 场景 | 是否合规 |
|---|---|
| 改物品数量 `+/-`，数值即时变化，**不弹窗** | ✅ 符合原则 1（只是落库延后） |
| 改属性基础值，行内输入即生效 | ✅ 符合 |
| 切换持续效果开关，汇总即时重算 | ✅ 符合 |
| 每改一个字段都要求点一次「保存」 | ❌ **不符合，本 PRD 明确禁止** |
| 整个面板一个「保存」按钮 | ✅ 本节的方案 |

**关键设计决策：加成表统一 vs 分表**

- **选择：统一多态表**
- 理由：汇总管线只需扫一张表 → 重算性能 O(n) 而非多次查询；新增加成来源（状态、称号、宗门）无需改表
- 权衡：外键级联需显式处理（删除 item/skill 时级联删 modifier），SQLite 需开启 `PRAGMA foreign_keys`；若项目当前未开，改为应用层事务清理

### 9.2.1 效果性质：被动 / 持续 / 释放（v1.3 新增，本节为模型正确性前提）

> **背景（需求方原话）：** 「有些技能或者装备效果是主动的，还有些是被动的；无法差别体现主动效果和被动效果；现在只有一个佩戴和激活，两者有时候可能都会存在。」

**问题诊断：这是两个正交的轴被压成了一根轴。**

| 轴 | 含义 | 现状 |
|---|---|---|
| **轴 A：载体状态**（Carrier State） | 这件东西「在不在身上 / 用不用」 | ✅ 已有：装备=佩戴、技能=启用 |
| **轴 B：效果性质**（Effect Nature） | 这条效果是「常驻改数值」还是「要角色主动做一个动作」 | ❌ **缺失，全部被当成常驻加成处理** |

装备的「佩戴」与技能的「启用」**本就是同一个轴的同构表达**（都只回答「载体的效果有没有资格生效」）。把它们当成两回事，再加上没有轴 B，就导致：一件装备同时带「被动 +500 防御」和「主动·铁壁姿态」时，面板只能把它们混成一堆加成，无法区分、无法分别控制。

**解法：给每一条效果声明 `nature`，共三档。**载体状态恒有 1 个，效果开关按性质出现——**开关长什么样由效果类型决定，而不是每个载体都长一样**，这正是「差别体现」的落点。

| 性质 | UI 徽标 | 语义 | 需要开启开关？ | 计入总属性汇总？ | 典型例子 |
|---|---|---|---|---|---|
| **被动** `passive` | `被`（灰） | 载体在效即常驻生效 | ❌ | ✅ **计入** | 风雷双匕：攻击 +320；龟息术：防御 +8% |
| **持续** `sustained` | `持`（蓝） | 载体在效后，还需**显式开启**才生效；有消耗与持续时间 | ✅ **额外开关** | ✅ **开启时计入** | 铁壁姿态：开启后防御 +40%，每回合耗 5 法力；杀意领域：范围内敌人闪避 -15% |
| **释放** `cast` | `放`（橙） | 需角色主动释放，瞬时结算 | ❌（它是动作，不是状态） | ❌ **永不参与属性汇总** | 疾风斩：造成 300% 攻击力伤害，CD 12s，耗蓝 30 |

**三层开关不会叠加成混乱。** 一个载体的状态组合是：

```
技能「龟息术」         → 启用/停用（载体）        → 被动效果直接生效
装备「玄龟甲」         → 佩戴/卸下（载体）
   ├ 被动：防御 +500   → 佩戴即计入
   └ 持续：铁壁姿态    → 额外开关 ON/OFF → 开启才计入
装备「风雷双匕」       → 佩戴/卸下（载体）
   ├ 被动：攻击 +320   → 佩戴即计入
   └ 释放：风雷一击    → 只记录参数，不进汇总
```

**关于第 4 种组合：被动 · 事件型。** 如「受到伤害时 20% 概率反弹 50% 伤害」。它不需要开启，但也不修改常驻属性。本 PRD **不单列第四档**，而是用 `nature='passive'` + `trigger='on_damaged'` 表达：**有 `trigger` 的效果一律不计入属性汇总**（判定优先级：`nature='cast'` → 不计入；`nature='sustained'` → 看 `active`；`nature='passive'` + 有 `trigger` → 不计入；其余计入）。

**汇总分解维度随之从 2 段变 3 段。**原汇总只回答「基础 → 总览」，现在必须回答「基础 / 被动贡献 / 持续贡献」——否则作者看不出「这个数是我穿上就有，还是我开了态势才有」。

```
final = (base + Σadd_被动 + Σadd_持续)
        × (1 + (Σpercent_被动 + Σpercent_持续) / 100)
        × Π mul_被动 × Π mul_持续
```

**为什么 `cast` 型不计入汇总（这是本节最重要的边界判断）：**
1. 它不是一个「属性修改器」，而是一次**动作的结果**。把「疾风斩造成 300% 伤害」算进攻击力，等于把弹药算成火力。
2. 计入会让「总属性」变成时间相关量——同一个面板，开战前和战斗中显示不同数字，作者反而失去基准。
3. **单向依赖是允许的**：`cast` 型效果**可以读取**汇总结果（倍率常写作「300% 攻击力」），但**不写入**汇总。面板在展示倍率时高亮引用到的属性当前值，方便作者照抄。

> ⚠️ **边界守则：只记录与展示，不结算。** 面板**不提供「释放」按钮**、不模拟伤害、不推演战斗回合——那属于 §14 明确的范围外（战斗模拟器）。作者要的是「写战斗前知道我这个技能参数是多少」，不是「帮我打赢」。

**给工程的两条硬约束：**
- `target_attr_id` 必须允许为 `NULL`（`cast` 型不指向任何属性），否则无法入库
- 汇总纯函数的**输入签名必须带 `nature` 与 `active`**，不能只看「载体在效」就累加——这是本项目最容易写错的一处（见 §9.4.1）

### 9.3 量纲体系：同入口、三模型

**这是本 PRD 最重要的技术澄清。** 需求原文把境界 / 熟练度 / 货币并列为「单位转化」，但三者的数学模型**互不等价**，不能共用一套换算实现：

| 类型 | 数学模型 | 典型例子 | 可换算性 |
|---|---|---|---|
| `ratio` 进制型 | **严格线性比例** | 1 金 = 100 银 = 10000 铜 | 双向精确，可自动进位 |
| `ladder` 阶梯型 | **有序非线性序列** | 炼气九层 → 筑基 → 金丹 → 元婴 | 不可线性换算（一层≠若干铜板）；只支持**位次比较**与作者自定义的**战力当量** |
| `threshold` 阈值型 | **数值区间 → 名称映射** | 熟练度 0-99 入门 / 100-499 熟练 / 500+ 大师 | 单向（数值 → 等级名 + 区间进度） |

统一抽象（TS 示意）：

```ts
type UnitSystem =
  | { kind: 'ratio';      base: string; levels: { name: string; ratioToBase: number }[] }
  | { kind: 'ladder';     levels: { name: string; order: number; subLevels?: number; power?: number }[] }
  | { kind: 'threshold';  levels: { name: string; min: number; max: number | null }[] }
```

**「作者需先设置」的落地：** 未配置 → 依赖模块显示「未配置，点击设置」引导，**不硬编码默认值**。这一点必须守住，否则会拿一套默认设定污染完全不同小说的世界观。

### 9.4 总属性汇总管线（必须严格定义）

#### 9.4.1 参与条件

条件分**两道闸门**，必须依次通过才计入（v1.3 修正：原先只有第一道，导致主动效果被错误累加）：

**闸门 1 —— 载体在效（Carrier State）**

- 物品：`equipped_slot_id` 非空 且 槽位在 `capacity` 内 且 类型通过 `accepts` 校验
- 技能：`enabled = true`
- 状态：`active = true`（P1）

**闸门 2 —— 效果性质允许计入（Effect Nature）**

| `nature` | 额外条件 | 结果 |
|---|---|---|
| `passive` | 无 `trigger` | ✅ 计入 |
| `passive` | **有** `trigger`（如 `on_damaged`） | ❌ 不计入（事件型） |
| `sustained` | `active = true` | ✅ 计入 |
| `sustained` | `active = false` | ❌ 不计入 |
| `cast` | — | ❌ **永不参与汇总** |

> 判定写成显式函数 `isCounted(mod) -> boolean`，禁止在累加处散落 `if`。汇总纯函数输入为 `(attributes, modifiers[], carriers[])`，输出为 `{ final, breakdown[] }`，其中 `breakdown` 的每一条**必须带 `nature` 标记**，供 §9.4.4 的明细分组。

#### 9.4.2 计算顺序

```
if 存在 op='override' 且 通过两道闸门:
    final = override 值（取 sort_order 最后一条）
else:
    final = (base + Σ add_被动 + Σ add_持续)
            × (1 + (Σ percent_被动 + Σ percent_持续) / 100)
            × Π mul_被动 × Π mul_持续
```

> 顺序固定为 **加算 → 百分比 → 乘算**，与主流游戏一致，避免不同作者写出不同结果。
> **被动与持续在数学上是同一池子**（都走同样的运算优先级），**只在展示层分组**。这一点必须说清楚：不要为了分组而把两类拆成两轮乘算，那会算出与作者预期不符的结果。
> `override` 优先级最高且**只取一条**（多条时取 sort_order 末位，并在明细中给出警示）。
> `cast` 型效果**不进入本管线**，但仍会出现在「汇总模块 → 另有 N 项主动技能」的提示行里（见 C-2）。

#### 9.4.3 熟练度缩放
当某技能加成勾选「按熟练度缩放」时，该条加成值为：

```
scaled = value × lerp(minScale, maxScale, clamp(proficiency / maxProficiency, 0, 1))
```
`minScale / maxScale / maxProficiency` 由作者在量纲或技能配置中给出。

#### 9.4.4 明细与性能
- 汇总结果**必须可反查明细**（REQ-017）：记录每条 `(sourceId, nature, active, appliedValue)`，不是只返回终值——**`nature` 与 `active` 必须一并记录**，否则 UI 无法做 §9.2.1 的「被动 / 持续」分组（REQ-041）
- 重算用 `Map` 缓存 + 脏标记增量；符合项目既有的「重计算用 Map 缓存」规范
- 汇总计算抽为**纯函数**，用 vitest 覆盖（含 §9.4.2 的运算优先级与 §9.4.3 的熟练度插值）；建议每个运算分支至少 1 个回归用例
- **`isCounted()` 的闸门矩阵必须单独覆盖 6 个用例**（§9.4.1 表格 5 行 + 一条「同一载体同时带 passive 与 cast，只有 passive 计入」的组合用例）。这是本功能最易回归的缺陷点：把 `cast` 算进总属性在视觉上毫无异常，只有对着数字才发现

### 9.5 与既有能力的整合

| 既有能力 | 复用方式 |

### 9.7 境界 ↔ R25 联动：复用既有等级体系（v1.4 新增，Q2 结项）

**决定：复用既有 R25 等级体系，不另建量纲表。** 境界在行囊里是**同一份数据的第二个视图**，不是一份副本。本节基于**已核对代码**的现状撰写，不是推测。

#### 9.7.1 既有结构盘点

| 既有 | 结构 | 对应 §9.3 的 ladder |
|---|---|---|
| `novel_level_systems` | `id, work_id, name, note` | ✅ 体系（一套境界，如「灵徒九境」） |
| `novel_levels` | `id, system_id, name, rank, note` | ✅ 阶（按 `rank` 排序） |
| `novel_level_conversions` | `id, from_level_id, to_level_id, relation, note` | ⚠️ 这是**体系间换算**，**不是阶内进位** |
| `novel_links` | `from_type, from_id, to_type='level', to_id, relation='当前境界'` | ✅ **当前境界的落库位置就在这一行** |
| IPC | `novel-level-system-add/rename/delete`、`novel-level-rename/delete`、`novel-link-add/remove` | ✅ 写入通道已具备 |

> **关键发现：`novel_levels` 只有 `rank`，没有「小层」。** 而 §9.3 的 ladder 与原型演示数据都需要「筑基七层」这种**主阶 × 小层**结构（原型里是 `sub: 9`）。**这是"复用"这个决定的唯一实质缺口，必须补。**

#### 9.7.2 三个必须补的缺口（诚实清单）

| 缺口 | 现状 | 补充方案 | 代价 |
|---|---|---|---|
| **① 小层（主阶 × 子层）** | 无字段 | `novel_levels` 加 `sub_levels INTEGER NOT NULL DEFAULT 1`（该阶有几小层；1 = 无小层，**兼容既有数据**） | 一个 migration，零破坏 |
| **② 战力当量** | 无字段 | `novel_levels` 加 `power REAL`（可空；作者自定义的跨阶比较基准，供 §9.3 的 `ladder` 使用） | 同上 |
| **③ 阶内进位** | 无实现 | 进位规则放**渲染层纯函数**，不入库：`at_sub >= sub_levels` → 进位到 `rank + 1` 的第 1 层 | 逻辑成本低，但**必须单测** |

> 三项都是**加列 / 加函数，不新建表、不改既有语义** —— 所以「复用」这个决定是站得住的。**前提是这三项要在同一个 migration 里一次做完**，不要分两次动 `novel_levels`（分两次会多一次表重建风险）。

#### 9.7.3 单一事实源与双向同步

```
                    ┌──────────────────────────────────┐
                    │  novel_links                     │
                    │  from_type='character'           │  ← 唯一事实源
                    │  to_type='level'                 │
                    │  relation='当前境界'             │
                    │  + 小层进度（见 9.7.4）          │
                    └───────────────┬──────────────────┘
                          ┌─────────┴─────────┐
                          ▼                   ▼
                  行囊 · 境界模块      实体面板 · EntityDetail
                  （读写同一行）       （读写同一行）
```

- **行囊「突破」→ 写 `novel_links`** → 主进程广播通知 → EntityDetail 重读
- **EntityDetail 改境界 → 写同一行** → 广播 → **行囊境界模块跟随刷新**（面板打开时）
- 阶梯名称 / 小层数 / 战力当量改的是 `novel_levels`，两边读同一张表，天然一致

**必须新增的通道（工程确认）：** 现在有 `novel-link-add` / `novel-link-remove`，但**没有"改"、也没有"通知"**。需要：
- `novel-link-set`：**幂等设置**，避免前端自己判断该 add 还是 remove（这类判断是 bug 温床）
- 一条跨组件通知：可复用既有 `windowManager` 广播，或渲染层事件总线。**参照 `registerActivityNotifyBridge()` 的显式注册模式**（`AGENTS.md` 要求：仅需某窗口处理的推送，封装成显式注册函数，避免模块加载副作用扩散）

#### 9.7.4 小层进度存哪儿（Q11，需工程定）

「当前在第几小层」是**状态**，不能塞进 `novel_levels`（那是定义）。两个选项：

| 方案 | 做法 | 权衡 |
|---|---|---|
| **A（倾向）** | 复用 `novel_links` 那行的 `note` 存 JSON 如 `{"sub":7}` | 零 migration；语义上略挤，但 `note` 在 R25 中当前未被使用 |
| **B** | 新建 `novel_level_progress(entity_id, level_id, sub)` | 语义干净，但多一张表，每次突破要 upsert |

倾向 **A**，技术方案评审时定；若工程判断 `note` 会被占用则走 B。

#### 9.7.5 ⚠️ 最容易踩的坑：ID 不是同一套

- `novel_links.from_id` 指向的是 **EntityPanel 的实体 ID**（`novel_entities.id`）
- 行囊的 `novel_pack_characters.id` 是**另一套 ID**
- **若不建立映射，双向同步会写进两条互不相干的关系行，表现为"改了没反应"** —— 而且这个 bug **不报错、只有静默不同步**，是最难发现的一类集成缺陷

**方案：** `novel_pack_characters` 增加 `entity_id TEXT`（可空，指向 `novel_entities.id`）。首次打开境界模块时：

1. 若已存在主角实体 → 让作者选一个绑定（默认选中标记为主角的实体）
2. 若不存在 → 提示可一并创建，或允许「仅行囊内使用」（此时境界**不参与 R25 联动**，但行囊内功能完整可用）

**这条必须在技术方案评审中单独确认**，属于"会静默失败"的集成缺陷。

#### 9.7.6 预留扩展位：境界的两种语义（口子，v1.5）

**现状（v1 唯一实现，linked）：** 行囊境界 **≡** 面板境界，是同一个数（§9.7.3）。

**可能的未来（split，本版不实现）：** 两者分离 —— 行囊记「真实修为」，面板挂「对外宣称的修为」。典型写作场景是扮猪吃虎、马甲、对外压制境界。

**做法：留口子 ≠ 先加一个空字段。** 提前加一个没人写的空列，只会在未来变成没人敢删的僵尸列。真正决定「切换成本」的，是**这个字段被多少处代码直接碰过**。

**所以 v1 只做一件事：把境界的读写收敛成一对函数。**

| 口子面 | v1 签名 | 未来 split 时的实现变化 | 调用方改动 |
|---|---|---|---|
| **读（行囊视角）** | `getRealm(): { level, sub }` | 优先返回独立值，缺失则回退联动值 | **零** |
| **读（面板视角）** | `getPanelRealm(): { level, sub }` | 不变（面板永远读联动值） | **零** |
| **写** | `setRealm(level, sub, origin)` —— **唯一写入口** | 按开关写独立字段或联动字段 | **零** |
| **落库** | `novel-link-set`（幂等 upsert） | 增加 `novel-pack-realm-standalone-set` | **零** |
| **UI** | 境界模块内无开关 | 境界模块内加「独立境界」开关 | 仅该模块内部 |

**工程契约（REQ-048）：**

1. 所有境界读取必须走 `getRealm()`；需要「对外展示的那份」时走 `getPanelRealm()`。
2. 所有境界写入必须走 `setRealm()` —— **任何绕过它的写入都算实现缺陷**，即使功能正确。
3. **禁止任何代码直接引用境界字段**（`novel_pack_characters.realm_at` / `novel_links` 的「当前境界」行）。

> **第 3 条不依赖 split 是否真的做，现在就要拦。** 直接引用不会在 v1 出错，只会在未来切换时变成 §9.7.5 那样的**静默不同步**。

**写入口必须知道「写哪一份」—— 这是口子最容易被实现错的地方（原型实测，非推演）：** `setRealm(level, sub, origin)` 的 `origin` 不是「哪个界面调的」这种文案用途，它决定**路由目标**：`origin === 'r25'` → 永远写面板那份；其余在 split 下写行囊自己那份。**若忽略这层语义，R25 侧的改动会落进行囊那份** —— 表现为「面板看着变了、行囊侧却没跟着变」的**反向**静默不同步（与 §9.7.5 是同一类缺陷的镜像）。原型第一版就踩了这个，被断言抓出后修正。

**契约不写下来就会当场被绕过 —— 同一轮实测的第二条证据：** 固化口子后做的第一遍全量检查，就抓到**一处真实越界** —— 面板头部的境界 chip（`renderChips()`）直接读了 `realm_at`。它当时**功能完全正常**，但在 split 打开后**不会跟随**。已改为走 `getRealm()`。**所以契约不是「照做一遍」，而是「每次改动后查一遍」** —— 这就是 §9.6 问题 8 的全部意义。

**这条契约的收益不依赖 split：** 即使永远不做 split，收敛访问也有三个即时好处 —— ① 阶内进位规则只有一处可改、可单独单测；② 「改了没反应」类 bug 的排查范围从全代码库缩到一个函数；③ 未来若要做「境界变动历史 / 突破日志」，挂点现成。

**为什么 v1 不直接做 split：** 多一个开关 = 作者每次改境界都要先想「我改的是哪一个」，这是纯认知税；且目前**没有任何证据**表明目标作者存在双值需求（§11 访谈加一条验证）。

**升级触发条件（出现任一，就把口子变成功能）：**

1. 作者反馈里出现「对外宣称的境界 / 真实修为」这类**双值表述**；
2. 出现「同一角色在不同章节需要展示不同境界」的用例；
3. 明确出现马甲 / 伪装 / 扮猪吃虎类写作场景的需求。

> 原型里有一个标注「预留扩展位」的开关（`#split=1`）用于**验证这个口子确实成立**：打开后行囊境界与面板境界分离，而**切换这个开关没有改动任何一个调用点**。**正式版 v1 不输出该开关** —— 它只属于设计验证，不属于产品。

### 9.6 给工程的问题

1. 「分离窗口」形态是否要新建窗口登记？单实例唤起如何管理？（参照 SettingsWindow）
2. `novel_pack_*` 表是否需要一并纳入现有 novel 备份导出链路？
3. EditorPane 当前是否消费了某些组合键？`Ctrl+Shift+B` 是否有冲突需要改？
4. 500+ 物品是否需要引入虚拟滚动，还是由主进程分页返回？（倾向先做前端分页，把虚拟滚动留到实测卡顿时再引入）
5. **草稿写入频率**（v1.4）：编辑防抖多久写一次 `novel_pack_drafts`？倾向 **800ms 防抖 + 面板关闭时必写**，需确认对 SQLite 的压力。
6. **`novel-link-set` 是否可以做成幂等 upsert**（v1.4）：避免前端判断 add/remove，减少一类竞态 bug。
7. **`novel_levels` 加列能否一次到位**（v1.4）：`sub_levels` 与 `power` 建议同 migration，避免二次表重建。
8. **境界读写收敛契约能否落入工程规范**（v1.5）：建议在代码评审清单里登记「禁止直接引用境界字段 / `novel_links` 的当前境界行」；若工程有 lint 能力，可加一条自定义规则。**这是口子能否存活的关键** —— 契约不会被一次性实现，只会被日常迭代一点点绕过（§9.7.6）。
9. **`getRealm` / `getPanelRealm` / `setRealm` 的落点确认**（v1.5）：建议放渲染层纯函数 + 主进程幂等通道。请工程确认这个边界是否干净、有没有必须从渲染层直连数据库的例外。

| **加成汇总的结果不符合作者预期（信不过）** | 中 | 高 | 强制提供来源明细与算式；固定运算优先级；✏️ Beta 期收集 5 个真实小说配置做回归用例 | PM + 工程 |

| **量纲三模型差异被工程简化为一套换算** | 中 | 高 | 本 PRD §9.3 已固定模型定义；技术方案评审必查 | 工程负责人 |
| **⚠️ 效果性质（§9.2.1）被工程简化为一根轴**（v1.3 新增） | **中** | **高** | 这是**需求方亲口反馈的缺陷**，极易复发：实现时若把「佩戴 / 激活」直接当成「效果生效」、不给 `nature` 分三档，主动效果会被静默累加进总属性——**视觉上完全无异常，只有对着数字才发现**。缓解：① 汇总纯函数输入签名必须含 `nature`/`active`（§9.4.1）；② `isCounted()` 闸门矩阵写 6 个单测（§9.4.4）；③ 技术方案评审必查「cast 型是否被排除」 | 工程负责人 + PM |

| **面板打开拖慢编辑器首屏** | 低 | 中 | 面板 lazy 挂载 + 汇总结果缓存；非功能需求已量化 Δ<100ms | 工程 |

## 14. 范围外

以下**明确不进 v1**，为防止范围蔓延、对齐期望：

| 排除项 | 原因 | 何时可能纳入 |
|---|---|---|
| **多角色（配角/反派/对手）管理** | 需求明确「当前先实现主角的」。UI 不暴露多角色入口 | P2（REQ-036）。**数据模型已预留 `character_id`** |
| **多角色间的换装备 / 交易** | 同上 | P2 之后 |
| **派生属性公式引擎**（攻击=力量×2+武器） | 引入表达式解析与安全沙箱，复杂度与收益不匹配 | P2（REQ-035） |
| **与在线同步 / 云备份的打通** | CheckIn 当前为本地优先架构 | 待基础设施就绪 |
| **移动 / Web 端适配** | CheckIn novel 版为桌面 Electron 应用 | 无计划 |
| **面板数据自动从正文解析**（NLP 抽取主角装备） | 当前无本地 NLP 能力，准确率不可控 | 长期探索 |
| **战斗模拟器 / 数值推演** | 超出「盘点」范畴 | 无计划 |
| **释放型效果的「释放」与伤害结算** | 面板只**记录并展示**主动技能的参数（倍率 / CD / 消耗 / 目标），**不提供释放按钮、不模拟结算**。理由：① 结算会引入回合、命中、抗性、目标选择等一整套战斗系统；② 会让「总属性」变成时间相关量，作者失去基准（§9.2.1）。**主动效果可以读取属性汇总，但不写入** | 无计划（§9.2.1 已定边界） |
| **小说间模板社区分享** | 需账号与分发体系 | P2 + 账号体系成熟后 |

### C. 术语表

| 术语 | 含义 |
|---|---|
| **行囊** | 本功能的产品名。主角当前状态的实时拼图视图：四核心模块 + 总属性汇总 + 可选模块 |
| **盘点记录** | 行囊在某一时刻的存档快照，用于「与本章初对比」（REQ-029）。与既有「章节历史快照」`SnapshotDrawer` 是两回事 |
| **让位（reflow）** | 正文区域重排收窄以腾出空间，内容不被覆盖 |
| **Peek** | 按住即看、松手/超时即消失的临时浮层 |
| **量纲体系（Unit System）** | 一套自定义的「该怎么读这个数」的规则：进制 / 阶梯 / 阈值三选一 |
| **槽位（Slot）** | 一个部位下可穿戴的格子数（戒指 2 槽 = 可戴两枚） |
| **运算 op** | add 加算 / percent 百分比 / mul 乘算 / override 覆盖 |
| **载体状态（Carrier State）** | 装备「佩戴 / 卸下」与技能「启用 / 停用」的统一抽象：只回答「这个载体的效果有没有资格生效」。**是所有载体都有的第一道闸门**（§9.2.1 轴 A） |
| **效果性质（Effect Nature）** | 单条效果的类别：`被动` / `持续` / `释放`。决定该条**是否带独立开关**、**是否计入总属性**。**与载体状态正交**（§9.2.1 轴 B） |
| **被动（Passive）** | 载体在效即常驻生效的效果，无开关，**计入**总属性。例：风雷双匕 攻击 +320 |
| **持续（Sustained）** | 载体在效后仍需**显式开启**才生效的效果，带独立开关与消耗。开启时**计入**总属性。例：铁壁姿态 防御 +40%，每回合耗 5 法力 |
| **释放（Cast）** | 需角色主动释放、瞬时结算的效果，**永不参与**总属性汇总，面板只记录与展示其参数。例：疾风斩 300% 攻击力 / CD 12s |
| **汇总闸门（Gates）** | 汇总管线的两道判定：① 载体在效 ② 效果性质允许计入。**两道全过才累加**（§9.4.1） |
| **草稿（Draft）** | 已编辑但**尚未提交**到正式表的状态。存主进程 `novel_pack_drafts`，跨窗口一致、崩溃不丢（§8.6） |
| **保存点** | 每次点「保存」时对**改动前**状态生成的盘点记录，作为可回退版本点。自动存档类型滚动保留最近 20 条（§8.6.4） |
| **载体绑定（`entity_id`）** | 行囊主角与 EntityPanel 实体的 ID 映射。**缺失会导致境界双向同步静默失效**（§9.7.5） |
| **境界读写口子** | `getRealm()` / `getPanelRealm()` / `setRealm()` 三个函数 —— 境界字段的**唯一合法访问路径**（§9.7.6） |
| **独立境界（standalone realm）** | 预留的 split 语义：行囊记「真实修为」、面板挂「对外宣称」。**v1 不实现**，只保留读写口子与升级触发条件（§9.7.6） |

### D. 输出本 PRD 时主动识别的问题（供评审）

1. **量纲三模型不可合并**（§9.3）：需求表述中的统一「单位转化」实际是三种数学性质不同的东西，必须分实现。
2. ~~**「快照」命名冲突**（§15 Q1）~~ → ✅ **已解决 2026-09-29**：功能定名「行囊」，历史存档改名「盘点记录」，与章节历史快照解耦。
3. **先实现主角 ≠ 单角色模型**（§14）：UI 只露一人，模型必须按 `character_id` 设计，否则多角色是重构级改动。
4. **默认值会污染不同世界观**（§8.4 原则 4）：所有未配置状态必须显示引导而非硬编码默认值。
5. **「不遮挡」是多形态问题而非单一样式问题**（§8.2）：单靠 reflow 满足不了双屏与临时速览场景，需三形态并存。
6. **主动 / 被动是两个正交轴，不是一根轴的两端**（§9.2.1，v1.3 新增）：需求方反馈「只有一个佩戴和激活，无法差别体现主动与被动，且两者会同时存在」。诊断结论是「载体状态」与「效果性质」被压成了一根轴 —— 必须拆开，否则主动效果会被错误累加进总属性，且一件装备上的被动与主动无法分别控制。
7. **主动效果必须区分「持续」与「释放」两种情况，不能只分被动/主动两档**（§9.2.1，v1.3 新增）：只分两档仍会出错 —— 「开启后防御 +40%」是应该计入汇总的（开启时），而「造成 300% 伤害」不该计入。两者的差别不是「主动与否」，而是**是否修改常驻属性**。
8. **「复用 R25」这个决定只覆盖了 60% 的现状**（§9.7.2，v1.4 新增）：核对代码后发现 `novel_levels` **没有小层字段**、没有战力当量、也没有阶内进位实现。三处都要补，但都是**加列 / 加纯函数**，不改既有语义，所以复用仍然成立 —— **但必须一次改到位，不可分两次动 `novel_levels`**。
9. **保存按钮若不给版本点，等于没解决问题**（§8.6.4，v1.4 新增）：需求方要的是「防误操作丢数据」，而按钮本身只改变落库时机。真正防丢失的是**每次保存前自动生成一条盘点记录**这个动作。**只做按钮不做版本点，是最容易交付出来的假解决。**
10. **境界双向同步有一个会静默失败的集成点**（§9.7.5，v1.4 新增）
11. **「留口子」的正确姿势是收敛访问，不是先加空字段**（§9.7.6，v1.5 新增）：需求方要求为「行囊境界 ≠ 面板境界」留口子。若直接加一个 `realm_standalone` 空列，它不会被写、也不会被读，未来仍是僵尸列；真正决定切换成本的是**字段被多少处代码直接碰过**。故 v1 只把读写收敛成三个函数，代价近零，且收益**不依赖 split 是否真的做**。：`novel_links.from_id` 是实体 ID，行囊角色 ID 是另一套。没有映射就会写进两条互不相干的关系行，表现为「改了没反应」，**不报错、不崩溃**，只在人工比对时才发现。
