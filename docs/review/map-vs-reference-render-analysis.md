## 0. 一句话结论

**参考实现的「和谐」不是渲染技术更好，而是把「素材撒布」当成一个有先验的空间布局问题来解：
先划分可放置区域（像素 alpha 掩码）→ 用网格控制密度与尺度 → 用气候带/连通性筛选素材族 →
以「丛簇」而不是「单点」为单位落位 → 最后按脚底 y 重排 z 序。**

本项目把同一个问题解成了「均匀随机撒点 + 碰撞拒绝」，因此在**密度梯度、成团性、素材族一致性、
边缘留白**四件事上同时缺失 —— 这恰好就是「贴纸感」与「手绘感」的分界。

## 2. 技术形态与数据模型（证据先行）

### 2.1 形态

纯 **Canvas 2D** 单页应用，非 WebGL / 非场景图引擎：

| 事实 | 证据 |
|---|---|
| 整张地图是一块固定尺寸 canvas | `map.html`：`<canvas id="canvas" width="595" height="842">`（A4 比例） |
| 自研极简「Stage」节点树（链表式，支持 `insertNext` / `remove` / `pin`） | `Stage.create()` / `ProjectActiveEntiy.paint.insertNext(b)` |
| AMD 按 `js_version` 加载，主包单文件 1.79MB | `js/map.js`：`requirejs.config({ baseUrl: ... , urlArgs: js_version })` → `all_model_base.js?v=1.122` |
| 无 WebGL、无矢量渲染器 | 全包 `getContext("2d")`，无 `gl.` 调用 |

### 2.2 图层栈（固定 11 层，自底向上）

`layer.CreatreBaseLineLayer` 一次装配，顺序写死：

```
basemap → shawdow_layer → paint(陆地/地形本体) → paint_cover[0](海洋修饰)
        → polygon_baseline → line_baseline → grid
        → point_baseline(素材) → text_baseline(地名) → mask_layer → default_layer
```

（证据：`decoded.js@203543` `CreatreBaseLineLayer:function`）

**关键观察 1**：`paint`（陆地）在 `point`（素材）**之下**，`text` 在素材之上 —— 这一条与本项目
`sheet/sea/coast/region/element/label/overlay` 的次序**基本一致**，不是差距来源。

**关键观察 2**：他们有一个本项目完全没有的层 —— `paint_cover`（画笔覆盖层，海洋浪花/海岸装饰），
位置**在陆地上、区块下**。

### 2.3 数据模型

```js
FeatureEntity = { name, x, y, z, width, height, scaleX, scaleY, alpha, angle, con }
ProjectEntity = { page, grid, mask_layer, text[], points[], lines[], polygons[],
                  paint, paint_cover[], shawdow_layer, basemap,
                  tree_folders: { text[], point[], line[], polygon[] }, cons[] }
FeatrueTypeEnum = { TEXT, POINT, LINE, Line_Dot, PAINT, PaintCover, POLYGON, BASEMAP,
                    ShawdowLayer, LayerBaseLine, *TreeFolder, AIBaseMap }
```

- `z` 是**独立于插入顺序的浮点层序**（本项目没有这个概念，纯靠 Pixi 插入顺序）。
- `tree_folders` = **图层组**，素材可以归类到组里，组有独立的 z 与显隐。
- `paint` 是**位图画布**，不是矢量多边形 —— 这是全篇最重要的架构分叉（见 §6 根因 A）。

## 3. 「和谐分布」的六个机制

### 3.1 素材组织：三套风格包 × 地貌带分池

素材在打包期就被拆成 **3 套互不混用的风格包**（魔幻 / 仙侠 / 羊皮纸），每套内部再按
**地貌带**分池。实测清单（脚本产出，见附录 A）：

| 风格 | 山体·主池 | 山体·丘陵带 | 山体·沙漠带 | 山体·雪原带 | 聚落 | 植被 | 小计 |
|---|---|---|---|---|---|---|---|
| 魔幻 | 30 | 4 | 3 | 6 | 9 | 3 | **55** |
| 仙侠 | 32 | 10 | 6 | 19 | 7 | 11 | **85** |
| 羊皮纸 | 30 | 9 | 12 | 30 | 7 | 7 | **95** |

代码形态（`decoded.js` 三处 `I.src=` 分支）：

```js
P==MapStyleEnum.MOHUAN?(I.src=..., I.mountains="30 张 · 空格分隔", 
                        I.mountains_grass=[4 张], I.mountains_desert=[3 张],
                        I.mountains_poles=[6 张], I.citys=[9 张],
                        I.forest1=[1 张], I.forest2=[1 张], I.forest3=[1 张])
```

**为什么这是「和谐」的第一层**：山体不是「一个池随机取」，而是**按所处地貌带换池**。
在雪原带上取 `mountains_poles`，在沙漠带上取 `mountains_desert`，读者看到的是
「同一气候带内画风一致、跨带渐变」——这正是真实地图的读法。

对照本项目：**52 张符号 + 4 张底图、9 个分类、只有一套**，风格靠 `ColorMatrixFilter` 整体染色
（`style.ts`）。分类维度是「展示用途」（mountain/forest/desert/settlement…），
**没有「气候带 / 地貌带」维度**，也没有按风格分包。

### 3.2 可放置区域：像素 alpha 掩码，不是「点在多边形内」

```js
// 掩码栅格化：逐格统计 alpha>51（≈20%）的像素占比
for (p...) for (C...) if (51 <= c[4*(p*d+C)+3]) v++;
v >= 0.3 * t && (m = true, k[h][l] = 1);      // 格内 ≥30% 像素不透明 → 可放
```

（证据：`decoded.js@590270`）

配置页的原话也是这一条：

> 「已有大陆须要在画笔层上…，**判定范围是画笔层上所有透明度大于 20% 的部分**。」
> （`decoded.js`：`lcw_useland_help` 的提示文案）

**为什么这是「和谐」的第二层**：陆地的存在形式是**带软边的位图**。海岸线附近 20%~100%
之间的半透明过渡区，在掩码里**天然不被计入可放置格** —— 于是海岸线自动得到一圈留白，
素材不会压在岸线上，轮廓始终干净。

对照本项目：`land.ts` 的 `pointInLand()` 判的是**素材锚点是否落在多边形内**。
锚点在多边形内即可落位，元素半径仍可越过海岸线 → 海岸轮廓被贴图糊掉，
`coastBake` 辛苦烘出来的白边被素材盖住。

### 3.3 布点：网格 + 每格 N 个 + 格内抖动（最核心的一条）

主循环（`decoded.js@551871`）：

```js
for (r = 0; r < rows; r++)
  for (t = 0; t < cols; t++)
    if (l[r][t] > 0 /* 有地形 */ && n[r][t] == 1 /* 可放置 */) {

      // ① 按地貌带选池 + 定基准尺度 w + 抖动幅度 D + 旋转范围
      if (m[r][t] === 0) {           // 丘陵带
        pool = I.mountains_grass;  w = 0.50 (仙侠 0.15 / 羊皮纸 0.20);
        D = rand(0,12)/100;        rot = ±15°;
        if (D > 0.06) { skip; }     // ← 主动丢弃约 50% 的格子（留白）
      } else if (k[r][t] === 0) {   // 沙漠带
        pool = I.mountains_desert; w = 0.50; D = rand(0,12)/100;
      } else if (贴边 2 行) {        // 雪原带（纬度带）
        pool = I.mountains_poles;  w = 0.18 (仙侠 0.25); D = rand(0,7)/100;
      } else {                       // 主池
        w = 0.18 (仙侠 0.10 / 魔幻 0.11); D = rand(0,7)/100; pool = I.mountains;
      }
      if (grid > 50) w += 0.10;      // 格越大 → 素材基准越大（尺寸与密度联动）

      // ② 落点 = 格中心 + 小抖动
      x = gw*t - 40 + rand(-5, 5) （丘陵 rand(-15,15)）
      y = gh*r - 40 + rand(-10,10)

      // ③ 同一格叠几层，随风格不同：
      //    羊皮纸：单层，但落点在三档错位里随机（-40 / -30 / -20）→ 靠错位制造参差
      //    仙侠  ：两层（-40 与 -30）
      //    魔幻  ：三层（-40 / -30 / -30）
      place(x, y, ...);                              // _0，基准层
      if (MOHUAN) place(x + 10, y + 10, ...);        // _1
      if (MOHUAN || XIANXIA) place(x + 10, y + 10, ...); // _2
    }
```

尺寸换算（`a()` 内部）：`scale = (w + D) / Ma`，`Ma = 格网基准 / 36`。
`a()` 里还有两个风格专属的取素材策略：魔幻在「平地」时优先从池尾 6 张取；
仙侠用最近 4 次未用过的索引（`na` 数组，LRU 去重）保证连续几个格子不出现同一张图。

**四条可复用的设计**：

1. **密度 = 网格尺寸**（`k ∈ {36, 54, 72}`，配置页 `lcw_f_size_0/1/2`）。
   改密度不是改「总数」，而是改**格子的物理边长**——于是密度变化时素材的**相对间距恒定**，
   画面不会出现「小图很挤、大图很空」。
2. **数量档 = 每格几个**，而不是总计数。小画布按风格叠 1~3 层（羊皮纸 1 / 仙侠 2 / 魔幻 3），
   大画布（宽 ≥ 3000px）改为**格内随机撒 2~6 个**，用同一个格网播撒，
   天然形成均匀但非机械的分布。
3. **尺度与网格联动**（`grid > 50 → w += 0.10`）：稀疏时素材同步变大，
   视觉重量守恒。这是「密度控制」里最容易被忽略的一条。
4. **主动留白**：丘陵有 `D > 0.06 → continue`，约 50% 的格子直接跳过。
   手绘地图的「疏」是画出来的，不是随机撞出来的。

对照本项目（`domain/generator.ts`）：

| 项 | 参考实现 | 本项目 |
|---|---|---|
| 布点骨架 | 网格（36/54/72） | 无网格；分区中心 `ZONE_MIN_DIST=130` + 极坐标 `radius=√rand × (46√count+40)` |
| 密度控制 | 网格边长 × 每格个数 | 总数档 `70/120/190` |
| 间距一致性 | 恒定（同一格网） | 随 `count` 与 `zoneR` 变化，块与块之间不一致 |
| 尺寸 | 基准 `0.18~0.5` + 抖动 `0~0.12`，且随格网补偿 | `0.85 ~ 1.20`（与网格/密度无关） |
| 旋转 | ±15°（丘陵）/ ±5°（其余） | ±7° |
| 留白 | 丘陵主动跳过 ~50% | 无（碰撞拒绝只防重叠，不产生疏密） |

### 3.4 丛簇：森林不是「一个点」，是「3 + N 个一组」

这是全篇最值得抄的一段（`decoded.js@562661` 起）：

```js
// ① 候选点筛选用「连通性先验」
if (O[a][h] === 1) {
  f = 8 邻域内 O==1 的个数;
  e = f === 1 ? 1 : (f > 1 ? 3 : -10);       // 孤立点弱、内部点强、无邻居几乎不出
  5 < rand(1,10) + e && m.push({x:h, y:a});
}

// ② 每个候选点固定放 3 个 + 视情况向四方追加 1~4 个
ja = (sprite.width * v + 50) / Ma;            // 簇直径 = 素材宽度 + 50px 呼吸边
place(p + rand(-ja/5, ja/5), r + rand(-D, D), scale = v + rand(-D,D)/100);  // ×3
if (上) place(p + rand(-ja/5,ja/5), r - rand(ja/2, ja/3), ...);
if (下) place(p + rand(-ja/5,ja/5), r + rand(ja/3, ja/2), ...);
if (左) place(p - rand(ja/2, ja/3), r + rand(-ja/5,ja/5), ...);
if (右) place(p + rand(ja/3, ja/2), r + rand(-ja/5,ja/5), ...);
```

**两个先验**：

- **连通性先验**：孤立点（8 邻域只有 1 个同类）出现概率约 20%，内部点（邻居 ≥2）接近 100%。
  结果就是「森林成片、边缘稀疏、内部致密」——**视觉上的团块感**，而不是均匀撒点。
- **丛簇结构**：一丛 = 3~7 个互相重叠的实例，尺寸同基准微抖、位置在半个素材宽度内抖动。
  这模拟的是真实植被的「一丛树」，而不是「一棵树被复制 N 次」。

对照本项目：`generator.ts` 是**一个 slot 一个材质一个实例**，靠 `PLACE_ATTEMPTS=28` 的
拒绝采样找位置。结果必然是均匀分布 + 无团块 + 无疏密梯度。这是「贴纸感」最直接的来源。

### 3.5 层级关系：三层机制叠加

| 机制 | 做法 | 证据 |
|---|---|---|
| 图层栈 | 11 层固定顺序（素材在区块上、地名在素材上） | `CreatreBaseLineLayer` |
| **z 浮点递增** | 新元素 `z = 同组 max(z) + 1`；在组内 `z = max(z) + 1e-4` | `b.z=f+1;` / `b.z=f+1E-4` |
| **按脚底 y 重排** | 生成完一批素材后，按 `y + height*scale`（脚底线）升序**重赋 z** | `p.sort(... p[d].y+p[d].height*p[d].scale > ...)` |
| 分组基线 | 森林用 `GetMinZ`（压到最底）、山脉用 `GetMaxZ` 之上 | `GetMinZ(FeatrueTypeEnum.Point…)` |
| 图层组 | 自动归入「自动生成山脉」「自动生成森林」两个 folder，可整组显隐/移动 | `tree_folders.point.push({name:"自动生成森林"})` |

**按脚底 y 排序**是手绘地图「前后遮挡」的标准做法：南边的灌木盖住北边的山脚。
本项目没有这一步（Pixi 按插入顺序），所以素材之间的遮挡关系是**生成顺序的副产品**，
不是画面逻辑。

### 3.6 底图：程序化 SDF 海岸 + 位图纹理羽化

两个独立机制，都值得注意。

**(a) 海岸形状：SDF + 域扭曲 + 距离衰减细节噪声**（`erodeGeoJSON`，`decoded.js@747732`）

```js
// 参数
{ width:1200, height:800, pad:140, warpAmp:115, noiseScale:0.012, octaves:5,
  detScale:0.085, detAmp:26, detRadius:28, minArea:700, smooth:2, seed:20240607 }

// 流程
1. GeoJSON → 画布栅格化 → 二值掩码
2. 双向距离变换（Felzenszwalb）→ 有符号距离场 SDF
3. 对每个像素：
     fx = x + fbm(x*q, y*q, octaves, seedA) * warpAmp      // 域扭曲
     fy = y + fbm(x*q+31.7, y*q-17.3, octaves, seedB) * warpAmp
     d  = sample(SDF, fx, fy)
     d += fbm(x*detScale, y*detScale, 3, seedC) * detAmp * exp(-d*d/(2*detRadius²))
4. marching squares at iso=0 → 轮廓 → 面积过滤 → 2 次角切平滑
```

关键在**第 3 步的衰减项**：

```
d_final = d_sdf + noise · detAmp · exp(-d² / (2·detRadius²))
```

**离海岸越近（d≈0），细节噪声越强；深入内陆则迅速衰减到 0。**
于是「边缘毛糙、内部干净」——海岸有手绘的碎边，而内陆保持平整，
**素材落上去不会与底图纹理互相干扰**。本项目 `land.ts` 的 `r(θ)=R(0.72+0.28·fbm)`
（单环星形 + 全程同强度噪声）给不出这个层次：后者的噪声是**全域均匀**的，
海岸与内陆一样粗糙，元素与底图在两处都要打架。

> **✅ 已落地（2.34.0）**：`land.ts` 改为 SDF 侵蚀管线，本节算法与参数**逐字照抄**
> （`warpAmp 115 / noiseScale 0.012 / octaves 5 / detScale 0.085 / detAmp 26 /
> detRadius 28 / smooth 2`，其画布 1px ≈ 1 世界单位，可直接 1:1）。
> 工程差异两处：母形用轻微起伏的极坐标环代替 GeoJSON 输入；侵蚀在**每岛局部
> 栅格**上独立进行 + `fitRingToSpan` 按实测半幅贴回格子（结构上保住海峡宽度）。
> 域扭曲按 stride 4 预采样、零线带外像素沿用 φ₀（性能 ≈ 0.1s/岛）。
> 落地明细见 CHANGELOG 2.34.0。

**(b) 地表纹理：`createPattern` 平铺 + 边缘羽化**（`decoded.js@544440`、`@718772`）

```js
// 陆地填纹理
a.CTX.fillStyle = a.CTX.createPattern(landTexture, "repeat");   // 可平铺纹理
a.CTX.globalCompositeOperation = "source-atop";                  // 只在陆地 alpha 内上色
a.CTX.fillRect(...);
const soft = EdgeSoftnessCanvas(a, 40);                          // 边缘羽化 40px
a.CTX.globalAlpha = 0.5; a.CTX.drawImage(soft);

// EdgeSoftnessCanvas(canvas, b) 的实现：多遍 shadowBlur 累积出一个从外向内渐进的软边
c = parseInt(20*b/25);
for (d = 0; d < c; d++) { shadowBlur = b - d; drawImage(反相遮罩); }
canvas.globalCompositeOperation = "destination-out"; drawImage(那个软边);
```

**纹理在陆地边缘向内淡出 40px**，加上外部 250px 宽的软描边（浅海带，见下），
形成「纹理—陆地—浅海—深海」四段连续过渡。本项目 `coastBake` 已有四层海岸带，
但**陆地内部是纯色 + 一张 multiply 纸纹**，没有「纹理随边缘淡出」这一手。

**(c) 浅海带：从位图轮廓重描 250px 软边**（`decoded.js@547757`）

```js
const polyline = getOutlinePolyline(paintLayerImageData);  // 从 alpha 提轮廓
ctx.strokeStyle = 仙侠 ? "#FFF" : "#65a6ba";
ctx.lineWidth = 250;                                       // ← 250px
ctx.stroke();
LineEdgeSoftness(canvas, {shape: polyline}, 250, ...);
shadowLayer.drawImage(canvas) with alpha 0.08（仙侠）/ 0.15
```

**注意**：他们的浅海带是从**位图 alpha** 反提轮廓再描边，不是矢量化几何。
这是位图架构的自然产物，也正是「放大发糊」的根因（见 §7 局限）。

### 3.7 区块（面）的视觉权重

```js
{ shape: removeNearPoint(country.shape[u], 8), color, alpha: 0.3,
  border_size: 3, border_color: "#73562d", border_alpha: 1,
  polygon_type: 6, shadow: 0, inset_shadow: 0, softness: 0 }
```

（`decoded.js@131642`）

有意思的是：**他们的区块填充 `alpha` 比本项目更高（0.3 vs 0.10），但画面并不显色**。
原因不是 alpha，而是**层级与数量**：

- 区块层级只有「国家/州」一级，`countries` 上限 **20 个**（`20<J&&(J=20)`）；
- 本项目是 **160 个郡级区块**，同一屏内颜色数量多了 8 倍。

所以 PRD §4.3 把 `REGION_FILL_ALPHA` 压到 0.10 是**在错误的维度上补偿**：
真正该压的是「同一视口内可辨识的区块数」，而不是透明度（压 alpha 只会让边界也一并变淡）。

## 5. 为什么「参考了架构但效果差很多」

PRD 附录 A 摘的是**图层与滤镜清单**，而真正决定观感的是**布点算法**——那一层没被摘出来。
按贡献排序，四个根因：

### 根因 A ·「位图陆地」vs「矢量陆地」决定了排布问题的形态

- 参考实现：陆地 = 带软边的位图 → 「哪里能放素材」是**像素统计**（格内 alpha 占比）。
  于是海岸留白、纹理羽化、浅海软边、素材避开半透明区，全部是**同一个 alpha 通道的副产品**。
- 本项目：陆地 = 闭合多边形 → 「哪里能放」是**点在多边形内**。
  几何上没有「半透明」这个概念，所以留白、羽化、避让都得**单独实现**，而目前一条都没实现。

> 这不是「他们技术更强」，而是**位图让四件事变成了零成本的副作用**。
> 本项目要在矢量上补齐，需要显式设计「海岸内缩带宽」这个新概念（见 §6 P1）。

### 根因 B · 布点从「撒点」退化为「泊松盘」

`generator.ts` 的 `CORE=0.55` + `PLACE_ATTEMPTS=28` 本质是**带收缩的泊松盘采样**：
均匀、可复现、零重叠（大部分）。这在「不重叠」这个目标上是优解，
但在「手绘感」这个目标上是**反解**——手绘地图的素材本来就大量重叠，且疏密不均。

参考实现从不追求「不重叠」：它先用网格保证**宏观均匀**，再让每格叠 1~3 个、
森林叠 3~7 个，用**受控的重叠**换取「层叠山峦 / 一丛树林」的厚度。

### 根因 C · 素材池的组织维度错了

本项目的分类轴是「**用途**」（mountain / forest / settlement / ruin…），
参考实现的分类轴是「**所处地貌带**」（grass / desert / poles / 主池）。

用途分类回答的是「用户想画什么」，地貌带分类回答的是「**这里应该出现什么画风**」。
自动生成需要的是后者。当前 `terrainMix` 只决定「选哪一类」，不决定「这一类里选哪一族」，
所以同一个 `mountain` 配方在雪原上也会抽到 `mountain-peak`。

### 根因 D · 缺少「位置先验」这一层

参考实现有两处位置先验，本项目一处都没有：

1. **连通性**（邻居数 → 出现概率）：让同类素材成片；
2. **纬度带**（`r < H/4`、`r > 3H/4` → 换素材族）：让地貌随纬度渐变。

两者都不贵（各十几行），但决定「这张图看起来像自然生长出来的，还是一张均匀网格」。

#### 与原建议不同的 6 处

1. **`zones` 是必填的多标签数组**，不是可选单值 `zone?`。一张「松树」同时属于
   主带和雪带，单值表达不了；`SpriteSource.zones` 仍可选（导入素材缺省 `core`），

2. **分带相对「陆地包围盒」而不是纸张**。陆地只占纸面中部 55%~70%，按纸张分带

   两个端点对齐参考实现的 `H/4`、`3H/4`，中间取中点（四带需要三个阈值，
   证据只给了两个，中点属重建）。
3. **回退链改成「本带 → core →（仅当两者皆空）同地形任意带」**。原建议是
   「同带 → 相邻带 → core」；相邻带回退会让沙漠带混进草原圆丘，等于没分带。
   但必须留「两者皆空」这个口子：`desert` 地形在 core 带里没有任何 core 素材
   （沙丘/绿洲全都是 desert 带），不放口子就会整片空掉。**只要本带有货就绝不跨带。**
4. **碰撞改成「同簇豁免、跨簇才比」**。原建议是全局 `CORE=0.35`；可是一个丛簇里

   跨簇仍拦"几乎整个压住"，同簇只拦"同一位置叠画"（锚点最小间距
   `min(w,h)×0.22`）。
5. **铺格顺序打乱后再迭代**（原建议没有这一条）。目标总数是硬上限，按行列顺序
   铺会在到达上限时把**南半边整片截掉**——症状是"北密南秃"且分带统计里沙带恒为 0。

6. **簇内用黄金角螺旋 + 微扰**（原建议是纯随机 ±w/5）。纯随机会把两个实例丢到
   相距 2 单位处 = 同一张贴图叠画；螺旋保证"相邻但不重合"，观感比等距环自然。

| 问题 | 现象 | 机制 |
|---|---|---|
| 配比不生效 | 预设写 `mountain 0.55 / forest 0.30`，实测产出 **83% 的山** | 旧实现把没认领的格全归给主地形，主地形每格又多铺 1 个。改为**配额表**（`budget`）：`expandTerrainMix` 的实例数即各配方的上限，用尽即不再开簇；没被认领的格 `terrain = null`，**就是平原** |
| 素材尺寸与格子脱钩 | 繁密档格子变小、素材不变 → 糊成山墙；稀疏档反之 → 图散 | `sizeScale = cellSize / BASE_CELL`（`BASE_CELL = 92`）。换档只换"精细度"，`素材 : 地块` 恒定 —— 对应参考实现的 `grid > 50 → w += 0.1` |
| 城堡和山一样高 | 城郭贴图 135×130 与山脉 200×127 按同一尺度摆，聚落压过地貌 | `TERRAIN_SCALE`（按**地形配方**归一）：山地 1.0 / 高原 0.95 / 丘陵 0.75 / 森林 0.72 / 聚落 0.52 / 遗迹 0.48。参考实现里城郭只有山峰三分之一，因为它的素材池按用途分组后各自归一 |

**为什么是「地形配方归一」而不是「全池统一长边」**：全池统一会把一棵单树
（42×86）放大到和森林贴片（170×159）一样宽 —— 单树和树林本来就该是两种体量。
真正需要统一的是**同一族内部**（山脉不该一条 200 宽、一条 80 宽），而族内的
差异由 `baseWidth` 的原生比例表达，`TERRAIN_SCALE` 只负责"族与族之间"。

剩下的族内差异靠两处抖动抹平：同簇共享基准（`0.88~1.14`）+ 实例微调
（`0.9~1.1`，从 `0.94~1.06` 放宽 —— 同一张贴图摆两次是最刺眼的重复，
旋转只有几度扛不住这个任务，尺寸错开一成以上才不像复制粘贴）。

#### 二、多片地形：为什么不是一片

单一区域生长会长出**一整块**主地形，读者看到"左边全是山、右边全是林"的两分天下；
参考实现的一张图里有 5~6 条互不相连的山脉，中间夹着平原。现在按配额拆片
（`CELLS_PER_PATCH = 7` / `MAX_PATCHES = 4`），种子点"取随机候选中离已有种子
最远的一个"（16 次采样），片与片之间自然留下平原。

#### 三、背景质感：海从"一块布"变成"一片海"

按视觉权重排序，四件事：

1. **浅滩方向反了**（最严重）。旧 `COAST_SHELF` 是深绿 `0x2f4a3c`，比海**更暗**，
   画出来是陆地外面套一圈暗环 —— 像贴纸阴影。任何地形图的浅滩都比深海亮
   （水浅 → 反射海底 → 明度上升），改成 `0x9dbfae / 0.22 / 宽 20`。
2. **等深线**（新增，性价比最高）。离岸 16 / 40 / 70 世界单位三圈细线，
   `2.2/1.7/1.3` 宽、`0.32/0.20/0.12` 不透明度。实现用"以轮廓中心等比放大"
   代替真正的多边形外扩：陆地是团块状，误差一二十个百分点，但**绝不会自交**
   （真外扩在几百顶点的弯折岸线上极易翻边）。烘焙期一次算完，运行期零成本。
3. **陆岸内阴影**（新增）。`alignment: 1` 的描边只画在路径内侧，模糊 + 陆地遮罩。
   参考实现的陆地不是一块均匀米黄：岸线内侧 10~20px 明显偏深偏暖。
   **遮罩是必须的**：22px 的描边模糊后会洇到海面上，在浅滩里压出一圈脏边，
   与第 1 条直接冲突。
4. **海面暗角**（新增，`MapCanvas.SEA_VIGNETTE`）。14 圈窄环从纸缘向内压暗
   （0.004 → 0.026），四角明显比中心沉。**必须画在海面之上**：`sheet` 在海面
   之下，画在那里会被不透明的海面整块盖掉（症状是"加了暗角但画面一点没变"，
   不报错）—— 已在 `render-stack-guard.test.ts` 的 `STATIC_STACK` 里钉死
   `sheet → sea → seaShade`。

#### 四、纸纹：海是海，纸是纸

旧实现把**底图**（青绿水纹漩涡）当纸纹 multiply 到陆地上：陆地带上青灰旋纹、
整体发暗。新增 `paperGrain.ts` 程序生成中性灰颗粒（三层可平铺值噪声 + 网点，
512²，`PAPER_GRAIN_LUMA = 0.88`，只压暗不提亮），`LAND_TEXTURE_ALPHA` 0.35 → 0.55。

**为什么程序生成而不是再加一张美术资源**：纸纹要求无缝平铺 + 中性灰，AI 生成的
图很难同时满足（颜色会偏）；而它只是噪声，生成 ~5ms，还能按需调尺寸与强度。
纯函数部分（`writePaperGrainPixels`）可单测，`createPaperGrainTexture` 在 jsdom
下返回 `null`（画布退化成纯米黄陆地，不抛）。

#### 五、参数（`generator.ts` / `coastBake.ts` 顶部常量）

| 常量 | 值 | 含义 |
|---|---|---|
| `INSTANCES_PER_CELL` | 3 | 每簇 2~4 个；用来把目标总数反解成格数 |
| `PLAIN_CELL_RATIO` | 0.18 | **平原占比目标**（只用来反解格边长；留白由"配额之外没认领的格"产生，不再随机丢弃） |
| `CELLS_PER_PATCH` / `MAX_PATCHES` | 7 / 4 | 同一地形平均几格另起一片 / 最多几片 |
| `BASE_CELL` | 92 | 标准档格边长基准（素材尺寸补偿的基准） |
| `TERRAIN_SCALE` | 0.48~1.0 | 按地形配方的体量系数 |
| `COAST_ISOBATHS` | 16/40/70 | 等深线离岸距离（世界单位）|
| `LAND_TEXTURE_ALPHA` | 0.55 | 纸纹 multiply 强度 |

实测（`seed = 20260411`，`standard`，真实 52 张池）：

| 预设 | 实例数 | 构成 | 说明 |
|---|---|---|---|
| 十万大山 | 96 | 山 55 / 林 24 / 河 11 / 遗迹 6 | 目标 120 是上限：跨簇防呆 + 岸线回退吃掉缺口 |
| 南疆沼泽 | — | 沼泽 / 丛林 / 河流 / 聚落 | 沼泽档可用 **7 种**（按 `terrains` 计：`swamp` 4 张全在 `core` 带 + `jungle` 3 张里 2 张 `core`、1 张 `grass`）。**7 张里 6 张靠跨带借用 `core`**，重复感最强（§7 L-7） |
| 万里雪原 | — | 雪峰 / 雪松 / 雪丘 | 雪带可用 **7 种**（按 `zones` 含 `snow` 计）：3 张雪峰 + 雪松 + 雪丘 + 松树 + 碎石荒地 —— 后两张是跨带借用，真正的"雪题材"只有 5 张。原写"只有 2 张"是错的，见 §9.5 |

> 对照：`十万大山` 可用 23 种、`mountain` 单类就有 16 张 —— 沼泽/雪原的重复感
> 来自**池子小一个量级**，不是算法差别。
>
> **两档的"7"不是同一个口径**：沼泽按 `terrains` 字段数，雪原按 `zones` 字段数。
> 引用时请带上口径，否则会像前一轮那样出现"雪原只有 2 张"这种数错的结论。
> 两个口径都能用 `pnpm count:sprites` 直接打出来。

## 7. 局限与未知（必读）

| # | 项 | 说明 |
|---|---|---|
| L-1 | **未做运行时捕获** | 全部结论来自静态代码。没有在浏览器里实测「格子数、实例数、实际渲染顺序」，数值链路是读代码推的。 |
| L-2 | **尺寸公式方向为推断** | `scale = (w + D) / Ma`，其中 `Ma = oa/36`。`oa` 的取值（格网尺寸 / 画布宽）在压缩代码里无法静态确定，因此「格越大 → 素材越大」这一条是**基于 `grid>50 → w+=0.1` 与美术直觉的推断**，不是证实。 |
| L-3 | **函数名被压缩** | `a()` / `b()` / `l()` 之类是局部闭包，语义靠调用上下文与参数量级反推；`w` 一度被我误读为「概率」，实为「基准尺度」。 |
| L-4 | **`erodeGeoJSON` 的 `detAmp/detRadius` 单位** | 参数在 1200×800 的中间坐标系里，换算到世界单位需要知道 `pad`/`fit` 的完整链路，本次未展开。 |
| L-5 | **站点可能改版** | 素材清单与锚点（`MapStyleEnum.MOHUAN?(I.src=`）随时可能变化；脚本失败时的报错会指出是哪一步。 |
| L-6 | **未评估其性能代价** | 位图架构在缩放到 2 倍以上会明显发糊（本项目 PRD §2.2 已认领这点优势）。抄机制可以，**不要抄位图架构**。 |
| L-7 | **地貌带素材池不均衡**（实测） | 总计 52 张：`mountain 16 / grassland 9 / snowfield 6 / desert 6 / forest 6 / swamp 4 / tundra 4 / lake 4 / river 4 / jungle 3 / oasis 1`。按 `zones` 汇总 `core 33 / grass 7 / desert 7 / snow 7` —— 沼泽档与雪原档只有 7 种可用素材，同屏重复不可避免。**这属于素材规模问题，不是布点算法能解决的**，扩池前不建议再调生成参数。 |

> 2. `Container._updateIsSimple()`：`isSimple = !renderGroup && effects.length === 0`

> 3. `collectRenderables` 于是走 `collectRenderablesWithEffects`，而
>    `StencilMaskPipe.push` 里正是直接调 `maskContainer.collectRenderables(...)`
>    ⇒ 遮罩几何被 `FilterEffect` 渲进**临时纹理**（此时 `colorMask` 仍为 0），
>    **主目标 stencil 恒空 → `MASK_ACTIVE` 区域为空 → 纸纹整块消失**，且不报错。

> `i × FEATHER/STEPS` 的陆地填充，各自 `alpha = LAND_TEXTURE_ALPHA / STEPS`。
> 全部走"普通 stencil 遮罩 + multiply 精灵"这条已验证路径，无 filters、无 RT、无对齐风险。

> 也就是说相邻两级本来就在"此消彼长"地过渡。
>
> 若再乘一次到填充上：视口停在某一级时该级权重≈1、相邻级≈1，而更深层≈0 —— 填充 alpha 会变成
> **双重衰减**，当前活跃层级反而被压淡，"线比面还淡"照样出现，只是换了个方向。
>
> **正确做法**：这里要的是"越深的层级，区块底色越淡"这种**与视口无关的静态层次感**，
> 必须引入一个**新的常量表**（例如 `REGION_LEVEL_FILL_SCALE`，按 `level` 索引，
> 不参与帽函数归一），与 `levelAlphas` 正交：`填充alpha = REGION_FILL_ALPHA × 静态层次系数`，
> 再交给容器 alpha 去做 LOD 过渡。验收标准也要改写成"同一视口下、各级静态系数按 level 单调递减"，
> 而不是"某组 `levelAlphas` 下的绝对值"。
>
> 在这一点写清楚之前，本条目**不应开工**——否则实现出来的东西会因为两次乘法而"看起来更淡但更脏"。

### 9.4 不要做的事（负向约束，比待办更重要）

1. **不要抄位图的陆地架构**（§7 L-6）。抄机制可以，位图陆地会让 2 倍以上缩放发糊 ——
   本项目 PRD §2.2 已认领矢量陆地的优势。
2. **不要动 `lod.ts` / `coords.ts` / 场景图 7 层结构**。PRD 已认领这三处优于参考实现。
3. **不要在渲染期加滤镜**。海岸全部在烘焙期烤进一张纹理（`bakeCoast`），运行期零滤镜 ——
   这是当前性能的基本盘，加一层实时滤镜会把「缩放流畅」这个优势吐回去。
4. **不要把 `PLAIN_CELL_RATIO` 当"随机留白"用**。它是**反解格边长的目标值**；
   真正的留白来自"配额之外没认领的格"。按旧语义随机丢弃格，会重现"北密南秃"。
5. **不要用全局 `REGION_FILL_ALPHA` 调区块观感**。那条路 2.27.0 已走到 0.10 的尽头，
   再往下压会让边界线孤零零浮在纸上；层次感的正确入口是**静态系数表**
   `REGION_LEVEL_FILL_SCALE`（2.36.0 已落地，按 level 索引、与视口无关）——
   **不是 `levelAlphas`**（LOD 权重，乘上去双重衰减，见 §9.5 勘误）。
6. **不要为"重复率"再调生成算法**。算法已到边界，剩下的是素材数量（`P1-5`）与翻转（序 4）。
7. **改公共原语前先数使用点**（`AGENTS.md`）：`MapCanvas` 的节点装配被
   `render-stack-guard.test.ts` / `bake.test.tsx` / `coastBake.test.ts` 三处钉着，
   改装配顺序会同时炸三个文件 —— 这是设计如此，不是测试太严。
8. **不要 `destroy` 自造的静态纹理**。纸纹 `getPaperGrainTexture()` 是**模块级单例、
   永不销毁**：`Texture.destroy(true)` 会把 `_source` 置 `null`，而 `MapWindow/main.tsx`
   开着 `StrictMode`，「挂载 → cleanup → 再挂载」里 `useMemo` **不会重算** ——
   第二轮拿同一张已销毁的纹理去烘焙，batcher 读 `_source.alphaMode` 抛 null，
   **整个画布白屏**，而报错看起来与纹理毫无关系。守卫在
   `render-stack-guard.test.ts` 的「纹理归属」组。
9. **不要给 `Graphics` 遮罩挂 `filters`（想加软边也不行）**。pixi 8.22 里
   `StencilMask.test = mask instanceof Container`、`AlphaMask.test = mask instanceof Sprite`
   —— Graphics 遮罩只能走 stencil（0/1，无 alpha）；而 `Container._updateIsSimple()` 是
   `isSimple = !renderGroup && effects.length === 0`，挂上 `BlurFilter` 就让 `isSimple = false`，
   `StencilMaskPipe.push` 里的 `maskContainer.collectRenderables(...)` 转而走
   `collectRenderablesWithEffects`，遮罩几何被渲进**临时纹理**、主目标 stencil 恒空
   ⇒ **被遮罩的内容整块消失，且不报错**。要软边只有两条路：换 `Sprite` 作遮罩（AlphaMask，
   需自己烘遮罩 RT 并对齐世界变换），或者**用多层内缩 + 逐层降 alpha 模拟**（`LAND_TEXTURE_STEPS` 的做法）。
   守卫：`coastBake.test.ts` 断言 `layerMask.filters` 长度为 0。
