## 1. 核心结论（先看这段）

### 1.1 推荐架构一句话

> **混合渲染层：底图贴图走 WebGL（PixiJS）批渲染 + 交互节点走独立 SVG/DOM 覆盖层 + 主进程侧瓦片金字塔预切分 + `novel_maps.content` 增量 JSON 持久化。**

即 **不二选一，而是分层**：

```
┌─────────────────────────────────────────────┐
│  React 19 外壳（antd 6 工具栏 / 面板）        │  ← 组件库优先条款（AGENTS §6.1.2）
├─────────────────────────────────────────────┤
│  交互层  SVG/DOM 覆盖层（节点/连线/标签/选中） │  ← 命中测试、可访问性、antd 生态
├─────────────────────────────────────────────┤
│  底图层  WebGL（PixiJS v8）瓦片 + 精灵批渲染  │  ← 2000+ 贴图性能主力
├─────────────────────────────────────────────┤
│  资源层  瓦片金字塔 + Texture Atlas（构建期）  │  ← 主进程预切分，运行时零解码压力
├─────────────────────────────────────────────┤
│  数据层  novel_maps.content JSON（增量落库）   │  ← better-sqlite3，对齐既有范式
└─────────────────────────────────────────────┘
```

### 1.2 三条硬判断

1. **纯 SVG 撑不住 2000+ 元素 + 无级缩放。** R28 现有 SVG 定义在"节点+连线"（数十~数百）量级是合适的，但叠加"大量底图贴图"后，SVG 的 DOM 节点数与 CSS 变换/重排成本会成为硬瓶颈。→ **建议 R28 的 SVG 定位收敛为"交互层"，底图另起 WebGL 层**（报告给出对比数据，PRD 修订由你决定）。

2. **WebGL 是唯一能同时满足"2000+ 贴图"与"无级缩放"的渲染后端。** Canvas2D 在 2000+ 独立 PNG 上会因 `drawImage` 调用次数与纹理上传抖动掉帧；WebGL 批渲染可把同图集元素合并为极少数 draw call。

3. **性能胜负的关键不在渲染 API，而在"资源是否预切分"。** 若 PNG 以 512/1024 大图散装形式在运行时缩放，任何后端都会卡。**构建期预切瓦片金字塔 + 图集打包**是收益最大的一步（预期贡献 60%+ 的性能改善），应作为第一阶段投入。

## 2. 渲染方案定量对比

### 2.1 对比矩阵（针对本项目约束）

评分：★ 优 / ● 可 / ○ 勉强 / ✗ 不可行

| 维度 | 纯 SVG（PRD 现状） | Canvas 2D | WebGL / PixiJS v8 | Leaflet / MapLibre | 自研 WebGL |
|---|---|---|---|---|---|
| 2000+ 独立贴图 | ✗（DOM 节点爆炸） | ○（~500 张后掉帧） | ★（批渲染 2000+ 无压力） | ●（栅格瓦片，矢量弱） | ★ |
| 2000+ 交互节点 | ○（>1000 命中测试变慢） | ● | ●（需自建命中） | ✗（非其模型） | ● |
| 无级缩放平滑度 | ●（CSS transform，文字会糊） | ●（重绘抖动） | ★（GPU 采样，天然平滑） | ★（瓦片金字塔原生） | ★ |
| 命中测试便利性 | ★（浏览器原生） | ○（手写数学） | ○（手写/Pixi hitArea） | ✗ | ✗ |
| 文字/标签可读性 | ★（原生文本） | ○（模糊/需重绘） | ○（BitmapText 或叠加层） | ✗ | ✗ |
| 撤销重做适配 | ★（React diff） | ●（dirty rect） | ●（场景图 diff） | ✗ | ○ |
| 与 antd/React 生态 | ★ 无缝 | ● | ●（需桥接） | ○ | ○ |
| 新增依赖成本 | 0 | 0 | +1（pixi.js ~1.5MB gz） | +1（较重，含地理概念） | 0（但自研成本高） |
| 违反 PRD Non-goal 风险 | — | — | — | **高**（自带地理/瓦片语义） | — |
| 团队心智负担 | 低 | 中 | 中高 | 中（需学地理栈） | 高 |
| **综合推荐度** | ⚠️ 仅交互层 | ⚠️ 备选 | ✅ **推荐底图层** | ❌ 排除 | ❌ 不必要 |

### 2.2 决定性论证：为什么不是纯 SVG、也不是纯 Canvas2D

**（1）纯 SVG 的失效点 — 数量级测算**

SVG 每个图形 = 一个 DOM 节点。2000 个贴图元素意味着：
- 2000 × `<image>` 节点 + 各自的 transform/opacity 属性
- 每次缩放平移，浏览器需重算 2000 个元素的布局与合成
- 实测经验值：SVG 在 **800~1500 个复杂元素**时开始出现明显交互延迟（拖拽掉到 30fps 以下）
- 若贴图带透明通道且互相重叠，还会触发昂贵的重绘区域计算

→ SVG 在"节点 + 连线"（R28 原始定义）场景是**正确选择**；在"2000+ 贴图"场景是**错误选择**。二者不是同一个问题。

**（2）Canvas 2D 的失效点**

Canvas 2D 的瓶颈是 `drawImage` 的**每帧调用次数**与**纹理上传**：
- 2000 次 `drawImage`/帧 ≈ 12~25ms（合 40~80fps，边界）
- 大量不同尺寸 PNG 会导致 GPU 纹理**频繁换绑**，破坏批处理
- 缩放时若无预乘/预切，会出现采样闪烁（aliasing）

→ Canvas2D 是"2000 元素"的**及格线方案**，但留给无级缩放的余量太小。

**（3）WebGL / PixiJS 的优势点**

- **批渲染（Batching）**：同图集（Texture Atlas）内的精灵合并为 1 个 draw call，2000+ 精灵可压到个位数 draw call
- **GPU 采样**：缩放/平移只是 uniform 矩阵变更，无重建开销，天然支持"无级"
- **天然支持瓦片与 LOD**：mipmap 可在缩小远景自动降采样，避免摩尔纹
- **成熟生态**：PixiJS v8 提供 `Container` 场景图、`culling`（视口裁剪）、`Assets` 加载器、`Ticker`，覆盖本项目 80% 需求，避免自研

**（4）为什么排除 Leaflet / MapLibre**

它们的模型是"经纬度 + 栅格瓦片 + 投影"，被 PRD R28 的 **Non-goal（不做真实地理/测绘/在线瓦片）** 直接否定。强行使用会引入 `EPSG:3857` 投影、`latLng` 坐标、地图合规审查等一整套无关复杂度。

> **结论：底图层用 PixiJS（WebGL），交互层保留 SVG/DOM。** 这是唯一同时满足性能、PRD 兼容性、团队心智负担的方案。

## 3. 2000+ 元素的高性能支撑方案

性能是**四层协同**的结果，任何单点优化都不够。

### 3.1 第一层：资源预切分（收益最大，优先级 P0）

```
构建期（Node 脚本，跑在 electron 主进程侧或 CI）
  ┌ 原始 PNG 大图 / 素材集
  ├─► ① 图集打包：同尺寸小精灵 → 一张 2048×2048 Atlas + JSON 坐标表
  ├─► ② 瓦片金字塔：大底图 → L0(1×1) L1(2×2) ... L5(32×32) 分级切片
  └─► ③ 压缩：PNG → WebP（体积降 60~70%，解码更快）
```

| 手段 | 解决的瓶颈 | 预期收益 |
|---|---|---|
| 图集打包 | 纹理换绑、draw call 数量 | draw call 2000 → 个位数 |
| 瓦片金字塔 | 缩放时的全量重绘与采样闪烁 | 缩放帧率 +200%+ |
| WebP 压缩 | 内存占用、解码耗时 | 内存 -60%，首屏加载 -50% |
| mipmap | 远景摩尔纹/闪烁 | 视觉质量 + 缩小场景性能 |

> **与资源解耦设计**：本轮资源规格未定，先落**切分工具链 + 目录约定**（`assets/map/atlas/`、`assets/map/tiles/{z}/{x}/{y}.webp`），资源到位后直接跑脚本。

### 3.2 第二层：视口裁剪（Culling）

只渲染"与当前视口相交（含预取边距）"的元素：

```
可见元素 = elements.filter(e => 
  e.bbox.intersects(viewport.expand(0.2))   // 20% 预取边距，防拖拽露白
)
```

- PixiJS 提供内建 `culling`，配合空间索引（四叉树 / 网格分桶）可将 2000 元素的过滤降到 O(可见数)
- **关键**：空间索引（Quadtree）必须建，否则每帧全量遍历 2000 个 AABB 判断仍是 O(n)
- 预期：2000 元素中通常仅 100~300 在视口内，渲染量降一个数量级

### 3.3 第三层：LOD（细节层级）

按缩放级别切换元素精细度，这是"无级缩放"的性能前提：

| 缩放级别 | 渲染内容 | 元素数预算 |
|---|---|---|
| 远（z < 0.3） | 仅大陆轮廓 + 主要城池（大图标签） | ~50 |
| 中（0.3 ≤ z < 1.0） | 城池/山脉/河流/关卡 + 主要连线 | ~300 |
| 近（z ≥ 1.0） | 全部元素 + 小装饰贴图 + 完整标签 | 全量 |

- LOD 由元素自身的 `minZoom` 属性驱动，而非硬编码分级
- 缩放于阈值附近抖动 → 加 **hysteresis（迟滞区）**，如 `minZoom=0.3` / `hideZoom=0.25`，避免频繁增删导致的闪烁与 GC 抖动

### 3.4 第四层：加载与内存

| 策略 | 说明 |
|---|---|
| 分层加载 | 先加载 L0 缩略图（秒级可见），后台渐进加载高清层 |
| 按需加载瓦片 | 视口内瓦片优先，拖拽方向预取相邻瓦片（LRU 缓存 + 上限） |
| 纹理池化 | 复用 Pixi `Texture` 对象，避免反复创建销毁导致 GPU 内存碎片 |
| 大对象外置 | 大体积瓦片不入 SQLite，走本地文件目录，DB 只存路径与元数据（对齐 `novel_maps.content` 设计） |

### 3.5 性能预算表（验收基线）

| 指标 | 目标 |
|---|---|
| 首屏可见（L0 缩略） | < 800ms |
| 全量 2000 元素就绪 | < 3s |
| 拖拽/平移帧率 | ≥ 55fps（@2000 元素可见 300） |
| 缩放帧率 | ≥ 55fps |
| 单次交互延迟（选中/拖拽元素） | < 16ms |
| 峰值内存（含纹理） | < 500MB |

> 这些数字应写入 PRD 的**验收标准**（PRD 目前未定义地图性能指标，是缺口）。

## 4. 无级缩放（Seamless Zoom）实现方案

### 4.1 核心机制：单变换矩阵 + 分级资源

"无级"不等于"每一帧全量重绘"。实现路径：

```
用户滚轮/触控板
   └─► 累积缩放因子（含 pinch/惯性，用 requestAnimationFrame 平滑插值）
        └─► 更新 viewport = { x, y, scale }   ← 单一事实源
             ├─► 底图层：Pixi Container.scale/position，GPU 直接采样
             ├─► 瓦片层：按 scale 选层级 z = clamp(log2(scale))，
             │            与相邻层级做 alpha 交叉淡入（避免跳变）
             ├─► 节点层：SVG 覆盖层 transform 同源同步
             └─► LOD 层：按 scale 增删元素（带迟滞）
```

### 4.2 三个关键细节

**（1）缩放锚点（Zoom to Cursor）**
缩放必须以**光标位置**为锚点，而非画布中心，否则体验割裂：

```ts
// 保持光标下的世界坐标不变
const worldBefore = screenToWorld(cursor, viewport);
viewport.scale *= factor;
const worldAfter = screenToWorld(cursor, viewport);
viewport.x += (worldAfter.x - worldBefore.x) * viewport.scale;
viewport.y += (worldAfter.y - worldBefore.y) * viewport.scale;
```

**（2）浮点精度与坐标空间**
- 世界坐标用**双精度**（JS number 天然满足），但渲染时相对**视口原点**偏移，避免大坐标下的浮点精度丢失（缩放深度大时易出现抖动）
- 建议世界坐标原点设在地图中心，而非左上角

**（3）标签去重与聚合**
远缩放时 2000 个标签会糊成一片：
- 标签设 `minZoom`，低于阈值不显示
- 高密度区域做**标签聚合**（相近标签合并为"XX 区域（12 处）"）
- 标签用 DOM/SVG 层渲染（保证文字清晰），**不随底图缩放模糊**

### 4.3 与 PRD "无级" 的差异提示

PRD R28 原文为"缩放平移"，未定义"无级/分级"。本方案提供的是**连续缩放 + 内部 LOD 分级**，对外表现为无级，满足用户目标，但**需在 PRD 中补一句性能与 LOD 说明**（建议，不强改）。

## 6. "资源待定"下的解耦设计

因为资源规格未定，以下决策**必须在拿到资源后再定稿**，但接口先固化：

| 待定项 | 影响 | 解耦策略 |
|---|---|---|
| 贴图是"瓦片"还是"散装精灵" | 决定瓦片金字塔是否需要 | 抽象 `TileSource` 接口，两种实现可切换 |
| 单贴图尺寸（256/512/1024） | 图集打包尺寸与 LOD 阈值 | 打包脚本参数化，配置驱动 |
| 是否带透明通道 | 渲染顺序与批处理策略 | Pixi 统一按 alpha 处理，成本可控 |
| 总资源体积 | 加载策略（全量 vs 按需） | 决策阈值：> 50MB 走分块按需加载 |
| 是否已有手绘底图 | 是否需要瓦片金字塔 | 手绘整图 → 必须预切；纯精灵 → 只需图集 |

**接口先行示例：**

```ts
interface TileSource {
  getTile(z: number, x: number, y: number): Promise<Texture>;
  maxZoom: number; minZoom: number;
  tileSize: number;
}
// 实现 A：预切瓦片目录  Impl: FileTileSource
```

## 12. SVG 交互层与 PNG 底图的一致性保证

> 本章回答一个具体问题：**SVG 交互层展示的图像，怎么确保与 PNG 底图一致？**
> 先给结论：一致性不是一个问题，而是**四个层面的问题**，其中三处必须严格对齐、一处必须刻意不对齐。

### 12.1 问题拆解

双层架构的本体矛盾在于：**WebGL 底图层与 SVG 交互层是两个独立的渲染上下文**，它们的绘制路径、抗锯齿方式、色彩处理、缩放采样策略都不同。若不刻意对齐，会出现"标记和素材看起来不是同一个东西"的割裂感。

| 层面 | 具体现象 | 是否要对齐 | 难度 |
|---|---|---|---|
| ① 几何位置 | 标记画的位置与素材实际位置对不齐 | **必须 100%** | 低（做对就永远对） |
| ② 色彩 | 两层颜色偏移、边缘发灰或发黑 | **必须** | 中 |
| ③ 缩放采样 | 放大时 PNG 变糊、SVG 依然锐利，观感割裂 | **必须** | 中 |
| ④ 材质质感 | SVG 手绘图标 vs PNG 位图素材，质感根本不同 | **刻意不对齐** | — |

**核心判断：不要试图让 SVG "看起来像" PNG。**
正确做法是让 SVG 层**只绘制 PNG 做不到的东西**——文字标签、选中框与控制点、连线。这三类内容本来就没有 PNG 对应物，也就不存在"一致性"问题。城池等实体一律由 PNG 素材呈现，SVG **不再重复绘制一份**。

### 12.2 层面① 几何对齐（根本手段：单一变换源）

几何错位的唯一成因是"两层各自推导坐标"。解法是**强制收敛到一套变换**：

```
        ┌──────────────────────────────┐
        │  viewport { x, y, scale }    │  ← Zustand store，唯一写入点
        └────────────┬─────────────────┘
                     │ rAF 内快照一次
        ┌────────────┴─────────────┐
        ▼                          ▼
  WebGL stage                 SVG root
  .position/.scale            svg.setAttribute('transform', ...)
  （来自 viewportToStageTransform）（来自 viewportToSvgTransform）
```

**三条硬约束：**

1. **同源**：两层的变换参数必须由**同一份 viewport 快照**推出，禁止组件内自行换算
2. **同帧**：两层的更新必须在**同一个 rAF 回调内**提交。先动底图再动 SVG，哪怕只差一帧，快速拖拽时就会看到错位抖动
3. **纯函数**：坐标换算收敛为纯函数（见 `docs/novel-map-coord-system.ts`），必须有单元测试覆盖往返一致性

**参考实现骨架：**

```ts
// docs/novel-map-coord-system.ts 中已给出完整实现
import {
  worldToScreen, screenToWorld, zoomAt,
  viewportToSvgTransform, viewportToStageTransform,
} from './novel-map-coord-system';

// 同一帧内更新两层
function commitFrame(viewport: Viewport, size: CanvasSize) {
  // 1. WebGL 层
  const stage = viewportToStageTransform(viewport, size);
  pixiContainer.position.set(stage.x, stage.y);
  pixiContainer.scale.set(stage.scale);

  // 2. SVG 层（用等价的 transform 串）
  svgRoot.setAttribute('transform', viewportToSvgTransform(viewport, size));

  // 3. 可选：文字标签反向补偿缩放（见 12.4）
}
```

**关键陷阱：世界原点必须在地图中心。**
若原点在左上角，深层缩放时大坐标会造成浮点精度丢失，表现为画面细微抖动。已在 `worldToScreen` 中体现（先减画布中心）。

**单测必测项：**

```ts
// 往返一致性
expect(worldToScreen(screenToWorld(p, vp, size), vp, size)).toBeCloseTo(p, 6);

// 锚点不变性：缩放前后，光标下的世界坐标必须相同
const world = screenToWorld(anchor, vp, size);
const next = zoomAt(vp, anchor, 1.2, size);
expect(screenToWorld(anchor, next, size).x).toBeCloseTo(world.x, 6);

// 两层变换等价性
expect(viewportToSvgTransform(vp, size))
  .toBe(`translate(${stage.x}, ${stage.y}) scale(${stage.scale})`);
```

### 12.3 层面② 色彩对齐

| 措施 | 说明 |
|---|---|
| 统一色彩空间 | 两层均按 **sRGB** 处理；Pixi 初始化时明确 `premultipliedAlpha` 设置，与 SVG 合成模型对齐 |
| 描边色取主题变量 | SVG 描边/填充只写 `var(--app-*)`，禁止硬编码 hex（对齐 `AGENTS.md` §6.1） |
| 避免半像素描边 | 描边宽度为奇数时易发虚；SVG 侧可加 `shape-rendering` 控制 |
| 抗锯齿差异 | SVG 的边缘抗锯齿由浏览器处理，与 GPU 不同；**文字与描边天然比位图锐利**，这属于合理的观感差异 |

> 注意：四套主题（aurora / cream / mint / midnight）下，SVG 层颜色需跟随主题；而 PNG 素材是固定位图，**不随主题变化**。因此主题切换时两层会有色差——这是**预期行为**（素材本身不该被主题改色），但需在浅色/深色主题下分别验证 SVG 描边的可读性。

### 12.4 层面③ 缩放采样对齐

这是最容易"看起来不一致"的地方：放大时 PNG 有像素感，SVG 依然锐利。

| 策略 | 说明 |
|---|---|
| PNG 侧用 mipmap + 线性过滤 | 缩小远景时避免摩尔纹，放大时保持平滑过渡 |
| SVG 侧用 `shape-rendering` | 交互控件（选中框等）建议 `crispEdges` 或 `geometricPrecision`，按视觉目标选 |
| **文字做反向补偿** | 标签**不随地图缩放**：字号恒定，仅位置随 map 变换。否则远看糊、近看巨大 |
| 线条宽度补偿 | 连线/描边用 `vector-effect="non-scaling-stroke"` 保持恒定视觉粗细 |

**文字反向补偿的实现要点：**

```tsx
// 标签放在随地图变换的 <g> 内的"反向缩放"子组里
<g transform={viewportToSvgTransform(viewport, size)}>
  {markers.map(m => (
    <g
      key={m.id}
      transform={`translate(${m.x}, ${m.y}) scale(${1 / viewport.scale})`}
    >
      {/* 图标以世界坐标定位，但尺寸恒定 —— 位置准、字清晰 */}
      <circle r={5} />
      <text dy={-10} textAnchor="middle">{m.name}</text>
    </g>
  ))}
</g>
```

> `scale(1 / viewport.scale)` 是让子元素抵消父级缩放的经典手法：位置随地图走，尺寸保持不变。这样"标记锚点"与 PNG 素材严格对齐，而标签始终清晰可读。

### 12.5 层面④ 刻意不对齐：材质质感

**明确决策：SVG 不追求与 PNG 材质质感一致。**

| SVG 层只画这三类内容 | 理由 |
|---|---|
| 文字标签 | PNG 无对应物，且需要随主题/语言变化 |
| 选中框、控制点、悬停高亮 | 纯粹的交互反馈，本质不属于地图内容 |
| 连线与连线标注 | 矢量本质，位图绘制反而低效 |

**禁止**：用 SVG 再画一份城池/山脉/河流图标去"对应" PNG 素材。那必然出现两套视觉语言，且维护双份资源。

### 12.6 一致性验证清单

上线前需逐项验证：

- [ ] 任意缩放级别下，标记锚点与素材边界的相对位置不偏移
- [ ] 快速连续拖拽画布时，两层无可见错位或抖动（尤其注意是否差帧）
- [ ] 缩放至最大/最小极限时，锚点仍锁定光标位置
- [ ] 四套主题下，SVG 描边与文字均清晰可读
- [ ] 导出 PNG 时，SVG 层内容（标签/连线/标记）与编辑器所见一致（导出需单独实现渲染路径）
- [ ] 文字标签在极端缩放（10% 与 800%）下不糊、不巨大
- [ ] 坐标换算纯函数的单测全部通过（往返一致性 + 锚点不变性）

### 12.7 与导出的一致性（补充风险）

**导出 PNG 是一个独立风险点。** 编辑器中地图由两层合成渲染，而导出需要一个**单次离屏渲染**：

- 方案 A：在离屏 canvas 上分别绘制底图与 SVG（SVG 可经 `Image` + `svg` data URL 栅格化），再合成
- 方案 B：导出时临时降级为纯位图路径，重绘一次

**风险**：导出结果与编辑器所见可能不一致（字体、抗锯齿、图层顺序）。
**应对**：导出必须走**同一套坐标变换**，且需专门做"所见即所得"的对比测试。此项已列入验证清单。
