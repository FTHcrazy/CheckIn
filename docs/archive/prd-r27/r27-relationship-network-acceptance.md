### 2.5 L4 性能基准层 → **不进 CI**，项目外脚本 + 手工记录

不进 CI 的四条硬理由：

1. **浏览器驱动没被声明**。`package.json` 的 deps/devDeps 里没有 playwright/puppeteer；但 `node_modules/` 下**实际存在** `playwright` + `playwright-core`（由 `@vitest/browser-playwright` 的可选依赖链带入，见 `pnpm-lock.yaml:3402`）。所以脚本**在本机能跑**（架构师已在用），却**不能当门禁**：换台机器 `pnpm install` 不保证装上，CI 上 `--frozen-lockfile` 也可能直接失败。要把它变成门禁就得显式声明依赖 = 破"零新增依赖"。
2. jsdom 无渲染管线：`requestAnimationFrame` 回调的间隔是定时器近似值，测出来的是"调度延迟"不是"绘制成本"。
3. 帧耗时对机器负载极敏感；本项目 CI 与开发机不同机，`p95` 会假红，久了就被 `skip`——比没有更差。
4. 架构师已在 `C:/Users/A/AppData/Local/Temp/r27-spike/` 建成可复现脚本（`force-bench.mjs` / `run-bench.mjs` + `render-bench.html` / `run-export*.mjs`）。**QA 不重写脚本**，只负责口径、阈值与结果归档。

> 这三层（单测 / 组件 / 源码守卫）进 CI，性能基准不进 CI —— 所以 §1 的"可自动化 93"只统计前两层 + 守卫层，脚本 16 条单列。**不要把脚本结果写进 `pnpm test`**，否则某天它会因为一台更慢的机器变红，然后被人加 `skip`，最后没人看。

设备与复跑口径见 §5.4。基准结果以表格形式回填到本文件附录 B（每次实现大改后追加一行，保留历史）。

## 5. 性能基准方案

### 5.1 每个基准项的构造与测量口径

| 基准 | 构造方法 | 起 → 止（口径） | 工具 | 样本量 | 阈值 | 失败时怎么定位 |
|---|---|---|---|---|---|---|
| `firstPaintMs` | 合成 200/500 图，进入浮层 | 入口 `onClick`（`performance.mark("rg:click")`）→ 预热 60 tick 后**首个 rAF 回调内**（`mark("rg:first")`） | `performance.mark/measure` | 每次会话 5 次，取**中位数** | `< 100ms` | 大于阈值时看两段拆分：`deriveMs`（派生）与 `prewarmMs`（60 tick）。前者大 → 派生层有 O(n²)；后者大 → 预热 tick 数未按规模降档 |
| `settleMs` | 同上，跑到主动停止 | `rg:click` → `cancelAnimationFrame` 那一帧（`mark("rg:settle")`） | 同上 | 5 次取中位 | `< 2000ms` | 看 `stopReason`：恒为 `maxTicks` 说明 alpha 衰减太慢（应降到 `alpha`）；`settleMs` 长但帧耗时正常 = 纯 tick 数多 → 调 `tickPerFrame` 2→3 |
| 帧 p95（`sim+render`） | 200 帧滚动/拖拽 | 每帧 `t0=performance.now()` → `sim(1tick)` → `render()` → `t1`，取 200 个 `(t1-t0)` 的 p95 | `performance.now()` 包住（与尖刺脚本同口径） | 200 帧，丢弃前 20 帧 warmup | `≤ 8ms` | **拆分 `simMs` / `renderMs`**（见 §5.2） |
| 降级档边界 | 8 个规模各跑 200 帧 | 同上 + `PerformanceObserver({type:"longtask"})` | 同上 + PO | 200 帧 × 8 档 | `p95 ≤ 8ms` 且 `longtask === 0` | 逐档看拐点：若 401 档突增 → 标签绘制回退（应只剩色点）；若 801 档突增 → 布局 O(n²) 主导 |
| 派生耗时 | 200/500 | `buildRelationGraph` 前后 | `performance.now()` | 50 次取 p95 | `< 5ms` | 超时八成是用了 `Array.find` 在 O(n²)；应改 Map 索引 |
| 边命中扫描 | 500 边 | 1000 次点线距离全扫，取均值 | `performance.now()` | 1000 次 | `< 1ms` | 超时说明加了空间索引反而更慢（预研已证 ≤800 节点索引是负收益） |
| 拖拽帧 | 200/500，指针拖动 2s | 拖拽期间 120 帧 | 同帧 p95 | 120 帧 | `p95 ≤ 8ms` | 掉帧先查是否在 `pointermove` 里 `setState`（`RG-G-01` 的同类问题） |
| 记忆体积 | 200 节点 | `new Blob([JSON.stringify(mem)]).size` | Node `Buffer.byteLength` | 1 次 | `< 8KB` | 超了看是否存了 `seed`/`name` 等冗余字段（只应存 `[x,y,f]`） |
| 预热段耗时 | 200/500 | 60 tick 累计 | `performance.now()` | 10 次取 p95 | `< 8ms` | 超了按 §5.2 降到 30 tick |

### 5.2 如何区分「布局慢」与「渲染慢」（失败定位的硬要求）

同一帧内打四个 mark，脚本输出四列而不是一列总和：

```
rg:f0  → sim 开始
rg:f1  → sim 结束          差值 = simMs   （纯布局，force-sim）
rg:f2  → 写 transform 结束   差值 = domMs   （节点层，DOM 写）
rg:f3  → canvas 重绘结束     差值 = canvasMs（边层，stroke）
```

判定表：

| 现象 | 结论 | 收口点 |
|---|---|---|
| `simMs` 占 >70% | **布局慢** | `force-sim.ts`：斥力求和、tick 数、是否误用 O(n²) 索引 |
| `domMs` 占 >50% | 节点层慢（节点数 × transform 写） | 是否每帧重写全部节点（应只写变化的）；是否在布局帧触发 React render |
| `canvasMs` 占 >50% | 边层慢 | 是否每条边单独 `beginPath+stroke`（应一次批处理）；是否每帧重建渐变 |
| 三项都正常但 p95 超线 | 被外部争抢（React/antd/CodeMirror） | 抓 `longtask` 的 attribution 看是谁 |

脚本另需支持 `mode: "hybrid" \| "dom" \| "canvas"` 三档切换（尖刺脚本已有），用于对照：hybrid 与 canvas 差得多 = DOM 节点层是瓶颈。

### 5.3 测量纪律

1. **只在同一台机器比较**。跨机器只比趋势，不比绝对值；换机必须重跑基线并重写附录 B。
2. **headless、固定视口 1000×720、DSR=1**（与附录 A 一致），关掉其它应用。
3. 每档先跑 20 帧 warmup 丢弃（JIT 预热）；正式样本 200 帧。
4. 每项跑 3 轮，取**中位数轮的 p95**，三轮极差 >30% 视为机器不稳，重跑。
5. 记录：CPU 型号、`navigator.hardwareConcurrency`、Chrome 版本、Node 版本（脚本部分）、测量时间。
