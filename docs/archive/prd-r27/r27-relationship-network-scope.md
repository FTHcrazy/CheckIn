## 一、一句话定义与作者痛点

### 1.1 一句话定义

> **把本书已建好的要素与关联，一次性渲染成可拖拽、可筛选的关系图，让作者在不离开编辑器、不丢一个字的前提下，扫一眼就看清「谁和谁有关系、哪些势力与地点被卷了进来」。**

它是 R24（要素互相关联）数据的**只读消费端**：本身不产生新数据，只把已经躺在 `novel_links` 里的关系换一种读法。

### 1.2 解决的痛点

| # | 作者痛点 | PRD 出处 | 本需求如何回应 |
|---|---|---|---|
| 1 | 写群像时不遗漏、不冲突——几十号人两两关系，列表读不出一条「结构」 | §4 用户故事「一键把已建好的关联渲染成关系网络图…写群像时不遗漏、不冲突」 | 力导向图把拓扑摊开，阵营 / 中心人物 / 孤岛一眼可见 |
| 2 | 要素卡的「关联要素」列表只能一次看一个人的邻居，看不到全局 | R24 现状（`EntityDetail` 单人视角） | 全量视图：所有人的关系在同一张画布上 |
| 3 | 卡壳时需要「3 秒内调出设定」 | G4 目标 | 图上点节点 → 节点小卡 → 一跳进资料卡，比逐层翻列表快 |
| 4 | 设定库随写作生长，但「长成什么样」从不被检视 → 大量孤立卡 | G5 目标 | 孤立要素**可见**（虚线）+ 计数提示，反向驱动作者补关系 |

> **不解决的痛点（避免误读）**：不帮助作者「想出」关系（那是人的事），不做关系合理性校验，不做时间线演进。

## 二、范围表

### 2.1 P0 —— 必做（缺任一条则不达「一键可用」）

| 编号 | 范围 | 判断依据 |
|---|---|---|
| P0-1 | 一键渲染：节点 = 本书**全部**要素，边 = 本书要素之间的关联；自动完成初始布局，**不需要用户再点任何按钮才出图** | PRD 说「一键」，多一步就不叫一键 |
| P0-2 | 节点单击 → 浮层内「节点小卡」（名称 / 类型 / 一句话 / 境界副标题 / 关联数）；小卡上「打开资料卡」→ 关浮层 + `openEntityDetail` | PRD 框架 ② ；为什么不直接跳见 §2.4-C-6 |
| P0-3 | 节点拖拽固定 + 坐标持久化（按作品），松手后 pin 住 | PRD 框架 ③ |
| P0-4 | 画布平移 + 缩放 + 「适应画布」（fit） | 200 节点必然超出视口，没有缩放等于不可用 |
| P0-5 | 按要素类型筛选（**单选** `Segmented`：全部 + `filterOrder`） | PRD 框架 ②「按类型筛选」 |
| P0-6 | 空态与降级（要素 < 3 / 可成图关联 < 2 / 节点数超阈值） | PRD 框架 ⑤ |
| P0-7 | 关闭并回到正文，**光标 / 滚动 / 未落库键入零丢失** | PRD §2 零打断原则（硬红线） |
| P0-8 | 孤立要素**可见**（虚线）+ 提示条「另有 N 个要素暂无关联」 | v1.1 修订 R-1，见附录 A |
| P0-9 | 双入口（`EntityPanel` 首行 + `ToolLauncher` 卡）共用一个 opener | v1.1 修订 R-2，见 §3.4 |

### 2.3 Non-goal —— 明确不做（每条给理由）

| 编号 | 不做 | 理由 |
|---|---|---|
| N-1 | **不做自动布局调参面板**（斥力 / 引力 / 边长滑块、算法切换） | ① 作者不是拓扑工程师，参数面板会退化成「调参玩具」，永远调不完；② 每次调参都要重跑模拟，与「打开即可看」直接冲突；③ 固定一套默认参数 + 「重新布局」一颗按钮已覆盖 99% 的抱怨。预研已把参数**硬编码进三力模型**（预研 §4.2），与本条一致 |
| N-2 | **不做跨作品关系网** | ① `novel_links` **没有 `work_id` 列**（预研 F12），跨书同名角色语义不成立（谁是谁？）；② PRD §3「单机单产品」与 G5「设定库随本书生长」都是单书内闭环；③ 跨书关系是独立产品命题（共享宇宙），需要单独的设定归属模型 |
| N-3 | **不做图上编辑要素内容**（改名 / 改类型 / 改一句话 / 删要素） | 要素编辑的唯一真相源是 `EntityDetail`（含类型迁移、境界重解析）。图上再开一条编辑入口 = 第二套校验，两处不一致只是时间问题 |
| N-4 | **不做图上新建关联**（拖线建边 / 右键建边） | ① `addLink` 只做「同对要素 + 同关系名」去重，**没有自环守卫**；图形化拖线会把误建成本降到近乎为零，等于放大这个缺口；② 建关系是「想清楚才做」的低频动作，不值得为它增加一个易错手势 |
| N-5 | **不做按势力折叠 / 节点聚合** | PRD §10 风险表已把「节点聚合（按势力折叠）」定位为 **P2 兜底**，不是 P1。P0/P1 先用类型筛选把图收小——筛选比聚合好理解、也好撤销 |
| N-6 | **不做关系的时间线 / 按章快照演进** | 需要按章版本化 `novel_links`（当前表无版本列、无生效章区间），是另一个需求的数据模型，不是渲染问题 |
| N-7 | **不做 3D / WebGL / 力导向以外的布局族**（环形、树形、分层 DAG） | 力导向是唯一能同时容纳「要素多类型 + 关系无层级」的通用布局；其它布局都要求用户先声明结构（谁是根、哪层在前），而作者没有这个心智 |
| N-8 | **不做第三方图谱 UI 皮肤**（G6 / AntV / Cytoscape 的默认视觉） | 见 §6.5，会与四套主题直接冲突 |
| N-9 | **不做常驻右栏小图** | 280–460px 宽下画 20 个以上节点就是一团毛线，必然被要求「能不能放大」，等于把 P0 推迟成两期 |
| N-10 | **不做键盘全量导航**（Tab 逐个遍历节点） | ① 图谱是无序二维空间，Tab 序无法定义；② 200 个 tabstop 只会让键盘用户在画布上"卡住"，比够不着更糟。**替代的无障碍基线**（不是不做无障碍，是换一条路）：节点 `tabIndex=-1` 不进入 tab 序；但**工具栏 / 两个入口 / 搜索框 / 关闭按钮 / 小卡与边详情内的按钮全部可聚焦**，且**「搜索」是键盘到达任意节点的唯一且完整路径**（命中 → 居中 → Enter 开小卡）。⚠️ 若预研把"节点必须是 DOM"的理由写成"`Tab` 可达"，请改写为"hover/tooltip/文本清晰/DPR 无关"这类真实理由（QA §9-Q1 已指出） |
| N-11 | **不做「无提示的静默裁剪」**（约束的是"静默"，不是"裁剪"本身） | 被裁剪的节点必须在界面上**明确告知**（提示条写明「仅显示关联最多的 500 个要素 **[显示全部]**」）并可一键恢复（**按钮必须真的可用**）。**有提示 + 可展开且可用 + 孤立不裁 + 默认不启用（③ 已执行且收窄后仍 >800 才开）** 的 Top-500 是允许的（见 D3 ⑤）；**静默少画几个节点、或默认就按 `degree` 裁剪**是禁止的——那条路会让作者在某个深夜发现"我的角色呢"，且无法自证是误伤 |

### 2.4 与代码实现的偏差（收口结论）

> 这是本文件最重要的一节：以下 10 条是「照着字面写就会踩坑」的地方。C-1~C-7 是我对 PRD 的勘误，C-8~C-10 是与预研对齐后新增的判定。

| # | 原表述 | 代码事实 | 收口结论 |
|---|---|---|---|
| **C-1** | 「节点 = 要素，边 = 关联，数据零新增，一键渲染即可」 | `novel_links` 是**多态**表：① 存在 `to_type = 'level'` 的行（「当前境界」绑定，`to_id` 指向 `novel_setting_levels.id`，**不是** `novel_entities` 的行）；② `useNovelData.ts:390` 的 `data.links` 是 `bundle.links`，**未按 workId 过滤**（`entities` 过滤了，`links` 没有）；③ `novel_links` **根本没有 `work_id` 列**（预研 F12） | 「边 = novel_links」**不成立**。必须两层收口：**① 顶点归属反推**（两端 id 都必须落在本书要素 id 集内 —— 这是唯一可行口径，因为表里没有 work_id）；**② 端点半解析**（`level` 不画边、降级为节点属性）。详见 §4.2 / §4.4 |
| **C-2** | 「双击边可加备注」 | ① 边线视觉宽度 1–1.5px，双击命中率极低；② `note` 列存在但**当前全链路没有任何写入口**（`addLink` 不传 `note`，`EntityDetail` 不展示也不编辑），值恒为 `null`；③ 预研拟将边画在 `<canvas>` 上，**没有 DOM hit area 可用** | **双击 → 单击**，且命中检测为数学判定（点到线段距离）。理由：缩放手势是滚轮/捏合，双击本来不冲突；问题从来不是冲突，而是命中率与"无 DOM 可点" |

## 三、视图形态与入口

### 3.1 三种候选形态（按「不打断码字 / 实现成本 / 关系图可读性」三维对比，5 分制，分高为好）

| 维度 | A. 右栏内嵌<br><sub>要素 Tab 内切成 graph 子视图（可参照现有 `toolSub` 二级面板模式）</sub> | B. 码字区全宽覆盖层<br><sub>页内覆盖 `.nv-page__body`，编辑器保持挂载不卸载</sub> | C. 独立窗口<br><sub>照 PackWindow / GlobalSettingWindow 模式新建窗口</sub> |
|---|---|---|---|
| **不打断码字** | 5 —— 面板本来就是「写着查」，本身不遮正文 | 3 —— 遮住正文，但草稿在编辑器里、一键回；不触发保存、不动光标 | 4 —— 正文完全不动，可双屏对照；但切回要靠 Alt+Tab |
| **实现成本** | 5 —— 最省：复用 `toolSub` + 现有面板宽高 | 3 —— 新增覆盖容器 + 层级 + Esc 优先级 + resize 重测 | 2 —— 窗口入口 HTML/main/App + `edition.ts` 三处登记 + 主进程创建 + 单实例 + 上下文投递 + preload + `edition.test.ts` 护栏 |
| **关系图可读性** | **1** —— 280–460px 宽，200 节点必然糊成一团；20 节点就开始互相压字 | 4 —— 可用整窗宽度（顶栏仍保留面包屑，不丢「我在第几章」的上下文） | 5 —— 可全屏、可第二屏、不受编辑器栏宽影响 |
| **合计** | 11 | **10** | 11 |

> 分数接近，说明三维之间是真正的取舍，不是一边倒。下面给判断依据。

### 3.2 推荐：**B. 码字区全宽覆盖层**（与预研 §1 一致）

1. **A 被「可读性 1 分」直接否掉，不是折中能救的。** 关系图的价值与画布面积是超线性的：20 个节点在 340px 宽里还能看，60 个就废。做 A 的唯一结果是「上线当天收到『能不能全屏』的需求」——等于把 P0 拆成两期，还先欠了一笔体验债。
2. **C 的成本是对的，但它买错了东西。** 独立窗口最贵的不是窗口本身，是**跨窗口数据同步**（`pack-window-context` / `novel-work-changed` 那套投递基建）。而这个图的生命周期是「打开—扫一眼—关掉」，典型时长以十秒计；为一个十秒的东西开一个 OS 级窗口（任务栏多一项、Alt+Tab 多一跳），交互链路反而更远。
3. **B 在代码里有现成的同构先例。** `EditorPane` 的「未选中章节空态」就是用覆盖层遮住**常驻的**编辑器而不是卸载它（`EditorPane/index.scss:247`，注释写着「遮住常驻编辑器而不是卸载它 —— 否则初始化 effect…」）。这正是本需求要的：未落库键入留在编辑器里，关掉覆盖层立刻接着写。
4. **B 的「不打断」是 3 分而不是 5 分，但这 2 分是可接受的产品取舍。** 关系图是「看」的任务，不是「写」的任务；作者进入时本来就预期「暂停打字」。真正的红线不是「不能遮正文」，而是 **「遮了之后一个字都不能丢、关掉之后光标还在原处」**——这条 B 完全满足（§九 B 组）。

## 四、节点与边语义映射表

### 4.1 节点：`novel_entities` 哪些 type 成为节点

> 统一原则（v1.1 修订）：**节点 = 本书 `novel_entities` 的一行，一一对应，全部画出。** 类型的差别只体现在「视觉权重」与「是否可被类型筛选关掉」，**不体现在「是不是节点」**。

| 要素 `type` | 成为节点 | P0 默认可见 | 视觉权重 | 说明与理由 |
|---|---|---|---|---|
| `character` 角色 | ✅ | 可见 | 主（实心 + 类型色描边） | 用户故事主体 |
| `faction` 势力 | ✅ | 可见 | 主 | **必须画**：阵营关系靠「角色 →（所属）→ 势力」这个中继表达；只看角色，「看清阵营」直接失败 |
| `location` 地点 | ✅ | 可见 | 次 | `归属地`/`出生地`/`驻地`/`走私通路`（模板里 4 条）全落在地点节点上 |
| `item` 物品 | ✅ | 可见 | 次 | 模板 2 条（`持有`/`认主`）；物品是关系中介，砍掉会断开角色-角色链路 |
| `level_system` 等级体系 | ✅ | 可见 | 次 | **v1.1 改口径**：原先我主张默认隐藏（理由："标尺不是关系主体"、模板里零关联必然成孤立点）。但 R-1 之后规则统一为「全部要素都画」，再对它单独开例外会造成"要素库看得到、图里看不到"的第二重困惑。**一致性 > 视觉洁癖**；用户可用类型筛选单独关掉它 |
| `custom` / `ct-*` 自定义类型 | ✅ | 可见 | 次 | 与要素库一致：用户自建类型是一等公民（R23），不给它降级 |

**孤立节点（度 = 0）**：**照画**，参与布局、自然漂在包围盒外围，用**虚线描边**区分（见 §6.2）。理由见附录 A。

### 4.2 边：`novel_links` 哪些行成为边

> 判据不是「表里有没有这行」，而是「两端能否落到本书的要素节点上」。

| link 情形 | 是否成边 | 处置规则 | 理由 |
|---|---|---|---|
| 两端 `type` 都是要素类型，且两端 id 都在**本书** `entities` 里 | ✅ 正常边 | 归组后渲染（§4.3） | 主路径 |
| `to_type = 'level'`（「当前境界」绑定） | ❌ **不画边** | **降级为节点属性**：该角色节点副标题显示境界名；名称由 `formatBoundRealmName(category.levels, link.toId, parseRealmNoteSub(link.note))` 派生（`EntityPanel/index.tsx:164-180` 已有同款逻辑，直接复用，勿另写） | ① `to_id` 指向 `novel_setting_levels.id`，**不是** `novel_entities` 的行 → 画出来是悬空/无名的假节点；② 境界是**状态**不是**关系**（一个人只有一个境界，属属性维度），画成边会让人误以为「境界」是关系主体。这也解释了为什么 `EntityDetail` 把它放在独立区块而非「关联要素」里 |
| 任一端在**别的作品**的要素上 | ❌ 丢弃 | 计入 `diagnostics.droppedByOtherWork`（供测试与排查），**不并入界面「已忽略」数字**（v1.6 裁决，理由见下） | `data.links` 未按作品过滤（C-1），这是**真实会发生**的：库里有第二本书，它的边就会混进来。不丢弃 = 图上出现无名悬空边。**不并入界面数字**：这些边本来就不是"这本书的关系"，把它算进「已忽略 N 条关联」会随"库里还有几本书"漂移，作者看到一个变动的 N 却无从追溯——恰恰是这条提示要防的那种误解 |
| 端点 `type` 既非要素类型也非 `level`（如 `chapter`） | ❌ 丢弃 | 计入诊断计数 | 当前**没有任何写入路径**产生章节端点（模板 9 条全是 entity/level，`addLink` 的 DTO 只来自 `EntityDetail` 的目标下拉）。表无约束所以"可能"存在 → 防御性丢弃即可，**不设计**「章节边」的视觉 |
| `from_id === to_id`（自环） | ❌ **不画** | 过滤 + 计入诊断计数 | 见 §4.3 |
| 端点 id 在 `novel_entities` 里查不到（脏数据） | ❌ 丢弃 | 计入诊断计数 | 当前**没有单要素删除能力**（全库无 `removeEntity`/`deleteEntity`），正常使用不会产生；但模板导入等路径仍可能有，防御成本近乎为零 |
| 完全重复行 | — | 归组阶段天然去重 | 表无 UNIQUE 约束，理论上可 insert 两行完全相同记录 |

**「已忽略 N 条关联」的呈现**：不做弹窗，只在头部右侧显示弱化文字 + `Tooltip` 明细（哪条、为什么）。理由：静默丢弃会让作者某天发现「我明明建过这个关系」却查不出原因，这是最难查的一类 bug。

**两个计数必须分开**（QA §9-Q4 提出，采纳）：

| 数字 | 分母 | 模板值 | 含义 |
|---|---|---|---|
| 提示条「另有 N 个要素暂无关联」 | `ignored.isolated` | **2** | 没有关联的**要素**（不是被丢弃的边）——它们照画（虚线） |
| 「已忽略 N 条关联」 | **`droppedLevel + droppedSelfLoop + droppedUnknown`**（**不含 `droppedByOtherWork`**，v1.6 裁决）= 与 §4.4 五键中的三个"丢弃类"键一致 | **1** | 被丢弃的**边**（模板里那 1 条是境界绑定 → `droppedLevel`） |

**`duplicate` 不进这个分母**（v1.5 评审裁决）：完全重复的行在**归组阶段天然去重**，两条一样的记录合并成一条边，属于**合并**不是**丢弃**——用户看到的边一条没少，报"已忽略"反而是虚报。§4.4 的 `diagnostics` 因此只有五键（`droppedByOtherWork / droppedLevel / droppedSelfLoop / droppedUnknown / isolatedIds`），**没有 duplicate 键**，C7 的验收也按五键写。

**`droppedByOtherWork` 也不进这个分母**（v1.6 裁决，QA 提出、PM 采纳）：它**保留在 `diagnostics` 里**供测试与排查，但**不并入界面数字**。理由：这个数会随"库里还有几本书"漂移——同一本书，多导入一本有 30 条关联的作品，「已忽略」就从 1 变成 31，而作者对那 30 条**既看不见也管不了**。提示条的全部价值是"让丢弃可追溯"，追溯不到的数字只会制造怀疑。

上表分母与 §4.4 契约**逐字对齐**，改任何一边都必须同步另一边（这是本轮 QA 交叉核对抓出来的第 2 处矛盾）。

两个数字混算会让口径失真（混入 `isolated` 得 3），用户会开始怀疑统计，而这一行文字的全部价值就是"让丢弃可追溯"。

### 4.3 方向性 / 双向去重 / 自环 / 多重边

| 议题 | 数据现状 | 收口规则 | 理由 |
|---|---|---|---|
| **方向性** | `novel_links` 有 `from→to`，但 UI 从未提供方向编辑（`EntityDetail` 添加关联只有「目标要素 + 关系名」） | **P0 画无向边**（视觉无箭头）；方向信息**保留在边详情**，形如「沈孤舟 → 陆青冥 · 亦敌亦友」 | ① 视觉给箭头 = 承诺「方向有意义」，而产品从未让用户表达方向，这是**虚假的精确**；② 现有去重规则本身是「一对要素 + 同关系名只留一条（任一方向）」（`useNovelData.ts:1174`），说明产品心智已是「一对关系」而非「一条有向边」。P1-9 再开「显示箭头」 |
| **双向去重** | 去重键是「**无序对** + 同 `relation`」：A→B「师徒」与 B→A「师徒」只能存一条；但 A→B「师徒」与 B→A「徒弟」可各存一条 | 两行**不合并成两条边**，合并进**同一条边的多关系标签**：显示「师徒 / 徒弟」。**不**做语义归一，**不**报警 | 这是作者用两种叫法描述同一件事，合法且有信息量；判定「师徒 = 徒弟」需要语义推理，产品不该替作者下判断（与「不做 NLP」同源） |
| **一对节点多条不同关系**（如「师徒」+「敌对」） | 合法，群像小说常见 | **合并为一条「多重边」**：**画布标签 = 首条 + `+N`**（如「亦敌亦友 +1」）；点开边详情**逐条列出**（每条各自的备注与「解除」）。**`·` 拼接（如「亦敌亦友 · 挚友」）只出现在边详情里，不得出现在画布标签上**。首条取**确定性排序后的第一条**（`localeCompare(a, b, "zh-Hans")`），不得依赖插入顺序 | 200 节点 × 500 边下，平行边间距在力导向里不可控（会叠在一起），合并 + `+N` 信息密度最高。**画布只给首条**：边标签是空间极稀缺资源（一条边中段只有几十像素），两个关系名拼起来会横跨节点、指向两个不同方向；而边详情本来就承担"完整列出"的职责，没必要在几十像素里挤。**排序必须确定**：否则同一份数据在不同机器 / 不同 ICU 版本上会渲染出不同字符串，快照测试与"我说的是哪条"的沟通都会抖（QA §9-Q6） |
| **自环** | `addLink` **没有** `fromId === toId` 守卫（代码事实），「角色 A 关联自己」存得进去 | **渲染层过滤 + 计入诊断**；P0 **不**改 `addLink`（不改现有行为）。建议架构师评估顺手补一行早退（预研 §3.4 已倾向"改"） | 自环在关系图里没有可读的视觉表达（圆环套自己），只会让度统计失真 |
| **跨作品校验守卫** | 预研 R2-3 核实：`EntityDetail` 的关联目标下拉数据源是已按 work 过滤的 `entities`，且排除自身 → **UI 路径造不出跨作品边**；真正的口子在主进程 `novel-link-set`（已有守卫） | **不在 `addLink` 加跨作品校验**（会是死代码），只在派生层做归属过滤 | 不写死代码，比"多一层保险"更重要 |

### 4.4 派生契约（产品侧输入，不是实现方案；预研 §3.2/§3.3 已给出签名）

| 输入 | 输出 | 必须成立的性质 |
|---|---|---|
| `entities`（已按 `activeWorkId` 过滤）、`links`（**全库，未过滤**）、`levelRungIndex` / `settings`、可见类型、可见关系名 | `nodes[]`、`edges[]`、`diagnostics{ droppedByOtherWork, droppedLevel, droppedSelfLoop, droppedUnknown, isolatedIds }` | ① **作品过滤必须发生**（不能信 `links` 已是本书的）；② 无自环、无重复边、无悬空端点；③ 同一输入产出同一结果（纯函数，可单测）；④ 布局坐标不参与该函数（坐标是另一层）；⑤ **孤立节点必须出现在 `nodes` 里**（R-1），不得在派生层被过滤掉 |

### 4.5 「人物关系网络」这个名字与实画范围

PRD 标题叫「人物关系网络」，但 §4.1 要求画势力 / 地点 / 物品 / 等级体系 / 自定义。收口：**保留产品名「关系网络」，实画「要素关系网络」（角色为视觉主体）**。不改名的理由：作者的心智是「人物关系」，势力/地点只是关系的延伸；改名成「要素关系网络」会抬高发现成本。工具箱卡片（§3.4.2）文案已用「人物关系网络」，与本结论一致，**不需要改文案**。

**I-12 三档降级的具体口径**（最容易做糊，单列）：

| 档位 | 判据 | 呈现 | 为什么不是其它做法 |
|---|---|---|---|
| D1 完全空态 | 本书要素数 **< 3** | 居中空态卡：标题「还画不出关系网络」+ 说明「至少需要 3 个要素」+ 主 CTA「去要素库建卡」 | 要素 < 3 时任何图都无意义（2 个点 1 条线不是网络）。**不渲染画布**，避免"加载失败"的错觉 |

## 六、视觉与设计语言约束

### 6.1 主题变量映射（四套主题必须同时成立）

> 铁律沿用 `AGENTS.md` §6.1.1：业务样式只写 `var(--app-*)`，TSX 内联样式同样禁止硬编码色值。**canvas 不吃 CSS 变量**，边与 canvas 文字的颜色必须由 JS 读取计算值后传入（预研 §9.2 已给桥接方案）。

| 元素 | 用哪个变量 | 禁止用的 | 说明 |
|---|---|---|---|
| 浮层根底 | `--app-bg` | `--app-surface` | `themes.scss` 明确：「窗口 / 页面根一律铺 `--app-bg`，不许铺 `--app-surface`」 |
| 节点底 | `--app-surface` | `--app-surface-elevated` | 节点不是浮层 |
| 节点描边（常态） | `--app-border-strong` | `--app-border` | 200 个 1px `--app-border` 在浅色主题下几乎看不见 |
| 节点描边（hover / 选中 / 邻接） | `metaOf(type).color` | — | 类型色只在这里出场 |
| **节点描边（孤立要素）** | `--app-border-strong` + **`dashed`** + 文字 `--app-text-muted` | 红色 / 警示色 | 孤立不是错误，只是"还没连"，用警示色会让作者以为数据有问题 |
| 节点头像块底 | `metaOf(type).colorWeak` | — | 内置类型是 `--app-*-weak`（四主题自动成立）；`ct-*` 由 `color-mix(in srgb, color 15%, transparent)` 派生（`entity-types-context.ts:33` 已有实现，复用） |
| 节点主文字 | `--app-text` | 类型色 | 见 §6.4 |
| 节点副文字（境界 / 类型名） | `--app-text-muted` | — | 与主文字拉开层级 |
| 边（常态） | `--app-border-strong` | `--app-text-disabled` | 后者在暗色下过淡 |
| 边（hover / 选中 / 邻接） | `--app-primary` + 线宽 2.2 | — | 与全站"当前/选中"语义一致 |
| 边标签底 | `--app-surface-elevated` | — | 标签本身就是浮层，用浮层专用变量 |
| 边标签文字 | `--app-text-secondary` | — | 比节点正文弱一档 |
| 已固定节点 | `--app-primary` 实线加粗 + 小图钉点 | — | 复用"当前/选中"语义，不新造色 |
| 节点小卡 / 边详情面板 | `--app-surface-elevated` + `--app-shadow-pop` | — | 浮层专用 |
| 筛选控件 | 类型 `Segmented`、关系 `Select`、操作 `Button` | 自绘 chips 群 | §6.5 的组件库边界 |
| 空态 | `.nv-empty` 现成样式 | 另写一套 | 与要素库空态视觉一致 |

### 6.2 层级与信息密度

| 层级 | 内容 | 密度约束 |
|---|---|---|
| L0 画布 | 无网格底、无渐变、无装饰 | P0 **不做网格底**：网格是"绘图工具"的语言（R28 地图需要），关系图要干净底突出拓扑 |
| L1 节点（默认） | 缩微要素卡：类型色圆角块（内含要素名首字）+ 名称单行（**恒 6 字截断**，悬停 / 选中显示全名） | 建议高 ≈ 40px。200 节点在 1000×700 画布上均摊 3500px²，40px 高 × ~120px 宽的 pill 可容纳 → **默认形态 pill 而非卡片**（与 `.nv-chip` 视觉同源，密度高 2–3 倍）。**截断口径唯一，不随档位变化**：≤400 节点全档一律 6 字截断（`Tooltip` / 悬停 / 选中给全名）；**401+ 只画色点、不画字**。不存在"到某个规模档才开始截断"的说法——不截断时一个 20 字长名会把节点撑成一条船，这跟性能无关，是信息密度的底线 |
| L1' 节点（孤立） | 同上 + **虚线描边** + 主文字 `--app-text-muted` | 让"没连上"在扫视阶段就能被识别，不必逐个去读 |
| L2 节点（hover / 选中 / 主角） | 追加一行副标题（类型名 / 境界名），尺寸放大到 ≈ 48px | 只对**单个**节点生效，不批量展开 |
| L3 边 | 线宽 1.4px；**节点数 ≤ 120 常驻标签（截断 8 字），> 120 改为仅悬停显示** | 预研 Q4 的取舍；500 条边全常驻必然糊屏 |
| L4 工具栏 | 类型 `Segmented` + 关系 `Select` + 视图操作（fit / ± / 导出 / 重新布局） | 单行；溢出时把次要操作收进「更多」`Dropdown` |
| L5 诊断信息 | 提示条（孤立 N 个）+「已忽略 N 条关联」 | 弱化文字 + `Tooltip`，不占主视觉 |

### 6.3 与要素类型色板的一致性

| 规则 | 内容 |
|---|---|
| 单一真相源 | 类型的展示 meta 一律经 `useEntityTypeMeta().metaOf(type)`，**禁止**直接索引 `ENTITY_TYPE_META`（`ct-*` 会拿到 `undefined`，`entity-types-context.ts:14` 原话） |
| 「三处一致」的第四处 | 既有约束是「类型色在正文高亮、卡片头像、筛选 chips 三处严格一致」（`novel-config.ts:135` 注释）。图谱是**第四处**，必须同源同色，不得为图论调色。**单一真相源是 `ENTITY_TYPE_META`（`novel-config.ts:139-170`）+ `useEntityTypeMeta()`**；`EditorPane/index.scss:224-244` 那张表只是标注层的**同值副本**，引它会绕过 `ct-*` 的 inline 注入（`--nv-mark-color`），因此在图里**不可作为数据源** |
| 内置类型 | `--app-primary` / `--app-accent-green` / `--app-accent-purple` / `--app-accent-amber` / `--app-accent-blue` / `--app-text-secondary`，换肤自动跟随 |
| 自建类型（`ct-*`） | 色值是用户用 `ColorPicker` 自选的**任意 hex**（`CUSTOM_TYPE_PALETTE` 只是"推荐起点"，不是可选范围）。因此：**只能用于描边 / 头像块底 / 角标点，绝不可用于文字颜色，也不可作为节点整块填充** |
| 8 色板 | `CUSTOM_TYPE_PALETTE`（8 个中饱和色）是"新建类型时的默认推荐"，**不是**图谱的独立调色板。图谱不得引入自己的色表 |

### 6.4 深色主题（`midnight`）对比度要求

| 项 | 要求 | 为什么 |
|---|---|---|
| 节点主文字 vs 节点底 | ≥ **4.5:1**（WCAG AA 正文） | 图谱是"读名字"的界面 |
| 节点副文字 vs 节点底 | ≥ **4.5:1** | 副文字是 P1 信息主体（境界 / 类型） |
| 边线 vs 画布底 | ≥ **3:1**（非文本对比度） | 边是拓扑信息本身，糊掉的边等于丢数据 |
| 孤立节点虚线 vs 画布底 | ≥ **3:1** | 虚线比实线更难辨识，不能靠"淡一点"来区分 |
| 类型色描边 vs 画布底 | ≥ **3:1**；不足时补一圈 `--app-surface` 内描边做视觉分离 | 自建类型任意 hex 在暗色下可能过暗（如 `#64748b`） |
| **硬规则** | 任何色值必须来自 `--app-*` **或** `metaOf().color`（后者仅限非文字元素）。**禁止** `filter: invert()` / `mix-blend-mode` 去"适配暗色" | 前者随主题切换自动成立；后者会同时破坏四套主题，并让导出 PNG 的颜色不可预期 |

### 6.5 第三方图谱 UI 皮肤禁令与组件库边界

| 项 | 结论 | 理由 |
|---|---|---|
| G6 / AntV / Cytoscape / vis-network 的**默认视觉** | ❌ 禁止 | 它们各自带来与 `--app-*` 无关的色板与圆角体系，四套主题下必有一两处"外来色斑"；且自带 tooltip / 上下文菜单会绕过 antd 暗色算法（正是 §6.1.2 要治的病） |
| 纯数学/布局库（如 `d3-force`） | ⚠️ 允许但**预研已实测排除** | 它不产生 DOM 与样式，不污染主题。但预研 §4.3 实测在 ≤800 节点规模 quadtree 是负收益、且要额外背 15KB → **结论是零新增依赖、自研三力模型**，本文不反对 |
| d3 全家桶的 `d3-selection` / `d3-zoom` / `d3-drag` | ❌ 禁止 | 与 React 的渲染所有权冲突（双写同一棵 DOM），且事件系统与 React 合成事件打架 |
| §6.1.2「禁止原生表单控件」的适用边界 | 画布**本身**属"自绘可视化画布"，不受该清单约束（清单管的是下拉/输入/按钮/浮层）；画布**外围**一切控件——`Segmented`、`Select`、`Input`、`Button`、`Tooltip`、`Popover`、`Popconfirm`、空态 CTA——**必须**用 antd | 防止实现时把筛选做成自绘 chip 群、把边详情做成手写 `position: fixed` 浮层 |

### 6.6 动效

| 项 | 约束 |
|---|---|
| 布局模拟 | 必须"渐进到位"（节点从初始位置平滑收敛），**不允许**首帧乱成一团再突然跳到位 |
| 稳态 | 模拟必须**主动停止**（PRD §10 风险表原文：「力导向仅作为初始布局、稳态后停止模拟」）。停止后不得再有每帧重绘 |
| 过渡时长 | 浮层开/关 ≤ 180ms / ≤ 150ms；节点 hover 放大 ≤ 120ms |
| `prefers-reduced-motion` | 命中时：布局直接给最终结果（不做收敛动画）、开合改为无动画淡入淡出、搜索命中不做脉冲。图谱是全站动效最强的场景，这条必须单独实现，不能靠全局开关 |

| `LEVEL_RELATION` 常量 | **复用** | 判断境界绑定用 `toType === "level"`，判断关系名用常量，不手写字面量 |
| `ToolLauncher` 工具卡清单 | **就地改造**（§3.4.3） | 只改 `relation` 一项的 `onOpen` / `state` / `plannedHint` 三个字段，不动容器版式（该文件的注释明确「新工具接入只需在清单里加一项」） |
| 「重置模板」（`onResetTemplate`） | **作为 P0 冒烟数据** | 模板实测：**11 要素**（3 角色 / 2 地点 / 2 势力 / 2 物品 / 1 等级体系 / 1 自定义）+ **8 条实体关联** + **1 条境界绑定**（`novel-template.ts:843-868`）。打开图的期望值：**11 节点 / 8 边 / 1 条降级为副标题 / 2 个孤立要素（`tpl-e-sys-lingtu`、`tpl-e-custom-calendar`）虚线显示 + 提示条「另有 2 个要素暂无关联」**。QA 不用手工造数据 |
| 跨窗口 / 跨会话状态 | **不需要** | 图是页内视图；不存在"另一个窗口在看同一张图" |
| `@dnd-kit` | **不建议用于节点拖拽** | 它是列表排序库（DOM 序），图中拖拽是自由坐标 + `setPointerCapture`，用它反而绕 |
| `framer-motion` | 可选，非强制 | 开合过渡可用；搜索命中脉冲建议纯 CSS `@keyframes`（预研 §6.5 已如此定） |

## 八、数据与埋点

### 8.1 需要新增的持久化：只有一项 —— 布局记忆

| 项 | 定义 |
|---|---|
| 存什么 | `Record<workId, { v: number; ts: number; k: number; tx: number; ty: number; nodes: Record<entityId, [x, y, fixed?]> }>`（结构见预研 §7.1） |
| 存哪 | `novel-config-get/set`，`STORAGE_KEYS` 新增 `relGraphLayout: "novel_rel_graph_layout"`。**不用 localStorage**（C-3） |
| 为什么按作品 | 坐标集合是"某本书的图"的快照；按作品分组换书互不影响，与 `novel_naming_favorites` 同范式 |
| 为什么连 viewport 一起存 | 用户在"放大看局部"的状态下关掉图，下次重开若被 fit 重置，等于每次都要重新找位置（预研 Q10，< 40 字节） |
| 写入时机 | 拖拽松手 / 缩放结束 / 平移结束后 **300ms 防抖**（对齐 `PANEL_WIDTH.debounceMs`）+ 卸载/关窗前兜底 flush |
| 读取时机 | 打开图时一次；读失败 → **静默**回退"跑一次布局"（`novel-config-get` 在 DB 未就绪时静默返回 null，预研 F22） |
| 容量 | 实测 200 节点 **5.85KB**、400 节点 11.66KB（预研 §7.1）。无压力 |
| **必须做的清理** | ① 写入前剔除已不存在的 `entityId`（预研 §7.3）；② 作品删除时一并清（`novel-work-delete` 有单事务级联，需在此处追加清 config 键）；③ 带 `v` 版本号，结构变更时直接丢弃旧值，不写迁移（config 不是业务表，无需走 §6.5） |

### 8.2 需要新增的埋点：建议 1 条

| 事件 | 时机 | payload | 参与既有指标？ |
|---|---|---|---|
| `rel_graph_open` | 图成功渲染首帧（含降级态） | **产品口径与性能口径取并集（评审裁决后的最终字段，实现按此为准）**：<br>`entry: "entity-panel" \| "tool-launcher" \| "entity-detail"` · `nodeCount` · `edgeCount` · `ignored: { level, dangling, selfLoop, duplicate }` · `deriveMs` · `firstPaintMs` · `settleMs` · `stopReason`<br>**`entry` 的用途**：判断双入口哪个真被用、能否砍掉一个（这是唯一数据依据） | **不参与**。`novel-usage-today` 的 SQL 有 `WHERE event = 'chapter_save'` 硬过滤（`novel-handlers.ts:1648` 起），`streakDays` 同样基于 `chapter_save` → 新增事件**不会**污染"今日新增"或连续码字天数 |

**建议理由**：`novel_usage_log` 本身支持任意 event 字符串（`event TEXT NOT NULL`），加一条的成本是一行 `logUsageEvent`（预研 F23 已核实无事件白名单）。收益是能回答必须回答的问题：**R27 有没有人用？两个入口哪个真被用？** 若不做埋点，P1 的排序只能靠猜。`entry` 字段是预研 Q9 的建议，采纳——它是"日后砍掉一个入口"的唯一数据依据。

### 8.3 「不需要」但可能被误以为需要的东西

| 项 | 结论 |
|---|---|
| 新表 | **不需要**。`novel_entities` / `novel_links` 已备齐；布局走 config |
| `novel_links` 加列 | **不需要**。`note` 列已存在（只是从未被写过）。加列会触碰 `compat` 下的增量迁移成本，无收益 |
| 布局表 / 单要素删除通道 | **不需要**（后者是既有产品缺口，不在 R27 范围） |
| **新的二进制写文件通道** | **需要**（P1 导出 PNG）。现有 `novel-export-file` 以 `utf8` 写字符串；应**扩展**该通道或新增 `novel-export-binary`（预研 §8.3 已给方案） |
| **新的 link 更新通道** | **需要**（P1 边备注）。`novel-link-add/remove` 无更新语义；`novel-link-set` 不能挪用（四元组先清后插会误删同端点平行边，预研 F6）。建议新增 `novel-link-note`（UPDATE note） |

## 附录 A · R-1「节点口径」拍板记录

**问题**：节点是否只画「参与了至少一条边的要素」？

**v1.0 的错**：为了给 QA 一个干净的数字（9 节点），我默认了"孤立要素不画"。这个选择把**实现便利**放在了**用户信任**之上：

- 用户新建一个角色、还没来得及连关系 → 打开图找不到他 → 第一反应不是"他还没关联"，而是**「我的数据丢了」**。
- 模板里被隐掉的两个恰好都是无关联要素，这个"巧合"会掩盖问题，让测试期发现不了。
- 更糟的是：**孤立要素是作者最需要被提醒的东西**（G5 目标就是"设定库随本书生长"）。把它们藏起来，等于把最有行动价值的信息（"这 8 个角色有 3 个还没连"）静音。

**结论（v1.1）**：**节点 = 本书全部要素**。孤立要素：

| 维度 | 处理 |
|---|---|
| 是否显示 | 显示 |
| 视觉区分 | 虚线描边 + 主文字 `--app-text-muted`（**不用**警示色：孤立不是错误） |
| 布局参与 | 参与，自然漂在包围盒外围（它们本来就没有结构，不该占据中心） |
| 提示 | 顶部提示条「另有 N 个要素暂无关联」+ 「去要素库」；N = 0 时不渲染 |
| 隐藏出口 | P1-8 提供开关（默认关） |
| 夹具期望 | **11 节点 / 8 边 / 1 条降级 / 2 个孤立** |

**代价（诚实记录）**：默认视图在"设定卡建得杂"的书里会多出十几个外围散点，扫视成本变高。缓解手段是类型筛选 + P1-8 开关。接受这个代价，因为另一种错误的代价（"找不到我的东西"）更高且更难挽留。

## 附录 B · R-2「双入口」拍板记录

**问题**：入口放几处？

**v1.0 的错**：只写了 `EntityPanel` 首行，漏掉了 `ToolLauncher` 里**已经存在**的「人物关系网络 · 规划中 · R27」占位卡（`ToolLauncher/index.tsx:58-67`）。上线后这张卡会永久显示"规划中"，而功能明明已经能用——这是最伤信任的一类不一致（用户会开始怀疑其它"规划中"是不是也早就能用了）。

**结论（v1.1）**：**双入口 + 单一 opener**，并按 §3.4.3 分三期把占位卡切到"已上线"、最终去掉角标。

**为什么不是"删掉这张卡"**：① 工具箱是 R31 定下的"工具入口统一收在右栏"的既定信息架构；② 两类心智都合理——"从要素出发"（要素 Tab）与"从功能出发"（工具箱）；③ `ToolLauncher` 的设计目标就是"新工具接入只需在清单里加一项"，删卡等于破坏这个扩展点。

**为什么必须共用一个 opener**：否则"关面板 + 开浮层 + 记埋点"三件事会被抄两遍，日后必有一处漏改（比如新增"从资料卡反跳"时只改了其中一个）。`entry` 参数让两个入口在数据上仍可区分。

## 附录 C · R-3「规模降级」拍板记录

**问题**（预研 v1.1 待拍）：节点数超过阈值时，是否接受「只显示度数 Top 500」？

### 过程（保留分歧，便于日后复盘）

| 阶段 | 结论 | 理由 |
|---|---|---|
| PM 初判（v1.2 首版） | **不接受任何按度数裁剪** | 度数排序是黑箱：作者看到"少了一个人"时既不知道为什么、也无法验证是否误伤；度数低 ≠ 不重要（只连一条边的人可能是全书关键伏笔）；有连线节点承载拓扑信息，删掉会让剩下的边指向虚空 |
| 评审裁决（v1.3 本版） | **允许，但必须满足四项条件，且只在 P2** | PM 的顾虑成立，但可以通过"**明示 + 可展开 + 孤立不裁 + 极端才触发**"把这四个风险逐个封住；对一个 >1200 要素的极端场景，完全禁止裁剪会让产品在该场景下直接不可用，代价比"可解释的裁剪"更高 |

**裁决后的口径（v1.5 定稿，分层 + 可逆）**：**默认永不静默按 `degree` 裁剪**。⑤ 只在**三个条件同时成立**时启用 —— ① 总量 `> 1200`；② **③ 已执行**（守卫通过、确已收窄到「角色」）；③ **收窄后仍 `> 800` 节点**（800 = 实测 p95 4.7ms 的上限档）。**③ 被跳过则 ⑤ 一律不启用**。启用后：对**有连线节点**取 `degree` Top 500 + **额外保留全部孤立节点（上限 200）**，提示条「仅显示关联最多的 500 个要素 **[显示全部]**」，「显示全部」必须真的可用（可给性能警告，不得禁用）。

### 四项条件（缺一不可，这也是 PM 原顾虑的解法）

| # | 条件 | 封住的风险 |
|---|---|---|
| 1 | **必须明示**：提示条写清"仅显示 Top 500、另有 N 个未显示" | 封住"黑箱"：用户知道发生过裁剪、知道少了多少 |
| 2 | **必须可一键展开，且「显示全部」真的可用**（卡顿也只给性能警告，不得禁用） | 封住"无法自证误伤"：想看的人点一下就能看到全部，自己承担性能代价。**禁用 = 把可逆变成不可逆，条件 2 会当场失效** |
| 3 | **孤立节点一律不被裁**（上限 200，超限同样计入提示条 N） | 封住"新建角色消失"：这正是 R-1 改口径的原因，不能在极端档把它偷偷推翻 |
| 4 | **只在 P2 兜底、只在 ①②③④ 之后**，且必须**③ 已执行 + 收窄后仍 > 800** 才启用 | 封住"误伤关键人物"的暴露面：200/500 基准规模下永不发生；③ 被跳过（角色占比不足）时连兜底都不开，避免"为了性能去裁一个本来就不是主体的类型" |

### 降级顺序（不跳级）

① 降信息密度（≤120 正常 → 121–200 隐藏角标 → 201–400 边标签仅悬停 → 401+ 只画色点不画字）
② 折叠孤立要素（提示条「另有 N 个要素暂无关联 [展开]」）
③ **默认把类型筛选收窄到「角色」——受守卫条件约束（见下节）**，收窄时 Segmented 高亮当前档位，用户可切回「全部」
④ 仍不够 → 提示「**当前显示 X / 共 Y 个要素**，先用类型筛选聚焦」，把决定权交回用户
⑤ **P2 兜底**（**默认不启用**）：`>1200` **且 ③ 已执行** **且 收窄后仍 > 800** → 有连线节点取 `degree` Top 500 + 孤立全保留（上限 200）+ 提示条「仅显示关联最多的 500 个要素 **[显示全部]**」（该按钮必须可用）。**③ 被跳过 → ⑤ 不启用**

> ③ 的价值：它是**在用户可见、可改的维度上收窄**（类型），而不是在黑箱维度上排序（度数）。同样把图收小，前者用户能理解并反悔，后者不能——所以 ③ 必须先于 ⑤ 用尽。

### ③ 的守卫条件（v1.4 评审裁决，写死）

**`roleCount ≥ 200` 且 `roleCount / totalNodes ≥ 30%`** 两个条件**同时满足**时，才允许默认收窄到「角色」；**任一不满足则整步跳过，直接进 ④**。

| 场景 | 角色数 / 总数 | 是否收窄 | 结果 |
|---|---|---|---|
| 一本 1200 要素、角色 620 个的书 | 620 / 1200 = 51.7% | **收窄** | 620 个角色仍是大图，但保留了主体类型，性能收益真实 |
| 一本 1200 要素、角色 80 个的书（历史/设定型作品） | 80 / 1200 = 6.7% | **不收窄，跳过 ③** | 若收窄则默认藏掉 93% 的要素——比度数裁剪更糟（度数裁剪还剩 500 个，且给了提示条） |

> **两处「不可达」说明，避免实现者写永远走不到的分支**（v1.5）：
> 1. **不存在"总量小但角色多"的收窄场景**：D3 只在 `> 1200` 进入，`totalNodes` 恒 ≥ 1200，所以 210/260 这类书根本到不了这一步（原表里那行已删）。
> 2. **在当前阈值下 `roleCount ≥ 200` 是冗余的**：占比 ≥ 30% 且总量 > 1200 ⇒ 角色数至少 360 > 200，条件 ① 自动成立。**保留它不是为了现在生效，而是给"将来下调 D3 阈值"留一道不出错的护栏**——若阈值降到 300，`300 × 30% = 90 < 200`，此时绝对值条件才真正拦得住。实现时**两条都要写**，不要因为"当前恒真"就省掉。

**为什么分子分母要双条件**：只看占比会在阈值下调后放过"总量小但全是角色"的书（收窄毫无收益，纯损失可见性）；只看绝对数会放过"角色很多但只是全书零头"的书（收窄后仍是半本书）。**两个条件合起来表达的是同一件事：被收窄掉的非角色要素，确实不是这本书的主体。**（当前阈值下绝对值那条恒真，理由见上「不可达说明」第 2 条。）

### 可见性契约（v1.4 评审裁决，四步共同约束）

| 档 | 必须可逆 / 可见的形态 |
|---|---|
| ① 降信息密度 | 信息密度只影响**标签与角标**，不影响节点是否存在；节点 hover 仍出全名 tooltip（§6.2），任何密度档都不改变"图里有什么" |
| ② 折叠孤立要素 | 提示条常驻「另有 N 个要素暂无关联 **[展开]**」，展开即恢复全部；展开后该提示条改为「已显示全部要素 [收起]」（可逆、双向） |
| ③ 收窄类型筛选 | Segmented **高亮当前档位**（文案「角色（已收窄）」级），旁边必须有「显示全部类型」出口；不得把收窄做成"用户看不见的状态" |
| ④ 提示用户筛选 | 提示条必须给出两个确定数字：**当前显示 X / 共 Y 个要素**（不是"部分要素未显示"这种模糊表述） |
| ⑤ P2 Top-500 | 见上「四项条件」第 1、2 条：明示 + 「显示全部」可一键展开且**真的可用**（卡顿只警告、不禁用）。**默认不启用**：仅当 ③ 已执行且收窄后仍 > 800 时出现 |

> 这条契约的存在理由：降级若只表现为"图里的点变少了"，作者无法区分**"功能坏了"**和**"系统在保护性能"**。四步降级每一步都要让用户能回答两个问题——「少了什么」和「怎么要回来」。


### 与另外两条 Non-goal 的关系

- **与 R-1（孤立要素必须可见）**：条件 3 直接保证——孤立节点在任何降级档都不会被裁；② 折叠时也必须给出明确 N 与展开入口。R-1 承诺的是**可发现性**（"我的东西找得到"），不是"同时可见"。
- **与 N-5（不做按势力聚合）**：N-5 拒绝的是"按势力折叠成团"（会造出用户无法预期的超节点）；② 折叠的是**度数为 0 的点**（没有结构，折叠不损失信息）；⑤ 裁的是**按度数排序的长尾**（明示且可展开）。三件事性质不同。
- **与 N-11（不做无提示的静默裁剪）**：N-11 是 ⑤ 的**约束条款**，不是它的反面。⑤ 允许的前提就是 N-11 的四项条件全部满足。

**尚未定、交给架构师+QA 的**：阈值的**具体数值**（预研 §5.4 按实测帧率给）。产品侧已定"降级顺序"、"五项条件"与"孤立不裁"三条边界。
