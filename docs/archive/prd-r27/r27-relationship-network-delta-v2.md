### 2.2 默认铺开口径与夹具新基线（数字必须与 §4 自洽）

| 池子 | 列出**本书全部要素**（含已在画布的），状态分两类：「已在画布」/「未上图」；顶部常驻「未上图 N」 |

### 2.3 §五 D3 五步降级：逐条存废

| 步 | 存废 | 新口径与理由 |
|---|---|---|
| ① 降信息密度 | **保留（阈值重估）** | 纯渲染，与成员集合无关。但**卡片面积 > pill**，原 120/200/400/800 四档全部失效：建议基准 60/120/200/400，由架构师实测后定（沿用产 Q-13 的数值开口） |
| ② 折叠孤立要素 | **作废** | 折叠的对象（画布上的孤立节点）默认已不存在；池子承担该职责，保留会造成"折叠 + 池子"两套隐藏机制 |
| ③ 默认收窄到「角色」 | **作废** | 成员集合已经是"用户可见、可撤销"的减法。再叠一层类型收窄会产生**三种可见状态**（在画布可见 / 在画布被筛掉 / 不在画布），用户无法区分"没上图"与"被筛掉"——这正是 A-13/A-14 想避免的困惑，只是换了个位置 |
| ④ 提示「当前显示 X / 共 Y」 | **保留，改写口径** | 状态栏固定给三个数：**画布 X · 池中 M · 全书 Y**，不变式 `X + M = Y`；类型/关系筛选只改"可见"，**不得改 X**（筛选不改变成员集合） |
| ⑤ Top-500 兜底 | **作废** | 默认永不按 degree 裁剪（原 N-11 的立场）；改为**用户显式动作**：图较大时顶部提示「图较大（X 个要素），可点『精简上图』」→ 弹层写明规则「只保留关联 ≥ 2 的要素，将移出 N 个到池中」+ 可撤销一次。**默认不执行** |
| **N-11** | **改写** | 从"不做无提示的**静默裁剪**"→"不做**不可见的上图裁剪**"：任何未上图要素必须在池子里可见、可数（N）、可一键全部上图；默认不按 degree 排序裁剪 |
| **N-1 / N-7** | **保留** | 不因换框架就开放算法/参数面板；本期仍只交付一种布局。框架能力 ≠ 产品功能 |
| **N-9（不做常驻右栏小图）** | **保留** | 独立窗口反而证明右栏放不下；入口仍在右栏 |

### 2.4 布局记忆新结构草案（字段级，不是建表方案）

**存储位置**：仍走 `novel_config`（键值表），**不新增 `STORAGE_KEYS`、不做一个键装全部作品**。键 = `novel_rel_graph_v1:<workId>:<graphId>`（`graphId` 本期恒 `g1`），值为**单个**视图对象：

```jsonc
// config 表：key = "novel_rel_graph_v1:tpl-w:g1"，value = 下面这段 JSON（单作品单键，直写不读改写）
{
  "v": 2,                    // 1 → 2：结构变更，v 不匹配即整条丢弃（原 nodes/k/tx/ty/tf 全部作废）
  "ts": 1730000000000,       // 调试用，不参与逻辑
  "view": { "k": 0.86, "tx": 42.5, "ty": 18 },       // viewport
  "members": {                                       // ★ 成员集合 = 坐标表（单一真相）
    "tpl-e-char-shen": [412.5, 208.3, 1],            // [x, y, fixed]  fixed: 0|1
    "tpl-e-char-lu":   [338.0, 291.7, 0]
  },
  "rev": 7,                  // 成员/坐标变更序号，用于跨窗口冲突检测（§5-Q5）
  "autoSeeded": 1            // 首次自动铺开已完成（避免每次打开重跑全量播种）
}
```

| 设计点 | 说明 |
|---|---|
| **键名即作品与视图** | `workId` / `graphId` 都进键名，值里不再包 `{"<workId>": …}` 与 `graphs{}`/`active` 层；"多视图"只需换 `graphId`（§5-Q1 预留，本期不写 `name` 字段） |
| **为什么不一个键装全部作品** | 一个键装全部 = 每次写都要 `configGet` → 合并 → `configSet`，图窗口与主窗口同时写会互相覆盖（且跨作品读写是纯浪费）。单键直写把竞争面缩到"同一本书" |
| **成员集合与坐标合一** | `members` 的 key 集就是"上图成员"；**池 = 全部要素 − members**。不另存 `pool[]`，避免"成员表说 A、坐标表没有 A"的双真相漂移 |
| `tf` 删除 | ③ 作废后 `tf` 无消费者；类型筛选降为窗口内会话态，不持久化 |
| `rev` | 每次成功写 members 自增；跨窗口写前比对，不一致则先拉取再合并（只合并"新增关系"提示，不自动移动已有节点） |
| 清理 | 写入前剔除已不存在的 `entityId`；删除作品时按前缀 `novel_rel_graph_v1:<workId>:` 级联删键（插入位置仍在 modifiers 之后） |
| 体积 | 200 成员 ≈ **6.4KB**（单键值，无外层包裹） |

### 3.1 连线建关系的交互顺序（含跨窗口导航）

| # | 步骤 | 边界 |
|---|---|---|
| 1 | 悬停卡片 → 右/下缘连线手柄出现 | 卡片未选中也可出柄；缩放 < 0.5× 时手柄加大点击区 |
| 2 | 按住手柄拖出 → 实时画虚线到指针；可悬停到另一卡片高亮 | 拖到空白处松手 = 取消，不弹任何框 |
| 3 | 松手在**另一卡片**上 → 弹「新建关系」弹层，关系名输入获得焦点 | 松手在**自身** = 立即阻断 + 提示「不能与自己建立关系」（不弹确认框） |
| 4 | 输入/选择关系名 → 实时校验 | 空名不能提交；命中"已存在同关系"→ 输入框下方红字「这对要素已有『X』关系」 |
| 5 | 点「创建关系」→ **二次确认**（§3.2） | 期间卡片与画布**不完全锁定**，但同一对要素不可并发发起第二条 |
| 6 | 确认 → 写入 → 边出现 → 池子/meta/主窗口三处同步 | 失败：边回滚 + toast；`changes === 0`（端点已删）→ 提示「该要素已被删除，请刷新」 |
| 7 | 跳转资料卡：卡片操作条「打开资料卡」或双击卡片 | **保留图窗口** → 主窗口 `show()+focus()` → 渲染可见后 `openEntityDetail(id)` |

### 3.2 二次确认的内容契约（"将要写入什么"必须逐项可见）

| 项 | 内容 | 为什么必须有 |
|---|---|---|
| 1 | 起点：要素名称 + 类型 | 拖拽容易松手在错误卡片上，名称是唯一能自证的字段 |
| 2 | 终点：要素名称 + 类型 | 同上（方向在数据层有 `from→to`，虽然 P0 画无向边，但入参必须有向） |
| 3 | 关系名（原文回显） | 自由文本，必须让用户复核拼写 |
| 4 | 重复判定结果：`将新建` / `已存在同关系（合并为多关系边，显示「X +1」）` | 数据层会合并平行边，不告知会让用户以为"建了两条" |
| 5 | 写入目标：作品名 | 跨作品是硬阻断，但目标必须可见（用户可能同时开两本书） |
| — | 不提供 | 备注输入（`addLink` 不支持 `note`，备注统一走边详情，避免"两条写入口"） |

### 3.3 写回后主窗口同步的三处（W-15 的落地清单）

| # | 位置 | 验收点 |
|---|---|---|
| 1 | 要素卡片（`EntityCard`）的「关联数」 | 数字 +1；该卡片若在列表可视区，不发生整列重排 |
| 2 | 资料卡 `EntityDetail` 的"关联要素"列表 | 新关系出现在列表内（顺序与既有派生规则一致），不出现重复行 |
| 3 | `EntityPanel` 首行入口 meta「N 个要素 · M 条关联」 | M +1、N 不变 |
| — | 同步通道 | 由架构定（广播/事件/重拉皆可），但**不得**要求用户手动刷新或重开窗口；同步失败时图窗口不得回滚已成功的写入 |

不变的部分：卡片仍是可拖拽元素（S2）、连线手柄挂在卡片左右（S3）、类型色仍走 `--app-*` / 自建类型 hex 单一真相源。

## §7 v2.3 实现期补充：S2 落地口径（拖拽 / 成员记忆 / 切书）

S2 开工时按实现需要补了五条口径，均不与 §2 的冻结裁定冲突，只是把「没说死的地方」定下来。

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 后续新建的关联，要不要**自动上图** | **不自动**。成员集合是唯一真相；未上图的要素在池子里显示「有关联」徽标（与「未上图」区分） | 若要自动，就必须再记一份「用户显式移出过」的墓碑名单，否则「拖回池子」下次打开会被自动带回。多一份状态比多一次点击更贵；池子里的「有关联」已经让用户看得见 |
| 2 | 切书行为 | **一律挂起，不自动跟随**：横幅「当前查看《A》，主窗口已切到《B》」+ [切到《B》] / [留在这本]；切之前先把当前书坐标写掉 | 自动跟随更顺，但正在摆图的人会一抬头发现画布换了一本书 |
| 3 | 写库时机 | 离散动作（拖入 / 移出）**立刻写**；拖动去抖 **250ms**；`window-close-request`（关闭守卫）与 `beforeunload` 各兜底刷一次 | 「拖了很久一直没松手」是唯一可能丢的窗口，而松手那次一定写 |
| 4 | 存储键与 rev | 键 `novel_rel_graph_v1:<workId>:g1`，值与 §2.4 一致；写入前剔除已不存在的要素 | 单键直写不需要读-改-写；剔除避免键随删卡无限增长 |
| 5 | 删作品级联 | `novel-work-delete` 末尾按前缀 `novel_rel_graph_v1:<id>:%` 清 `novel_config`（排在行囊 modifiers 之后、作品行之前） | 作品没了记忆就是孤儿；位置保证 work_id 仍可用且不抢 pack 的子查询顺序 |

**关窗不弹确认框**：坐标不是「需要用户决策的草稿」——关窗时静默刷盘后放行，
只有写库真的失败才留一条提示。S3 的「未确认连线」不同，那时才需要问。

**结构合规（AGENTS §5.2 / §6.1.2）**：关系图窗口的组件全部改成「目录 + `index.tsx` + `index.scss`」
（`EntityNode` / `EntityPool` / `NodeDetailCard` / `RelationCanvas` / `WorkSwitchBanner`），
窗口级 `index.scss` 只留骨架。工具栏、池子检索与行、详情卡关闭与关系行、横幅按钮
一律用组件库（`Button` / `Input` / `Tooltip` / `Alert`），外观靠组件级 CSS 变量 + `widget.ant-button-reset` 清零点重绘。

**唯一的例外**：画布节点卡（`EntityNode`）不是 `Button`。它是**画布图形**，点选 / 拖拽 /
焦点全部由 React Flow 的 node wrapper 提供；再套一层 `Button` 会得到两个叠在一起的焦点目标
与拖拽阈值冲突。真正属于控件的按钮一律用组件库组件。

## §8 v2.4 实现期补充：S3 落地口径（连线 / 写回 / 同步）

S3 开工时按实现需要补了六条口径，同样不与 §2 的冻结裁定冲突。前三条是「ADR 只给了
方向、没给定型」的地方，后三条是实现时才发现必须写死的细节。

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 一次确认写多条时，`rev` 谁来加 | **主进程**：渲染层只传本地快照与 `expectedRev`，主进程把 `rev` 置为 `expectedRev + 1` 后落库并回传 | 两处各自 +1 必然漂移；回传值才是库里的事实，图窗口 `adoptRev()` 只接不写 |
| 2 | 坐标 flush 与提交撞车 | 提交前 `await flush()`；`flush` 写回的 `rev` **只许前进**（`Math.max(库/本地)`） | flush 在途时若按旧 rev+1 写回，会把刚提交的版本顶回去，下一次提交就误判 `stale` |
| 3 | 图窗口如何拿到新边 | 主进程事务成功后广播 `novel-links-changed`（带 `created` / `merged` / `notes` 增量），**图窗口按返回值自己合并、不重载 bundle** | 重载会让 `useGraphDoc` 的记忆重装，正在拖的坐标被库里旧值盖掉；且状态机会闪一次 loading |
| 4 | 画布的 Delete / Backspace | **禁用**（`deleteKeyCode={null}`） | React Flow 默认按键会直接删节点与边，而节点背后是真实要素与真实关系 —— 误按一次就是「图上看不见了、库里也没了」 |
| 5 | 「去右栏删除」怎么跳 | `window-send-to` 增加可选 `raise` 参数：主进程把目标窗口 `show()+focus()+moveTop()` 后再投递 `rel-open-entity` | 只发消息不抬窗口时，目标窗口被关系图完全遮住，用户会觉得点了没反应；`workId` 不匹配则只给提示不硬跳 |
| 6 | 未确认连线的关窗处理 | 弹层开着 = 有草稿 → 武装关闭守卫；`window-close-request` 时代理给上层弹「放弃并关闭 / 继续编辑」，**不静默丢弃** | 与 S2 的坐标不同：坐标是静默刷盘，连线草稿是「用户还没决定的东西」 |

**写回范围仍是「新建 + 备注」**：边详情只提供备注编辑与「去右栏删除」链接，不提供改关系名、
不提供删边。原因：图上能改名会让「一条边 = 哪一行」难以解释（一条视觉边可能对应 N 行），
而删除是不可逆动作，值得多一次跳转。

**合并语义（不是阻断）**：同端点 + 同关系名已存在时，输入框下方红字「这对要素已有「X」关系」，
第 4 项显示「已存在同关系（合并为「X +1」）」，**按钮仍可点** —— 用户可能就是想补一条备注，
拦死反而要他先删再建。主进程侧按四元组 `SELECT` 去重，命中归入 `merged[]`。

**主窗口三处同步全部是派生**：`EntityCard` 关联数、`EntityDetail` 关系列表、面板头
「N 个要素 · M 条关联」都从 `bundle.links` 派生，所以 `novel-links-changed` 只需按 id 合并
`links` 一张表，**不重载 bundle、不碰正在编辑的正文**。

## §9 v2.5 实现期补充：S4 落地口径（反向同步 / 密度 / 可达性 / 埋点）

S4 开工时按实现需要补了七条口径，均不与 §2 的冻结裁定冲突。与前两批不同的是，
这批四条交付物**各自可独立 revert**，所以每条都写成「改了哪里、坏了会怎样」。

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 密度档阈值 | **三档 `full / compact / minimal`，边界 60 / 200 / 400**（400 只加提示条，不再降档）；按**上图成员数**算，不按筛选后的可见数 | 原 120/200/400/800 是按 pill 标定的；v2.2 改成约 190×36 紧凑卡后按面积比前移（与 §2.3「建议 60/120/200/400」一致，其中 120 这档因卡面已无角标可留而与 200 合并，即 §6 说的「可简化」）。按成员数算是因为筛选只该改「哪些淡出」 |
| 2 | 降密度时节点集合 | **一律不变**（只隐角标/文字，不删节点） | RG-I-39 的关键断言是「401–800 档可见节点数 === 总节点数」。真正的减法只有用户显式动作（拖回池子 / 精简上图） |
| 3 | 反向同步的通道 | **复用 `novel-links-changed`**，载荷扩为 `{workId?, rev?, created, merged, notes, removed, relations}`，主进程抽到 `electron/novel-links-events.ts` 统一实现 | 两个生产者（单事务提交 / 主窗口增删）共用一条通道，事件名与「排除发送者」只写一次；再开一条 `novel-links-removed` 就会出现「谁先到」的第二套顺序问题 |
| 4 | `workId` 缺省 | `novel_links` 没有 work_id，只能由 `from` 端点反查；反查不到（境界绑定 / 库未就绪）时**不带 workId 照发**，接收方按 id 合并 | 丢消息的代价（图上看不见刚删的边）远大于过滤不严的代价（id 全局唯一，合并是幂等的空操作） |
| 5 | 反向同步为什么不重排 | **不重载记忆、不重建节点**：节点集合来自 `members`（不是来自边），删一条边不可能让卡片消失；装载签名不含 edges（§8-3 已设） | 重载 = 用户摆了一小时的坐标被库里旧值盖掉。这也是本批唯一的硬红线 |
| 6 | 池子键盘口径 | 行内 `↑↓ / Home / End` 移焦点；**`Enter` = 主操作**（未上图=上图，已上图=选中）；检索框 `↓` 直接进结果列；**不做 listbox + roving tabindex** | roving 会把每行压成一个 tab 停靠点，行尾「移出」就再也到不了（可访问性反而变差）；鼠标点行仍恒为「选中」，因为点一下是想看，不是想改画布 |
| 7 | 埋点口径 | `rel_graph_link_created` = `fromType` / `toType` / `relationLen`（码点） / `merged` / `ms` / `failReason?`；`failReason` 三态 `cancelled` / `blocked` / 写库失败码；`rel_graph_open` 增 `memberCount` / `poolCount` / `relationCount` | 只记成功等于把噪声当信号；`blocked` 与 `cancelled` 必须分开 —— 前者说明引导不到位，后者只是没兴趣 |

**未做（有意）**：主窗口没有「改关系名」入口，`relations` 分支只备契约、无生产者。
等改名功能上线时，主进程补一条广播即可，两个窗口的合并逻辑已经就绪。

**与 §8 的衔接**：§8-3 说「图窗口按返回值自己合并、不重载 bundle」只覆盖了
图窗口→主窗口；本条把同一条规则补成双向 —— 主窗口→图窗口走的是**同一个
handler**，所以两边的幂等与过滤口径不可能漂移。

## §10 v2.6 实现期补充：S5 落地口径（导出 PNG）

S5 是最后一批，交付一条「导出 PNG」链路。它与前三批的关键差异：**这是全 R27
唯一一条「只看结果、不看状态」的交付**——用户拿到的是文件，不是界面上的状态。
所以口径全部围绕「怎么保证那张图是对的」。

| # | 议题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 取景方式 | **`webContents.capturePage(rect)`**，截的就是用户眼前那一帧 | 这是唯一「所见即所得」的方式（RG-X-02 / RG-G-04 的历史红线）。任何离屏重绘（`zoomFactor` 放大、G6 导出图数据、SVG 序列化）都会产生第二套渲染器，屏幕一套、导出另一套 |
| 2 | 像素口径 | **`capturePage` 按 DIP 截，像素 = CSS × DPR**；1× 屏就是 1×，不假装 2× | `zoomFactor=2` 缩的是 CSS 视口（图会变小），不是提高采样。附录 A 已否决「用 zoomFactor 提分辨率」。DPR 现读不缓存——窗口跨屏时会变 |
| 3 | 两条通道 | **取景 `relation-window-export` / 落盘 `novel-export-binary` 分开**；落盘**绝不复用** `novel-export-file` | 现成的 `exportFile` 是 `writeFile(path, content, "utf8")`，用它写 PNG =「不报错但图坏了」。这是最难查的一类 bug：用户拿到打不开的文件，日志里一切正常。所以二进制写盘必须是一条独立通道，`writeFile` 不带 encoding |
| 4 | 覆盖物抑制 | 导出时给画布根节点挂 `is-exporting`，**纯 CSS** `visibility:hidden` 隐藏工具栏 / 缩放控件 / 密度提示条 / 连线手柄 / attribution；选中态压回常态 | 用 `visibility` 不用 `display`：前者不触发 reflow，截图期间图面一个像素不挪。清单在 `utils/export-png.ts` 定义一次，scss 按清单写规则，`export-png.test.ts` 双向校验「清单里每条都在 scss 有落点」 |
| 5 | 空图兜底 | 截图判 `isEmpty()` + **重试 3 次**（间隔 90ms）+ **最小字节数兜底**（纯色帧不是空图）；最小化时 `restore()` 一次 | Electron 首帧为空是生态已知抖动；只判 `isEmpty()` 会放过「1×1 或损坏帧」（只有几百字节），而 1200×800 哪怕极度单调也在几十 KB 量级 |
| 6 | 编排时序 | 点导出 → `await flush()`（冲刷未落库坐标）→ 挂类名 → **等两帧** → 取景 → `finally` 摘类名 → 弹框落盘 | 一帧给 React 提交类名，一帧给合成器重绘。`setTimeout(0)` 会被合成器合并进同一帧，截到旧画面。`finally` 保证失败 / 取消 / 异常三条路径都摘类名 |
| 7 | 交互 | 导出按钮带下拉：「导出 PNG」/「先适应画布再导出」（无动画 fitView 后截）；导出中按钮 loading、防连点（ref 同步锁） | 「先适应」解决「图摆偏了导出也偏」的直觉诉求；无动画 fitView 让 hook 的两帧等待覆盖这次重绘，不用额外等动画时长 |

**未做（有意）**：
- 只导 PNG（不导 SVG / PDF）——`sanitizeFileName` 已参数化扩展名，未来加格式不用改实现；
- 不导「池子里没上图的要素」——图就是图，池子状态不是图的一部分；
- 不做后台导出进度条——`capturePage` 是同步取景，毫秒级，弹个保存框的等待已经足够。

**与 §9 的衔接**：§9-1 的密度档「降密度不删节点」保证导出时极简档（只画色点）
也是**完整的节点集合**——用户导出的图在信息量上可降、在结构上不缺。S5 的覆盖物
抑制只针对「操作辅助」，与「图本身的内容」是两条互不干扰的线。
