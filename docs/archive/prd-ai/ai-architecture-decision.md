## 一、结论（决策摘要）

1. **不单独开「AI 对话窗口」**：AI 能力是「就地操作」（起名、润色、续写都发生在编辑器/面板上下文里），独立聊天窗会打断创作流。全局对话窗（如 RAG 问答）留待有明确需求时再评估。
2. **AI 能力独立成「服务层」**（非窗口、非业务域）：新增 `src/shared/ai/` 横向分层，被各窗口/功能面板复用。
3. **零重构**：AI 服务层落在现有 `src/shared/` 共享层空位上，全部是「新增文件 + 新增 IPC 白名单」，不改任何现有模块。
4. **AI 不直读 novel 库**：上下文由「调用方传入」，AI 服务层是「与业务无关」的纯净能力层。

---

## 二、为什么不是「独立窗口」

| 形态 | 判断 | 理由 |
|------|------|------|
| 独立对话窗口（类 ChatGPT） | ❌ 不做 | 起名/润色/续写是「就地操作」，切窗口打断创作流 |
| 独立 AI 服务层（代码层） | ✅ 采用 | 复用单元正确，是「方便后续润色接入」的正解 |
| 独立侧边栏抽屉 | ⚠️ 备选 | 改造量大，本期不做 |

## 三、架构设计

### 3.1 分层总览

```
┌──────────────────────────────────────────────────────────────┐
│ 功能面板层（就地操作，各窗口已有代码，不改）                    │
│   NameGeneratorPanel（起名）  EditorPane（未来润色/续写）        │
├──────────────────────────────────────────────────────────────┤
│ ★ AI 服务层（新增 src/shared/ai/，横向复用）                    │
│   ├─ ai-client.ts      统一调用入口（generate / stream）         │
│   ├─ ai-context.ts     拼装「当前文本 + 人物/设定」上下文         │
│   ├─ ai-types.ts       请求/响应/错误契约                        │
│   └─ ai-errors.ts      错误归一（401/超时/额度 → 可读文案）       │
├──────────────────────────────────────────────────────────────┤
│ 主进程（R-AI-01 已定义）                                          │
│   ├─ 读 ai.db 配置 + 解密 Key                                   │
│   ├─ 请求路由（OpenAI 兼容 / Ollama）                            │
│   ├─ 流式：protocol.handle 内部端点为主（流派3），IPC 转发兜底（流派1）│
│   └─ 错误归一                                                    │
├──────────────────────────────────────────────────────────────┤
│ ai.db（独立库，随用户隔离，R-AI-01 已定）                        │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 各层职责边界

| 层 | 负责 | 不负责 | 依赖方向 |
|---|---|---|---|
| 功能面板 | 组装「用户操作 + 业务上下文」，调用 AI 服务层 | 不碰 Key、不碰 HTTP、不碰错误码 | → 依赖 AI 服务层 |
| **AI 服务层** | 统一 `generate/stream` 接口、拼上下文、错误归一 | 不读 ai.db、不发 HTTP（走主进程） | → 依赖 `electronAPI.ai` |
| 主进程 ai-handlers | 读配置、解密、发请求、流式转发 | 不感知「起名/润色」业务语义 | ← 只被 AI 服务层调用 |
| ai.db | 存配置/Key/后续记忆 | — | 只被 ai-handlers 读写 |

### 3.3 核心原则

- **AI 服务层不直接发 HTTP**：调用只走 `electronAPI.ai`，网络请求永远在主进程。这是对 §8.7「主进程不代理 HTTP」契约的**刻意豁免**（凭据安全 + 端点无法枚举，理由见第五节·A），AI 服务层本身只做「拼上下文 + 错误归一」，不碰 Key、不碰网络。
- **AI 服务层不 import novel 任何模块**：它「与业务无关」，只知道「prompt + 上下文 → 调模型」。
- **上下文最小化**：发什么数据给模型由调用方（最懂业务处）决定，天然做对数据最小化。
- **主进程是「管家」不是「流式搬运工」**：流式主方案用 `protocol.handle` 内部端点（流派 3）——主进程只做「发起请求 + 返回流」这一次，渲染进程自己消费流；`protocol.handle` 不可用的场景才退回 IPC 逐块转发（流派 1，攒批控频）。详见 R-AI-04 预研点 4。

## 四、为什么「不直读 novel 库」，改「调用方传上下文」

| 做法 | 耦合 | 问题 |
|---|---|---|
| AI 服务层直读 novel 库 | 强耦合 | 跨域污染、AI 能读多少数据不可控（隐私/成本） |
| **调用方传上下文**（采用） | 松耦合 | 加新功能不改服务层；上下文可控；可独立单测 |

> 演进方向：将来做「AI 深度理解整本书」（RAG 问答），在 AI 服务层之上再加
> `ai-context-provider` 组装「本书全貌」。这是后续版本，不破坏本分层。

### 5.1 放置位置决策

采用 **`src/shared/ai/` 独立目录**（而非 `src/shared/services/ai.ts`）：
- AI 是「一组能力」（调用 + 上下文 + 错误 + 流式），非单个 service；
- 与 `shared/novel`、`shared/http` 平级，符合「一个能力域一个目录」；
- 后期功能增多不会让 `services/` 膨胀。

## 五·A、豁免 §8.7「主进程不代理 HTTP」契约（关键决策，必须显式声明）

> **背景**：`AGENTS.md` §8.7 有一条**强制契约**（1.5.0 重构）——
> 「网络请求一律在渲染进程发起，主进程不再代理任何 HTTP」，
> 「**不要**新增任何逐请求转发用的 IPC 通道」。
> 该契约对 news / git 等「渲染进程持凭据、session 级 CORS 放行」的场景是正确且已铺好的路。

**本 AI 接入方案刻意豁免这条契约**，理由与边界如下（这是**有意的架构决策，不是绕过**）：

### 为什么必须豁免

| 维度 | §8.7 契约的适用前提 | AI 业务的差异 | 结论 |
|---|---|---|---|
| **凭据位置** | Cookie 走 session jar，渲染进程凭 `credentials:include` 隐式携带，**Key 不下放也够用** | AI 用 `Authorization: Bearer <API Key>`，**Key 若下放渲染进程，就是明文暴露**（news/git 的 Cookie 从不进渲染进程内存） | AI 的凭据比 Cookie 更敏感，必须留在主进程 |
| **CORS 放行成本** | `onHeadersReceived` 注入 CORS 头，白名单域名有限（60s / git） | AI 要支持**用户自填任意 OpenAI 兼容地址**（DeepSeek/通义/智谱/Ollama…），域名无法枚举，逐个放行 CORS = 把 session 安全网打成筛子 | 无法用固定白名单覆盖「任意自填端点」 |
| **流式/超时** | 现有 http 客户端是「一次性响应」模型 | AI 的润色/续写要**长时流式**（SSE），且模型推理超时是秒级起步，与渲染进程 HTTP 客户端「短请求 + 快速中断」的定位不匹配 | 主进程 `net.fetch`（Chromium 网络栈、自动跟随系统代理）更适合 |

### 豁免后的边界（守住 §8.7 的「精神」）

豁免的是「**谁发 HTTP 请求**」这一条，但**不豁免** §8.7 的其它约束，也不制造新的逐请求转发通道：

1. **不新增「通用」HTTP 转发通道**：只新增 `electronAPI.ai` **这一个语义化入口**，且它只处理「AI 模型调用」这一件事（读配置 + 解密 Key + 发模型请求 + 错误归一），**不是**一个可被任意业务复用的「主进程代理 fetch」。news / git 等既有业务**继续走渲染进程 HTTP**，互不干扰。
2. **凭据永不下放渲染进程**：`api_key` 经 `safeStorage` 加密存 `ai.db`，解密只发生在主进程 `ai-handlers` 内部；渲染进程**拿不到明文 Key**。这比 §8.7 的 Cookie 模式（凭据经 session jar 隐式随请求走）**更严格**。
3. **复用既有网络先例**：主进程发请求**复用 `net.fetch`**（`novel-font-handlers.ts` 已趟过的坑：自动跟随系统代理、无 CORS），不引入新的网络库。
4. **错误归一仍在主进程**：AI 的 401/402/429/超时/地址不可达，统一在主进程归一为可读文案（R-AI-01 FR-10），渲染进程只拿结果。

### 一句话

> **§8.7 的「渲染进程发请求」是为了「Cookie 凭据安全 + CORS 白名单可控」两个前提；**
> **AI 业务两者都不满足（Key 比 Cookie 敏感、端点无法枚举），所以豁免「谁发请求」，**
> **但用「语义化单入口 + 凭据不下放 + 复用 net.fetch」守住了 §8.7 的「不铺通用转发通道、凭据安全」这一精神。**
