## 〇、阅读须知：本文的「推演」与「数据」边界

> **硬约束前置声明**：截至目前，CheckIn **没有任何真实的用户反馈与埋点回流数据**。
> 本文所有关于「用户是否买单 / 功能是否高频 / 留存是否提升」的判断，**全部是产品推演**，
> 不是实测结论。为避免推演被误读为事实，本文做如下标记约定：

| 标记 | 含义 |
|---|---|
| 【推演】 | 基于产品逻辑与同类产品经验的判断，**未经数据验证**，随时可能被数据推翻 |
| 【已核实】 | 已在代码 / 文档中被确认的客观事实（含版本、文件、表结构） |
| 【估算】 | 量化口径的估算值，非实测，仅用于建立量级认知与后续对照 |

**代码级核实结论（本次额外做的自查，供后续判断用）**：

| 核实项 | 结果 |
|---|---|
| `ai_naming_trigger / success / fallback / adopt` 四个埋点事件 | ❌ **代码中零落地**（全库 grep 无匹配）。R-AI-02 §10.2 定义了事件，但从未实现 |
| `novel_usage_log`（R14 埋点通道） | ✅ 已存在（`electron/novel-db.ts`），但**实际只落了 5 类事件**：`pack_open / pack_effect_add / pack_realm_bind / pack_open_setting_center / goal_reach`，**与 AI 无关** |
| `ai_log` 表 | ✅ 已存在（`electron/ai-db.ts`），记 prompt / 输出 / 耗时 / 错误码，是**技术调试日志**，非产品指标 |
| 埋点回收链路 | ❌ **不存在**。应用无后端，本地日志无法自动回传，也没有「导出统计」出口 |
| 已落地的 AI 功能 | 【已核实】AI 配置层（R-AI-01）、AI 起名（R-AI-02）、**AI 润色**（`PolishPreview` + `buildPolishPrompt`，已落地但未单独编号） |

> **一句话结论**：两个试点在**工程上成功了**，在**产品验证上是盲的**——
> 我们既不知道用户有没有配置 AI，也不知道配了之后用了几次、好不好用、有没有留下。
> 因此本文把「补齐数据回流」列为 **P0 且必须与下一个功能同批次上线**，而不是一个可延后的优化项。

## 一、两个试点的复盘（R-AI-01 配置层 / R-AI-02 起名增强）

### 1.1 试点一：AI 配置层 —— 验证了什么

| 结论 | 依据 | 性质 |
|---|---|---|
| 「无后端 + BYOK + 本地 Ollama 双轨」的纯客户端接入模型**工程可行** | `electron/ai-db.ts`（独立 ai.db）、`electron/handlers/ai-handlers.ts`、`SettingsWindow/hooks/useAiConfig.ts`、`AISection` 均已落地 | 【已核实】 |
| 「凭据不出主进程」的安全模型**可执行** | Key 经 `safeStorage` 加密存 ai.db，解密只在主进程；渲染进程拿不到明文 | 【已核实】 |
| 对 §8.7「主进程不代理 HTTP」的**刻意豁免**站得住 | 语义化单入口 `electronAPI.ai`，不是通用转发通道；复用 `net.fetch` | 【已核实】 |
| 「设置窗口左导航 + 右内容」能容纳四段配置（总开关/连接方式/凭据/高级参数）而不拥挤 | 2.6.0 已改造完成 | 【已核实】 |

### 1.2 试点一 —— 暴露了什么

| # | 问题 | 性质 |
|---|---|---|
| E-01 | **配置是一次性前置门槛，且对「小白」是最大流失点**：用户必须自己去第三方平台申请 Key、复制粘贴、理解 Base URL / 模型名。项目无后端，**结构性无法提供内置免费额度**（R-AI-01 §4.2 明确不做），这条门槛无法靠产品设计完全消除 | 【已核实】约束 +【推演】影响 |
| E-02 | **配置成功后没有任何「AI 正在帮我」的可见证据**：无用量、无次数、无成本、无节省时长。用户无法回答「我配了 AI，值不值」，续用动机弱 | 【推演】 |
| E-03 | **「测试连接通过」≠「功能好用」**：配置层只验证连通性，不验证模型能力。Ollama 7B 小模型与 DeepSeek 在同一起名功能上的产出质量可能天差地别，但配置层没有「模型能力分级 / 建议」 | 【推演】 |
| E-04 | **配置留存无法度量**：R-AI-01 §2.4 定的「7 日内仍保留有效配置 ≥80%」无采集手段 | 【已核实】 |

**对后续功能的启示 ①**：
> 每一个新 AI 功能都必须**自带可感知的价值证据**（用了几次 / 省了多少 / 产出多少），
> 否则「配置门槛」这笔预支成本换不回留存。这是 R-AI-05（数据回流看板）必须 P0 的根本原因。

### 1.3 试点二：AI 起名增强 —— 验证了什么

| 结论 | 依据 | 性质 |
|---|---|---|
| 「叠加降级」模式（默认 AI、本地规则引擎兜底）**工程成立、无白屏** | `NameGeneratorPanel` 已接入，本地引擎作 fallback | 【已核实】 |
| 「AI 服务层不 import novel、上下文由调用方以纯字符串传入」这条铁律**可落地** | `buildNamingPrompt` 只收 `NamingContext`，不 import novel | 【已核实】 |
| 「编辑器/面板不感知 AI 业务语义」的可维护性**成立** | `EditorPane` 只暴露 `insertText / appendText / replaceAll / replaceRange`，润色逻辑全在 `useNovelPage` 编排 | 【已核实】 |
| 输出契约脆弱（靠 `split("\n")` + 正则解析）是**真实欠债**，已被识别并收口 | `ai-context-and-output-spec.md` 已拍板 JSON + 寓意 + 三层保险 | 【已核实】 |

### 1.4 试点二 —— 暴露了什么

| # | 问题 | 性质 |
|---|---|---|
| E-05 | **起名是低频场景**。一个人名/地名在一本书的创作周期里发生次数有限，作为「首个 AI 功能」天然难以承担留存指标。这一点 R-AI-02 §14 已作为选型风险记录在案（RK-01，等级中） | 【推演】（与 PRD 原记录一致） |
| E-06 | **埋点零落地**：R-AI-02 定义的 4 个事件一个都没实现 → 试点**既无法证实也无法证伪** | 【已核实】 |
| E-07 | **「先跑通链路」必然在质量上欠债**：输出解析、上下文自动灌入、题材字段都在事后才补（`ai-context-and-output-spec.md`） | 【推演】 |
| E-08 | **试点价值判断标准落空**：R-AI-02 §2.2 定「以链路是否跑通 + 用户是否愿为 AI 起名配置 Key 为准」，后者因 E-06 **无法回答** | 【已核实】 |

### 1.5 复盘对后续的三条硬启示

1. **下一个 AI 功能必须选「高频」**：写作过程中**每天/每章都发生**的动作（写、改、卡、回顾），而不是「一本书发生几次」的动作（起名）。否则永远产生不了留存信号。
2. **埋点与功能必须同批次上线**：不能「先上功能、埋点后续补」——起名试点已经用一次失败证明了这条。
3. **润色已经趟出「就地操作」的交互范式，应被后续所有文本变换类功能复用**：`选中 → 浮层预览 → 换一种/重试 → 确认替换 → 失败不替换原文`。后续不要再为每个功能各造一套交互。

## 三、功能方向清单（12 项）

### R-AI-05 · AI 用量与效果回流看板（元能力）

- **一句话定位**：把「AI 帮了我多少」变成用户自己看得见的数字，并把这份数据变成产品迭代的依据。

- **应用场景**：
  - **创作者（所有人）**：配完 AI 之后，想知道「我这个月用了多少次 AI、省了多少时间、花了多少钱（token 估算）」，在 `SettingsWindow → AI 配置` 分区新增「用量与效果」子页查看。
  - **产品经理（我们自己）**：需要回答「起名试点到底有没有人用」「下一个功能该排哪个」——目前**一个数据都没有**。
  - **排查场景**：AI 老失败，用户需要把「AI 调用日志」（`ai_log` 已有）导出给我们定位。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 用户感知 | 配了 AI，无任何反馈，用不用全凭感觉 | 可见「本月 AI 调用 37 次 · 润色 22 / 起名 9 / 续写 6 · 采纳 18 次」【估算口径】 |
  | 排障 | 用户说「AI 没反应」，只能靠猜 | 一键导出最近 N 条 `ai_log`（脱敏）回传 |
  | 产品决策 | 全凭推演 | 有真实事件流 |

- **对留存与黏度的价值**：
  - 机制：**A 首次价值感知 + D 续费与口碑**（用户能看到「AI 帮我省了 X」，是口碑传播的具体素材）+ **E 数据资产回流**（元能力，让后续所有优先级判断有依据）。
  - 等级：**高**。理由：它本身不产生创作价值，但它是**唯一能让其它 11 个功能被正确排序和持续优化的东西**；同时它把「配置 Key 这笔沉没成本」显性化，降低「配了不用→觉得不值→卸载」的流失路径。

- **依赖关系**：
  - 复用：`ai.db` 已有 `ai_log` 表（intent / model / duration / error_code）——**但它是技术日志，缺产品维度**（无「采纳」、无「功能内步骤」、无「用户是否保留结果」）。
  - 复用：`novel_usage_log`（R14）已有 IPC 写入通道，**但 AI 事件一个没落**，需扩展统一 schema。
  - 新增：① 统一事件 schema（`ai_event`：intent / step=trigger\|success\|fallback\|adopt\|edit / duration_ms / error_code / meta）；② 一个聚合查询 handler；③ 设置页「用量与效果」子页（复用 `AISection` 的四段组织风格）；④ 「导出诊断包」按钮（JSON 文件，用户主动回传）。
  - **不需要新上下文**，不需要模型能力。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | 无后端 → 数据出不去，回流仍是空谈 | ① 本地看板先让用户**自己**看到价值（这本就有留存价值）；② 「一键导出匿名统计」让用户**主动**回传（opt-in，导出前展示将要发送的内容）；③ 严禁静默上报 |
  | 埋点污染主流程 | 沿用 `logUsageEvent` 既有范式：**失败静默，绝不阻塞写作链路** |
  | 日志撑爆磁盘 | `ai_log` 已有截断（各 ~4000 字）；新增事件表设**保留上限**（如最近 5000 条，超出滚动清理，可在设置里配） |
  | 合规 | 事件**只记元数据**（intent / 步骤 / 耗时 / 错误码 / 结果条数），**不记正文、不记作品名、不记邮箱**；导出包默认脱敏 |

- **优先级建议**：**P0（最高，且必须与 R-AI-06 同批次上线）**。
  理由：成本最低（表与通道都在，只差 schema + 一个 UI），但它是后面 11 个功能能否被正确决策的前提。**再上 2~3 个 AI 功能而不建回流，等于第二次盲飞。**

### R-AI-06 · 文本变换工具箱（扩写 / 精简 / 改写 / 换语气 / 转视角）

- **一句话定位**：选中一段字，一键让它变长、变短、变味、换个人称——把润色从「一个按钮」升级成「一组动词」。

- **应用场景**：
  - **谁**：正在码字的小说作者（**最主力人群**）。
  - **什么环节**：写作过程中最频繁的微操作——「这段打斗太干，想扩」「这段太啰嗦，想砍」「这段从第三人称换成第一人称试试」「这段太现代，想古风一点」。
  - **哪个界面触发**：`NovelWindow → EditorPane` **选中文本 → 浮动工具栏 / 右键菜单**（**完全复用已落地的 `PolishPreview` 浮层与 `useNovelPage.runPolish` 编排**），不新增窗口、编辑器内核不改（遵守「编辑器不感知 AI」铁律）。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 步骤 | 选中→复制→切到外部 AI 站→粘贴并说明要求→等待→复制回→替换 ≈ **7 步** | 选中→点「扩写」→浮层预览→确认 ≈ **4 步**【估算】 |
  | 耗时 | 单次 **3~8 分钟**（含切窗口、重新说明上下文） | 单次 **15~40 秒**（含模型往返）【估算】 |
  | 上下文丢失 | 每次都要重新跟外部 AI 解释「这本书是仙侠、主角叫 XX」 | 自动灌入书名/题材/命中人物卡（复用 `BookSnapshot` + collector） |

- **对留存与黏度的价值**：
  - 机制：**B 创作频次**（把「改一段」的单位成本从分钟级压到秒级 → 单位时间内产出更多 → 周活跃创作天数上升）+ **A 首次价值感知**（这是新用户最可能在第一次使用时就尖叫的功能）。
  - 等级：**高**。理由：**高频 × 即时可感**。这是本文唯一一个「每天都发生 + 效果立竿见影 + 实现成本极低（复用润色链路）」的三重命中项。

- **依赖关系**：
  - 复用（几乎全部现成）：`shared/ai/ai-client.aiGenerate`、`ai-context.buildPolishPrompt`、`PolishPreview` 浮层、`useNovelPage.runPolish`、`EditorPane.replaceRange`。
  - 新增：① 一组 `assembleXxxSpec` 模板（扩写/精简/改写语气/转视角/转人称）；② 浮层内的「变换类型」选择器；③ 各类型埋点（随 R-AI-05 一起上）。
  - 上下文：选中文本 + 前后文窗口 + 命中的人物卡（`ai-context-and-output-spec.md` 已拍板「反向匹配人物卡」）。
  - **不需要 RAG，不需要整本书索引**。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | AI 不可用 / Key 失效 / 超时 | **入口按配置态显隐**：未配置 AI 时，浮层不出现 AI 分组（或出现但点击引导去配置），**绝不出现点了没反应的死按钮**；失败沿用润色现有行为——**浮层内报错，不替换原文** |
  | 改写后「失去作者自己的味道」 | ① 浮层默认**预览 + 确认**，绝不直接改正文；② 提供「换一种」重试；③ 提供「撤销」（复用编辑器的 undo） |
  | 长文本超 token / 成本高 | 限制单次处理上限（如 ≤2000 字【估算】），超出提示「请分批处理」；设置页可设「单次最大字数」 |
  | 弱模型（Ollama 小模型）质量差 | 沿用 output-spec 的三层保险；对 `text` 型输出增加「输出为空 / 与原文一致 → 视为失败」判定（润色已有此逻辑，直接复用） |

- **优先级建议**：**P0**。
  理由：**最高频、最低成本、最强即时感知**。它是「把 AI 从『一个玩具』变成『每天都用的工具』」的开关，应排在续写之前——因为它复用的全是已落地代码，边际成本近乎为零。

### R-AI-07 · 就地续写（接着写 N 字）

- **一句话定位**：光标停在卡住的地方，让 AI 顺着前文往下写一段，给 2~3 个候选，你挑一个改。

- **应用场景**：
  - **谁**：写到一半卡住的作者（**卡文是小说创作最典型的中断原因**）。
  - **什么环节**：上一句写完了，下一句不知道怎么接；或者知道剧情走向，但懒得铺陈过渡段。
  - **哪个界面触发**：`EditorPane` 光标处 → 快捷键 / 浮动工具栏「续写」→ 侧边浮层给候选 → 确认后 `insertText`。**同在编辑器内完成，不切窗口**（遵守 R-AI-03）。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 卡文停顿 | 平均停顿 **5~15 分钟**，或直接关掉软件今天不写了【估算】 | 出 3 个候选约 **20~40 秒**，选一个改或当跳板，**1~2 分钟**恢复写作流【估算】 |
  | 续写质量 | 去外部 AI 站续写，要手动贴前文、手动说明设定，且贴回来格式常乱 | 自动带「本章前文 + 上一章摘要 + 当前大纲节点 + 命中人物卡」 |
  | 中断率 | 卡文 → 关闭应用（当日创作终止） | 卡文 → 续写 → 继续（当日创作继续） |

- **对留存与黏度的价值**：
  - 机制：**B 创作频次 + 流失拦截**（卡文是创作类应用最直接的流失触发器；把「中断退出」转成「继续写」等于直接救留存）。
  - 等级：**高**。理由：它作用在**流失发生的那一刻**，而不是锦上添花。

- **依赖关系**：
  - 复用：`shared/ai`、`EditorPane.insertText`、润色的浮层范式。
  - **需要新上下文**：① 光标前文（截断 ~1000 字）；② 上一章摘要 —— **依赖 R-AI-09 先有摘要能力**（否则退化为「只带本章前文」）；③ 当前大纲节点（`OutlinePanel` 数据已存在）；④ 命中人物卡。
  - 需要 `assembleContinuationSpec` 模板（`ai-context-and-output-spec.md` Phase 3 已预留位置，正好落位）。
  - 需要流式输出（R-AI-04 预研的 `protocol.handle` / IPC 兜底）——**这是本项目第一个真正需要流式的场景**。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | 续写偏离剧情 / 人设崩坏 | ① 强制上下文：大纲节点 + 人物卡 + 前文摘要；② 只给**候选不自动写入**；③ 显眼标注「AI 建议，请自行改写」 |
  | 「AI 代写」争议 | 定位为**跳板**而非代笔：默认输出较短（300~600 字【估算】），UI 文案强调「接着改」；提供「全书 AI 生成占比」的诚实统计（挂 R-AI-05 看板） |
  | 流式未就绪 | 降级为**非流式一次性返回**（起名已验证可行），体验略差但不阻塞 |
  | AI 不可用 | 入口隐藏 / 引导配置，**绝不出现空转按钮**；无本地兜底（本地规则引擎无法续写），但也不应该假装能 |
  | 长前文成本 | 前文截断 + 「只带本章」/「带上一章摘要」两档范围选择（见 §五 数据分级） |

- **优先级建议**：**P0（排在 R-AI-06 之后同批或紧随）**。
  理由：价值极高（直接救流失），但依赖流式与摘要上下文，**成本高于 R-AI-06**。建议 2.7.x 内落地，若流式阻塞则先上非流式版。

### R-AI-08 · 实体 / 设定抽取 → 一键建卡

- **一句话定位**：写完一章，AI 把里面出现的人物、地点、势力、物品、境界扒出来，你勾一勾就变成要素卡 / 角色卡。

- **应用场景**：
  - **谁**：所有作者，尤其是**不习惯手动整理设定**的多数派。
  - **什么痛点**：`EntityPanel`（要素卡）与 `CharacterPack`（行囊）是好东西，但**录入是最烦的体力活**——写完一章要回头把新出场人物一个个敲进卡片，多数人懒得做，导致设定库长期空置。
  - **哪个界面触发**：`EditorPane` 工具栏 / `SupportPanel` → 「从本章抽取设定」→ 候选列表（带类型、置信度、出处句子）→ 勾选 → 批量写入 `entities` / 行囊。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 一章 3000 字建卡 | 手工 **5~8 张卡，6~10 分钟**【估算】 | 抽取 + 勾选确认 **1~2 分钟**【估算】 |
  | 设定库填充率 | 低（懒得录）→ 后续功能（一致性校对、关系图）**无米下锅** | 高 → 给 R-AI-10 / R-AI-15 提供数据基础 |
  | 卡片的字段完整度 | 常常只有名字，summary 空 | AI 顺带给出一句话摘要 |

- **对留存与黏度的价值**：
  - 机制：**C 切换成本（数据资产沉淀）**。这是本文**最重要的一条切换成本机制**：AI 的产出不是吐在聊天框里的一次性文本，而是**沉淀进用户自己的要素库 / 行囊 / 设定中心**。用得越久，这本书的设定库越厚，换软件的代价越高。
  - 等级：**高**。理由：它是唯一一个「用户越用，产品越难被替换」的机制，且顺带解决了后续多个功能的冷启动（没设定卡，一致性校对和关系图都是空谈）。

- **依赖关系**：
  - 复用：`entities` 现有写入通道（`novel-handlers`）、`EntityPanel`、`CharacterPack` 的建卡入口。
  - 上下文：当前章节全文（**L3 级数据，需授权，见 §五**）+ 已有要素卡名（用于**去重**，避免重复建卡）。
  - 新增：`assembleExtractSpec` 模板 + `json-array` 输出契约（`{name, type, summary, evidence}`）+ 候选确认 UI。
  - **`json-array` 输出契约已在 `ai-context-and-output-spec.md` 落地，直接复用**，是本条成本可控的关键。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | AI 不可用 | 入口隐藏。**本地降级方案**：提供「按已有要素卡名做正则全文匹配」的轻量本地抽取（能抓到已录入的角色，抓不到新角色）——作为**弱兜底**可选做，不影响主路径 |
  | 误抽 / 抽错类型 | ① 必须**人工勾选确认**才入库，绝不静默写入；② 展示出处句子供判断；③ 与已有卡重名时明确标「已存在，将更新」 |
  | 章节过长超 token | 分块处理（按段落窗口滑窗，最后合并去重）；或提供「只抽取本章 / 只抽取选中段落」 |
  | 隐私 | 章节全文属 L3，**必须走 §五 的授权弹窗**（展示将发送字数） |

- **优先级建议**：**P0**。
  理由：一是高频（每写完一章一次），二是**它是 R-AI-10（一致性校对）与 R-AI-15（关系建议）的数据前置**——没有设定卡，那两个功能是空壳。排在 2.8.x 阶段第一位。

### R-AI-09 · 章节摘要与大纲回流

- **一句话定位**：每章写完自动生成一段梗概，回头看的时候读梗概就行，不用重读 3000 字。

- **应用场景**：
  - **谁**：写长篇（几十万字）且**隔天/隔周继续写**的作者（长篇作者是留存主力）。
  - **什么痛点**：断更几天后回来，忘了上一章写到哪、伏笔埋在哪，要重读一遍，重读成本随字数线性增长 → 越到后期越容易弃坑。
  - **哪个界面触发**：① `ChapterTree` 章节右键 → 「生成本章摘要」；② 章节切换时侧栏自动显示已有摘要；③ 可选：摘要一键写入 `OutlinePanel` 对应节点 / 章节备注。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 恢复上下文 | 重读上一章 3000 字 **3~5 分钟**【估算】 | 读 AI 摘要 **20~30 秒**【估算】 |
  | 长篇后期 | 50 万字后回顾成本极高 → 弃坑率上升【推演】 | 摘要链让「回看任意一章」成本恒定 |
  | 大纲维护 | 大纲写完就过时，与正文脱节 | 摘要可**反向回填大纲**，让大纲保持活性 |

- **对留存与黏度的价值**：
  - 机制：**B 创作频次 + C 切换成本**。降低「回到创作状态」的启动成本（断更后复活率），且摘要链是沉淀在用户库里的数据资产。
  - 等级：**中高**。理由：**中频**（每章一次，非每天多次）但**作用在流失最致命的环节（断更后不回来）**，且长篇作者的生命周期价值最高。

- **依赖关系**：
  - 复用：`novel-handlers` 章节 / 大纲写入通道、`OutlinePanel`。
  - 上下文：单章全文（L3，需授权）+ 已有大纲节点（用于对齐）。
  - 新增：摘要存储位（章节表新增字段 **或** 存 `novel_config` 映射）——**需架构师定落点**；`assembleSummarySpec` 模板。
  - **产出可被 R-AI-07（续写）复用为「上一章摘要」上下文**，有跨功能复利。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | AI 不可用 | 入口隐藏。**本地降级**：沿用「手工写章节备注」——本来就是这个动作，功能消失不造成功能缺口 |
  | 摘要剧透自己 / 不准确 | 摘要只在用户主动查看时展示；提供「重新生成」；明确标注「AI 生成」 |
  | 存储落点争议 | 请架构师在 §六 待拍板问题中定 |
  | 成本 | 单章一次调用，成本可控；提供「仅在新章节首次保存时提示一次」 |

- **优先级建议**：**P1**。
  理由：价值明确且是 R-AI-07 的上游，但**频次不及文本变换**，且需要新增存储字段（有 schema 变更成本）。建议放在 2.8.x，与 R-AI-08 同批（共用「章节级 AI 处理」的授权与分块基础设施）。

### R-AI-10 · 一致性校对（「设定警察」）

- **一句话定位**：全书扫一遍，告诉你「第 12 章主角叫李玄，第 30 章写成李元」「境界体系里没有『元婴后期』这一档」「第 8 章埋的伏笔到 60 章没收」。

- **应用场景**：
  - **谁**：写长篇、设定复杂的作者（仙侠 / 西幻 / 悬疑——设定越复杂越刚需）。
  - **什么痛点**：**这是人工几乎不可能完成的任务**。50 万字里找一个错别字式的人名不一致、一个时间线矛盾，人类做不到，但读者一眼就看见，是长篇最典型的口碑事故。
  - **哪个界面触发**：`SupportPanel` 或 `EditorPane` 工具栏 → 「全书一致性检查」→ 候选问题列表（类型 / 位置 / 证据句 / 建议）→ 点击跳转定位 → 用户自行决定改不改。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 全书一致性检查 | **几乎不做**（人工不可行，估算 0 次/本） | 一次扫描给出候选问题清单，**耗时 1~3 分钟**【估算】 |
  | 严重度 | 人名崩坏 / 境界崩坏是**读者弃书**的头等原因之一【推演】 | 发布前可自查，明显降低事故率 |
  | 手段 | 只能靠 `SearchPanel` 手动搜名字逐个核对 | 自动比对「正文 vs 要素卡 vs 境界阶梯（novel_setting_levels）」 |

- **对留存与黏度的价值**：
  - 机制：**C 切换成本 + D 续费与口碑**。这是**竞品很难抄、本地规则完全做不到**的能力（需要语义理解 + 全书比对），是真正的差异化护城河；且它的价值随字数增长而增长——写得越多越离不开。
  - 等级：**高**（差异化价值）+ 频次**中低**。

- **依赖关系**：
  - **强依赖 R-AI-08**：没有要素卡和境界体系，校对没有比对基准。
  - 复用：`SearchPanel` 的**本地全文检索**（关键！用于「本地召回候选片段 → 只把相关片段送模型」，避免整本书上传，见 §五）；`novel_setting_levels` 境界阶梯；`EditorPane` 定位跳转。
  - 上下文：**跨章节检索结果（非整本书）**——这是本功能在隐私与成本上能成立的关键设计。
  - 新增：`assembleConsistencySpec` + `json-array` 输出（`{type, severity, chapterId, evidence, suggestion}`）+ 问题列表 UI。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | **误报率高**（最大风险） | ① 只**提示**不自动改，永远由用户决定；② 分「确定/疑似」两档；③ 提供「忽略此项」并记住（存本地，避免重复报） |
  | 成本高 / 慢 | ① 本地检索先召回（把 50 万字缩到 N 个千字段落）；② 提供「只检查人名」「只检查境界」「只检查时间线」分项开关；③ 后台任务化，可中断 |
  | AI 不可用 | 入口隐藏。**本地降级**：「人名一致性」这类**有明确比对基准**的检查可以做成纯本地规则（要素卡名 vs 正文的近似串匹配，如编辑距离 / 同音字），这条本地规则兜底的价值很高，建议**必须做** |
  | 隐私 | 只送检索召回的片段，不送全书；L3 授权弹窗 |

- **优先级建议**：**P1**。
  理由：**差异化价值最高**，但依赖链最长（需 R-AI-08 先有设定卡）且误报风险需要打磨。排在 2.8.x 后段。

### R-AI-11 · 卡文救援 · 剧情分支建议

- **一句话定位**：写不下去的时候，让 AI 给你 3~5 条「接下来可能发生什么」，你挑一条（或者骂一句然后自己想出来了）。

- **应用场景**：
  - **谁**：卡文的作者（与 R-AI-07 同源，但作用层次不同——R-AI-07 救「句子」，本条救「走向」）。
  - **什么痛点**：「我知道该打一架，但不知道打完怎么收」——这种**结构层**的卡文，续写帮不上忙。
  - **哪个界面触发**：`OutlinePanel`（大纲面板）选中节点 → 「给我几个走向」；或 `InspirationPanel`（灵感速记）→ 「卡文急救」按钮。产出可直接存为灵感速记或大纲候选节点。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 结构化卡文 | 干坐 / 关掉应用 / 去刷手机，**恢复时间不可控**【推演】 | 3~5 条分支建议 + 各自的冲突点，**1 分钟内拿到可决策项**【估算】 |
  | 灵感沉淀 | 想法转瞬即逝，不记下来 | 一键存进 `InspirationPanel`，沉淀为资产 |

- **对留存与黏度的价值**：
  - 机制：**B 创作频次 + 情绪价值**。卡文是创作类应用最大的流失触发器之一，而「被救回来一次」的记忆强度远高于普通功能——**首次价值感知极强**。
  - 等级：**中高**。理由：频次中低（不是每天卡文），但**单次影响力极大**（直接决定这次创作 session 是死是活），且与 R-AI-12（创作日报）配合可形成「卡文→救援→完成→复盘」的正循环。

- **依赖关系**：
  - 复用：`OutlinePanel`、`InspirationPanel`（**现成的灵感速记出口，非常适合承接 AI 产出**）。
  - 上下文：当前大纲节点 + 前文摘要（依赖 R-AI-09）+ 要素卡 + 题材。
  - 新增：`assembleBranchSpec` + `json-array` 输出（`{title, conflict, consequence}`）。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | 建议同质化 / 套路化（AI 最爱给「神秘人出现」） | ① prompt 强制要求「必须基于本书已有设定与未收伏笔」；② 提供「更狗血 / 更克制 / 更反转」风格旋钮；③ 「换一批」 |
  | 剧透自己后续 | 建议只在用户主动触发时生成，不做自动推送 |
  | AI 不可用 | 入口隐藏。**本地降级**：无（纯创意任务无法规则化），但可提供「随机灵感词卡」的本地兜底（复用现有词库/灵感工具），保持入口不空 |
  | 用户觉得「被 AI 抢了创作权」 | 明确定位「跳板 / 反向刺激」，文案强调「不一定采纳，用来打破僵局」 |

- **优先级建议**：**P1**。
  理由：情绪价值高、与灵感面板天然契合，但频次低于写作动作，且依赖前文摘要（R-AI-09）。排在 2.9.x。

### R-AI-12 · 创作日报 / 写作复盘（checkin 域 × novel 域联动）

- **一句话定位**：像健身 App 的周报一样，告诉你这周写了多少字、哪天写得最好、AI 帮了几次、下周建议先补哪一章。

- **应用场景**：
  - **谁**：把写小说当长期项目经营、需要**正反馈维持动力**的作者。
  - **什么痛点**：写了 3 个月，感觉「好像没写多少」，缺乏成就感 → 弃坑。CheckIn 已有 `goal_reach`（每日目标达成）埋点和字数统计，但**只是散点数字，没有叙事**。
  - **哪个界面触发**：`NovelWindow` 启动时的轻量卡片 / `SupportPanel` 新增「创作周报」入口 / 可选接入 `BaseWindow` 的 `HomePage` 与 `DailyPage`（checkin 域联动——**这是 CheckIn 相对纯写作软件的独特优势**）。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 成就感 | 只有「今日 xxx 字」一个数字 | 「本周 4 天在写，共 12,340 字，比上周 +23%；第 18 章进度最快；AI 帮你处理了 27 次」【估算口径】 |
  | 目标感 | 目标达成后无后续引导 | 给出下周建议（如「第 22 章已 14 天未更新，伏笔 A 未收」） |
  | 仪式感 | 无 | 周报 = 打卡仪式，与 `checkin` 打卡心智天然契合 |

- **对留存与黏度的价值**：
  - 机制：**B 创作频次 + A 首次价值感知 + 差异化**。① 周报制造「回来看看」的理由（打开频次）；② 进步可视化 = 持续动力；③ **checkin 域联动是竞品没有的牌**（别的写作软件没有打卡/日程/记账这套数据）。
  - 等级：**中高**。理由：它不直接帮写作，但**它制造打开应用的理由**——对留存的最短路径是「让用户多打开一次」。

- **依赖关系**：
  - 复用：`novel_usage_log` 已有数据（字数、目标达成）、`chapter` 变更时间、R-AI-05 的 `ai_event` 数据（AI 帮忙次数）——**本条是 R-AI-05 数据的第一个消费方，形成闭环**。
  - 复用：`BaseWindow` 的 `HomePage` / `DailyPage` UI 范式（checkin 域联动）。
  - 上下文：**主要是本地聚合数据，AI 只负责「把数字讲成故事」**（最后一步润色成文案）——**token 成本极低，且 AI 失败时数字照常展示**，天然满足降级要求。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | 数据不足显得空 | 冷启动期只展示客观数字，AI 叙事在数据满 2 周后才启用 |
  | AI 文案油腻 / 鸡汤 | 提供「只要数据，不要文案」开关；文案风格克制（事实优先，不吹捧） |
  | AI 不可用 | **完美降级**：周报退化为纯数据卡片（数字全部本地可得），**功能不受损**，只是少了那段话 |
  | 跨窗口 | 若要接入 HomePage，需注意窗口隔离规则（数据经 `novel-service` / IPC，禁止跨窗口 import） |

- **优先级建议**：**P1**。
  理由：成本主要在本地聚合（AI 只做最后一步文案），降级完美，且能消化 R-AI-05 的数据形成闭环。排在 2.9.x。

### R-AI-13 · 起名增强 v2（寓意 / 批量体系化 / 跨书风格锚定）

- **一句话定位**：从「给 10 个名字」升级到「给一整个势力/家族/地名体系的命名方案，每个都带寓意」。

- **应用场景**：
  - **谁**：已在使用起名工具的作者（`NameGeneratorPanel` 已有用户）。
  - **什么痛点**：v1 只能一个个起；实际需要的是「这个魔门七位长老的名字要成套」「这个国家的地名要同源」「给主角起的名字要有寓意可写进设定卡」。
  - **哪个界面触发**：`NameGeneratorPanel` 内新增「批量体系化」模式；结果卡的「寓意」字段（`ai-context-and-output-spec.md` 已拍板 JSON + meaning）直接展示并可写入要素卡 summary。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 起一套 7 人长老名 | 反复生成 7 次 + 人工挑选搭配，**8~15 分钟**【估算】 | 一次生成成套方案，**1~2 分钟**【估算】 |
  | 寓意 | 无（v1 只有名字） | 每个名字带寓意，可一键写入设定卡 |
  | 风格一致性 | 靠用户自己把风格词填对 | 自动锚定本书题材（依赖 `genre` 字段，见下） |

- **对留存与黏度的价值**：
  - 机制：**C 切换成本**（名字+寓意写进要素卡 = 资产沉淀）+ **满意度**（补齐 v1 的明显短板）。
  - 等级：**中低**。理由：**低频场景的加深**。起名本来就低频（E-05），v2 提升的是满意度而非频次，对留存的边际贡献有限。

- **依赖关系**：
  - 复用：`NameGeneratorPanel` 全部现有出口（插正文 / 建角色卡 / 收藏）、本地规则引擎兜底。
  - **依赖 `work.genre` 题材字段**（`ai-context-and-output-spec.md` Phase 2 已拍板补，但**尚未落地**）——不补则风格锚定只能弱兜底。
  - 依赖：R-AI-05 的埋点（**只有拿到 v1 的真实使用率与采纳率，才知道 v2 该不该做**）。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | **v1 价值未验证就加深（最大风险）** | 明确设卡：**R-AI-05 数据回流跑满一个版本周期后，若起名触发量/采纳率低于阈值，v2 直接砍掉** |
  | AI 不可用 | 沿用 v1 已验证的「叠加降级」：回退本地规则引擎 + 提示（**这是全项目最成熟的降级路径**） |
  | 批量结果撞名 | 客户端过滤 + 本地补齐（v1 已有逻辑） |

- **优先级建议**：**P2**。
  理由：**低频场景，且必须等 R-AI-05 的数据来说话**。在知道「起名到底有没有人用」之前投入 v2，是把资源押在已记录为风险（R-AI-02 RK-01）的场景上。建议列入 3.0 观察池。

### R-AI-14 · 角色卡 / 设定卡字段补全

- **一句话定位**：建卡时只填名字 + 一句话，AI 帮你把外貌、性格、动机、口头禅、关系建议补齐，你再改。

- **应用场景**：
  - **谁**：想用行囊（`CharacterPack`）但**面对空表单无从下手**的作者。
  - **什么痛点**：`CharacterPack` 的卡片字段很专业（角色卡 / 物品 / 技能 / 境界），但**空表单是最大的劝退点**——很多人开了卡就只填个名字。
  - **哪个界面触发**：`CharacterPack` 建卡 / 编辑卡界面 → 「AI 补全」按钮 → 逐字段预览 → 用户勾选采纳哪些字段（**不整体覆盖**）。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 填一张完整角色卡 | **5~10 分钟**，或干脆放弃只填名字【估算】 | 一句话 → 补全 → 改，**1~2 分钟**【估算】 |
  | 卡片空置率 | 高（推测：多数卡只有名字）【推演】 | 降低 → 让行囊真正成为资产 |

- **对留存与黏度的价值**：
  - 机制：**C 切换成本**（填充行囊 = 沉淀资产）+ **功能激活率**（把「开了但没用」的行囊变成「真在用」的行囊）。
  - 等级：**中**。理由：价值是**激活既有功能**而非创造新价值；且与 R-AI-08（从正文抽取建卡）**部分重叠**——R-AI-08 从正文抽，本条从空表单填，两条路径互补但可二选一优先。

- **依赖关系**：
  - 复用：`CharacterPack` 现有字段与写入通道、`SettingCenter` 设定中心。
  - 上下文：卡名 + 用户一句话描述 + 本书题材 + 已有要素卡（保持人设不冲突）。
  - **不需要章节正文**，隐私与成本都很低（L1/L2 级）。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | 补全内容与已有设定冲突 | 注入已有要素卡做约束；**逐字段采纳**而非整体覆盖 |
  | 生成内容套路化 | 提供「再生成一次本字段」的单字段重试 |
  | AI 不可用 | 入口隐藏。降级 = 回到手工填表（本来就是这个动作），**无功能缺口** |
  | 与 R-AI-08 重叠导致资源浪费 | **建议先做 R-AI-08**（从正文抽更省力、更贴合本书），本条视行囊激活数据再定 |

- **优先级建议**：**P2**。
  理由：与 R-AI-08 存在能力重叠且优先级更低（R-AI-08 从正文抽是「顺手」，本条要用户主动发起）。列入 3.0，视行囊激活数据决定。

### R-AI-15 · 人物关系建议（从正文推断关系边）

- **一句话定位**：AI 从正文里读出「A 和 B 看起来是师徒」，你点确认，关系图（`novel_links`）上就多一条边。

- **应用场景**：
  - **谁**：用关系网络窗口（`RelationWindow`）的作者，以及**还没用起来的人**。
  - **什么痛点**：关系图是 CheckIn 的亮点功能，但**手工维护关系边很烦** → 图大概率是空的 → 亮点功能没被激活。
  - **哪个界面触发**：`RelationWindow` 内 → 「从正文推断关系」→ 候选边列表（带证据句、关系类型、置信度）→ 勾选 → 走 `novel-graph-commit` 单事务写入并广播 `novel-links-changed`（**严格遵守 AGENTS.md §2.1 的唯一广播出口规则**）。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 建 20 条关系边 | 手工逐条加，**15~25 分钟**【估算】，多数人不做 | 推断 + 勾选，**2~4 分钟**【估算】 |
  | 关系图激活率 | 低（图空 = 功能等于不存在）【推演】 | 提升 → 亮点功能真正被用上 |

- **对留存与黏度的价值**：
  - 机制：**C 切换成本**（关系图是高度结构化、极难迁移的数据资产）+ **功能激活**。
  - 等级：**中**。理由：沉淀价值高，但**受益人群窄**（只有维护关系图的人受益），频次低（建一次管很久）。

- **依赖关系**：
  - **强依赖 R-AI-08**（需先有要素卡才有节点）。
  - 复用：`RelationWindow` 现有画布、`novel-graph-commit` 事务与 `novel-links-changed` 广播（**必须复用，不得另起写入路径**）、`novel_links` 关系类型体系。
  - 上下文：章节片段（L3 授权）+ 已有要素卡与已有关系边（去重）。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | **误判关系**（把仇人判成恋人，很尴尬） | ① 全部**人工确认**才写入；② 展示证据句；③ 置信度分档，低置信默认不勾选 |
  | 与 R-AI-10 一致性校对有重叠 | 边界划分：**R-AI-10 报问题，本条建资产**。本条只做「新增关系边」的正向建设 |
  | AI 不可用 | 入口隐藏。降级 = 回到手工加边（现状），**无功能缺口** |
  | 写入路径风险 | 必须经 `novel-graph-commit` 单事务 + 唯一广播出口，避免图与库不一致 |

- **优先级建议**：**P2**。
  理由：受益面窄、频次低、强依赖前置。列入 3.0。

### R-AI-16 · checkin 域轻量 AI（记账分类 / 备忘摘要 / 待办拆解）

- **一句话定位**：把 AI 从「小说域专属」拓到「全应用」，让 lite 版用户和办公场景也用得上。

- **应用场景**：
  - **谁**：把 CheckIn 当日常工具用的用户（不只是写小说的那批）。
  - **什么痛点**：① `LedgerPage` 记账要手动选分类，懒得选就全归「其他」→ 统计失去意义；② `MemoPage` 攒了一堆备忘，找不着重点；③ `TodoPage` 一个大任务不知道怎么拆。
  - **哪个界面触发**：`LedgerPage` 记账弹窗输入备注后**自动建议分类**；`MemoPage` 侧栏「AI 摘要」；`TodoPage` 任务「AI 拆解子任务」。

- **预期体验提升（改造前 vs 改造后）**：
  | 维度 | 改造前 | 改造后 |
  |---|---|---|
  | 记账分类 | 每次手动选，或懒得选 → 分类统计失真 | 输入备注自动建议分类，**一键确认** |
  | 备忘回顾 | 翻一堆历史备忘 | 侧栏一句话摘要 |
  | 大任务拆解 | 自己想怎么拆 | AI 给 3~5 条子任务，勾选采纳 |

- **对留存与黏度的价值**：
  - 机制：**A 首次价值感知（扩大覆盖面） + B 频次**。目前 AI 只对 novel 域用户开放（`ai.db` 在 `EDITION !== "lite"` 才初始化），**checkin 域用户完全接触不到 AI** → 本条把 AI 的受益人群从「novel 域」扩到「全部用户」。
  - 等级：**中**。理由：覆盖面扩大是实打实的，但**这些场景 AI 的不可替代性弱**（分类建议用规则也能做到七八成），且分散了小说域的投入。

- **依赖关系**：
  - **需要放开 `ai.db` 的 edition 限制**（R-AI-01 §7 / R-AI-04 预研点 2 已决策：`EDITION !== "lite"`；放开会引入新窗口与配置入口的适配工作）。
  - 复用：`shared/ai`（checkin 域同样只 import 服务层，遵守铁律）、`ledger` / `memo` / `todo` 的既有 IPC。
  - 上下文：单条记录文本（L1/L2，**隐私敏感度低**）。
  - **注意**：AI 设置入口当前挂在 `SettingsWindow`，lite 版不展示 → 放开需同步改 UI 开关逻辑。

- **主要风险与降级路径**：
  | 风险 | 应对 |
  |---|---|
  | **分散主线资源（最大风险）** | CheckIn 的差异化与付费意愿集中在小说域；本条属于「广而不深」。**建议排在小说域高频场景全部落地之后再考虑** |
  | AI 不可用 | 入口隐藏。降级：记账分类 → **本地规则兜底（关键词匹配历史分类，这个本地方案其实很好用）**；备忘摘要 → 无摘要（回到现状） |
  | lite 版适配 | 需评估 `ai.db` 初始化与设置入口的 edition 分支改造量 |

- **优先级建议**：**P2**。
  理由：**战略上正确，时机上靠后**。在小说域高频场景（R-AI-06/07/08）还没做透之前投入 checkin 域，会稀释最有可能产生留存的战场。列入 3.0，且建议届时先只做「记账分类建议」这一个（本地规则兜底最成熟、频次最高）。

## 四、关于「不新建独立 AI 聊天窗口」决策的复核（R-AI-03 §一·1）

R-AI-03 决策：「AI 能力是就地操作，独立聊天窗会打断创作流；全局对话窗（RAG 问答）留待有明确需求时再评估」。
任务是复核该决策是否应被推翻。**本节给出明确结论：**

### 4.1 结论：**维持原决策 —— 不新建独立 AI 聊天窗口**

理由（补充论证，非简单复述）：

| 论据 | 说明 |
|---|---|
| 创作流的中断成本被低估 | 写作是**高认知负荷、高上下文驻留**的活动。切窗口 = 丢失上下文 = 回来要重读。**独立窗口把 AI 变成「另一件事」，就地操作把它变成「同一件事的一个动作」**，这是两种完全不同的心智模型 |
| 独立窗口会诱导「泛化用法」，稀释价值密度 | 聊天窗的默认值是「随便问」，而本产品的高价值场景全是**有明确输入与明确产出落点**的（选中→变换→替换；章节→抽取→建卡）。落点明确 = 可埋点、可度量、可沉淀；聊天窗 = 说完即走，**产出沉淀不进用户库，切换成本为零** —— 与 §三 的 C 机制（数据资产沉淀）直接冲突 |
| 与「AI 是增强不是依赖」的降级哲学冲突 | 就地操作可以「入口隐藏 + 无功能缺口」地降级；聊天窗一旦成为入口，AI 不可用时就是**一个空的聊天框**，是最差的失败态 |
| 成本结构 | 独立窗口 = 新窗口目录 + edition 登记 + 窗口生命周期 + 会话管理 + 历史持久化，而**复用 `PolishPreview` 浮层范式几乎零新增交互成本** |

### 4.2 但可以新增一个**不违反该决策**的形态：就地问答条（R-AI-17，3.0 候选）

R-AI-03 禁止的是**「独立窗口」**，不是「问答」本身。故提出受限形态：

| 项 | 定义 |
|---|---|
| 形态 | 在**既有** `SupportPanel`（支持面板）内新增一个「问这本书」输入条，**不是新窗口、不新增 edition 入口** |
| 触发条件 | ① R-AI-05 数据显示 AI 功能月活渗透 ≥ **40%**【估算阈值，待校准】；② 用户主动表达对「跨书检索/回顾」的需求（反馈、日志中出现 ≥ **10 次**【估算】）；③ 就地操作已覆盖的高频场景（R-AI-06/07/08）全部落地且稳定 |
| 技术方案 | **本地召回 + 模型判定**：复用 `SearchPanel` 的本地全文检索先召回 Top-N 片段 → 只把片段送模型 → 答案附引用位置可跳转。**绝不上传整本书建立云端索引**（无后端，也不合规） |
| 隐私 | L3 级，走 §五 授权弹窗；本地索引（若将来建）存在用户自己的库里，**不上传** |
| 降级 | AI 不可用时，输入框退化为**普通全书检索**（功能不消失，只是没有 AI 总结）——这是它优于独立聊天窗的又一证据 |

> **触发条件未满足前，本条不立项。**

### 4.3 若未来要**真正推翻**（建独立窗口），必须同时满足

1. §4.2 的三条触发条件**全部**满足，且
2. 数据显示存在「就地入口无法承载」的场景（如需要**长时间多轮**对话、需要**同时对照多个面板**），且
3. 即便推翻，也应做成**从既有面板唤起的浮层 / 抽屉**，而非独立 BrowserWindow（保留窗口隔离与 edition 清单的稳定性）。

## 五、数据出境与用户授权：整本书类功能的统一门槛

R-AI-08 / R-AI-09 / R-AI-10 / R-AI-15 / R-AI-17 都涉及「把正文发给模型」。项目是**纯本地应用、无后端**，用户数据是核心信任资产。本节定统一规则，**所有 L3 功能必须遵守**。

### 5.1 数据分级

| 级别 | 内容 | 示例功能 | 门槛 |
|---|---|---|---|
| **L1 字段级** | 类型 / 风格 / 名字 / 题材等元数据 | 起名（R-AI-02）、关系建议的实体名 | 沿用配置层既有告知 |
| **L2 片段级** | 选中文本 + 前后文窗口（≤ ~2000 字） | 文本变换（R-AI-06）、续写（R-AI-07） | 沿用配置层既有告知；提供「单次最大字数」设置 |
| **L3 全书级** | 整章 / 多章 / 全书 | 实体抽取（R-AI-08）、章节摘要（R-AI-09）、一致性校对（R-AI-10）、关系推断（R-AI-15）、全书问答（R-AI-17） | **必须走 §5.2 授权 + §5.3 成本控制 + §5.4 最小化** |

### 5.2 授权要求（L3 强制）

1. **首次触发时显式授权弹窗**，说明：将发送什么、发给谁（用户在配置层填的服务商域名）、是否可撤销。
2. **可撤销**：设置页「AI 配置」分区提供「允许 AI 读取整章内容」总开关，关掉后所有 L3 功能入口隐藏或禁用（**禁用必须给出原因，不能静默失效**）。
3. **按次可拒绝**：即使开了总开关，单次调用仍提供「本次范围」选择（见 §5.3）。
4. **本地模型优先提示**：若用户配置了 Ollama 本地模型，弹窗中明确提示「当前使用本地模型，内容不出本机」。

### 5.3 成本与范围控制（L3 强制）

每次 L3 调用前展示**范围选择器**与估算：

```
本次将发送：第 12 章全文（约 3,200 字 ≈ 4,500 tokens，费用约 ¥0.0X【估算】）
范围：[仅本章] [选中段落] [最近 3 章] [全书（不推荐，约 12 万字）]
```

- 提供「单次最大字数」与「月度用量提醒」设置项（数据来自 R-AI-05）。
- **默认范围应保守**（默认「仅本章」或「仅选中」）。

### 5.4 最小化原则（技术上强制）

- **本地召回优先**：能用 `SearchPanel` 本地检索缩小范围的（一致性校对、全书问答），**一律先本地召回再送模型**，禁止无脑全量上传。
- **不做云端索引**：无后端，也不应建。若将来做全书 RAG，索引必须落在用户本机（ai.db / novel.db），不上传。
- **不落正文**：`ai_log` 已有截断（各 ~4000 字）且明确「不记作品全文」，L3 功能的日志需同样遵守，**必要时只记字数与章节 ID，不记正文**。

### 5.5 合规提示位

配置层与每个 L3 功能首次使用时，需明确展示：「你将自行向第三方模型服务商发送数据，CheckIn 不中转、不存储你的作品内容」。

## 七、分阶段路线建议

### 阶段一 · 2.7.x —— 主题：**「让 AI 高频化，并且看得见」**

| 内容 | 编号 |
|---|---|
| 统一 AI 事件 schema + 本地聚合 + 「用量与效果」看板 + 导出诊断包 | R-AI-05（P0） |
| 文本变换工具箱（扩写/精简/改写/换语气/转视角），复用润色浮层 | R-AI-06（P0） |
| 就地续写（流式阻塞则先上非流式版） | R-AI-07（P0） |

**本阶段要回答的验证问题**：
1. **AI 是否真正高频化？** —— 启用 AI 的用户，人均**每周** AI 调用次数是否从「个位数/月」提升到 **≥3 次/周**【估算阈值，待校准】？
2. **AI 是否带来留存差异？** —— 使用 AI 功能的用户 vs 未使用者，次周创作活跃天数是否有显著差异？
3. **配置门槛的真实损耗在哪？** —— `ai_event` 中 `fallback.reason` 的分布：`未配置` 占多数（说明门槛问题）还是 `401/超时` 占多数（说明配置质量问题）？
4. **哪一种变换最被需要？** —— 扩写/精简/改写/换语气的使用占比（用于决定下一阶段打磨重点）。

> 若问题 1 / 2 答案为否，**应暂停后续 AI 投入，回头解决配置门槛与模型质量**，而不是继续加功能。

## 八、跨功能的两条横切建议（不占编号，但影响全部功能）

### 8.1 「AI 产出必须沉淀」原则（建议写入 AGENTS.md 铁律）

> 凡是 AI 产出的**结构化内容**（名字、要素卡、摘要、关系边、大纲节点），**必须提供「存入用户库」的出口**；
> 只有**一次性文本**（润色结果、续写候选）才允许「用完即走」。
> 理由：**沉淀 = 切换成本 = 留存**。吐在聊天框里的 AI 产出，用户换软件时带不走，等于零资产。

### 8.2 「AI 入口必须可消失」原则（降级哲学的统一表述）

> 每个 AI 入口在 AI 不可用时，**要么隐藏、要么禁用并说明原因、要么有本地兜底**；
> **绝不允许出现「点了没反应」或「空聊天框」**。
> 本 PRD 中每个功能都已按此原则给出降级路径，评审时应逐条核对。
