# Novel（小说）模块 · 产品视角审查报告

> 审查范围：CheckIn 桌面端 novel 子域（`src/windows/NovelWindow/**`、`electron/handlers/novel-*.ts`、`electron/novel-db.ts`、`src/shared/components/{CharacterPack, SettingCenter}/**`、`src/shared/novel/**`）。
> 审查基线：`6cdcde2` 工作树。
> 结论结构：每项统一「现状 → 问题 → 影响 → 建议 → 优先级（P0–P2）」。文末附短期可落地改进项汇总 + 待产品确认问题清单。

---

## 0. 范围与产品定位校正（务必先读）

在对"功能完整性与业务闭环"下结论前，必须先厘清这个产品的真实定位，否则会对着一个"阅读平台"的模板臆测它没有的模块：

- **这是一个桌面端（Electron）小说「写作 / 码字」工具**，不是书城、不是阅读器、不是连载发布平台。
- 数据全部落**本地 SQLite**：`novel.db`（`novel_*` / `novel_pack_*` / `novel_config` / `novel_usage_log`），书架底栏明示"本地优先 · 数据存储于本机"。**没有服务端、没有账号级云端存储**（账号仅用于登录态，见下）。
- 用户需求中提到的 **「书城/分类、书籍详情、阅读器、订阅付费、评论互动」在当前代码库中均不存在**——全仓检索（`书城|订阅|付费|评论|阅读器|商城`）零命中。因此本报告**不会**臆测这些模块的"缺失问题"，而是把它们归入 §8"待产品确认"（是否在规划内）。
- 真正值得审查的"功能完整性与业务闭环"，围绕**写作工具的留存与转化**展开：续写体验、数据安全/备份、多端、导入导出、写作辅助、统计激励、埋点等。

## 1. 断点续读 / 续写

### 1.1 已有"单点续写"，但缺"每章位置记忆"
- **现状**：续写位置记忆（R6）已实现——记 `cursor + scrollTop`，启动恢复，书架 Hero 卡片展示"继续写作"，`openWorkCard` 优先该作品位置记忆、否则取最近更新章节。工程实现严谨（一次性恢复、rAF 复位、越界夹取）。
- **问题**：位置记忆是**整本书一个续写点**（`hero.chapterId`），不是"每章各自记进度"。作者跳到别的章节校对后再回来，只能回到"上次写的那一章"的章顶，而非该章内上次读到的位置。
- **影响**：对"多章并行推进 / 校对型"作者，断点续读的颗粒度太粗，频繁跳章时找位置成本高，是留存的一个隐性摩擦点。
- **建议**：位置记忆升维为"按章存储"（`chapterId → {cursor, scrollTop}`），切章即存、回章即恢复。
- **优先级**：P1

### 1.2 崩溃恢复链路完整，是亮点
- **现状**：`novel_editor_session` 会话标记驱动崩溃恢复，`RestoreBanner` + 恢复后回到断点；正文草稿在主进程表、重挂载 flushDraft 兜底。这套机制对写作工具是**核心价值**，做得扎实。
- **建议**：保持；仅建议在恢复横幅上补充"恢复了多少字 / 恢复到哪个时间点"的信息，增强用户对数据安全的确信。
- **优先级**：P2

## 2. 数据安全 / 备份 / 多端同步

### 2.1 无云同步、无多端，数据单点存本机（最高风险项）
- **现状**：数据全在本地 `novel.db`；`electron/backup-utils.ts` 只服务于 **todo / memo** 的 zip 备份，**novel 域没有对等的备份/导出机制**（只有"作品/卷/章导出为文本"与"设定导出 JSON/MD"，属内容导出而非数据库备份）。账号体系（`authDb` / `userDb`）用于多用户隔离，不是云同步。
- **问题**：**换机 / 重装 / 磁盘损坏 = 全部作品、角色、设定、关系图丢失**，没有可恢复的备份出口。这是写作工具最致命的产品缺口。
- **影响**：一旦发生即不可逆，用户信任崩塌、直接流失；"写了 300 万字"却无备份是口碑级风险。
- **建议**：① **P0 短期**：提供 novel 域的一键"全量备份 / 恢复"（zip 打包 `novel.db` 或导出结构化 JSON，含章节正文/要素/设定/链接/快照），对标 todo/memo 的既有实现；② **P1 中期**：接入云同步（WorkBuddy 云服务或用户自选网盘目录），实现多端/换机同步；③ 本地定期自动快照提醒。
- **优先级**：P0

### 2.2 导出格式偏"写作中间产物"，缺出版级格式
- **现状**：导入支持 TXT / DOCX（mammoth 抽取纯文本）；导出有"作品/卷/章"（文本类）+ 设定 JSON/MD + 关系图 PNG（`novel-export-handlers.ts` 的 `capturePage` 取景）。
- **问题**：导出**没有 EPUB / 结构化 DOCX / 排版后的成品格式**，导出的是"可编辑文本"而非"可出版/可分享的成品"。
- **影响**：作者"写完想发出来/导成电子书看效果"这一步断掉，作品的"出口价值"没兑现，影响对工具"能帮我出成果"的认知。
- **建议**：补 EPUB 导出（章节结构 + 卷章层级天然适配 EPUB 目录）与排版后 DOCX 导出；列为 P1。
- **优先级**：P1

### 2.3 删除是"物理级联删除"，无回收站 / 撤销（数据安全第二风险点）
- **现状**：删除作品走 `WorkManageMenu` → `useNovelData.deleteWork` → 主进程 `novel-work-delete` **级联物理删除**（作品 + 章节 + 要素 + 设定 + 链接 + 快照），仅前端"二次确认"，确认后**不可逆**。章节/卷删除同样是二次确认后即删，全仓检索无 `回收站 / 软删除 / deleted_at / undo` 任何命中。
- **问题**：误删不可恢复。写作者删除往往是"清理中误点"或"删了后悔"，而这里删掉的是**几十万字 + 整套世界观**，一次误操作代价极大。
- **影响**：与 §2.1 叠加构成完整的数据安全链风险——没有备份、也没有"删错反悔"的兜底，是全产品**口碑级隐患**。
- **建议**：① 短期：删除前展示"将删除 N 章 / N 万字 / N 个角色"的明确代价预览；② 引入**回收站（软删除 + 30 天可恢复）**或至少"删除后短暂可撤销（undo toast）"；③ 与 §2.1 的备份一起作为数据安全三件套。
- **优先级**：P1（若 P0 备份落地，本项可降级；二者至少取一）

### 2.4 导入格式偏窄，搬库迁移门槛高
- **现状**：导入仅支持 **TXT / DOCX**（`novel-import-parser.ts` 仅解析 TXT 章节结构；DOCX 经 mammoth 抽纯文本）。
- **问题**：不支持 **EPUB / Markdown** 导入，而这两者是网络小说作者与 Markdown 写作工具用户搬家的主流载体。
- **影响**：存量作者从其它工具迁入时需先转格式，转化漏斗在"第一步导入"就流失。
- **建议**：补 EPUB 导入（章节 + 目录层级天然映射卷章）与 Markdown 导入（按标题切章）。
- **优先级**：P2

## 3. 离线缓存 / 本地性能

### 3.1 本质即"离线原生"，无需"缓存"但需"大数据量验证"
- **现状**：数据本地 SQLite，天然离线可用（本身就是离线应用）；性能上做了长篇小说优化（要素出场章数索引按章缓存 + 分片调度，`useAppearanceStore.ts`，实测 3000 章冷扫 9s→分片不卡）。
- **问题**：无传统意义的"离线缓存"需求；但**超长作品（万章级）的冷启动 / 首屏 / 章节树渲染**是否仍流畅，代码里只有 3000 章这一档的实证，缺更大量级的压测结论。
- **建议**：做一次万章级 + 百万字级的启动/切章/搜索性能基准，据此决定是否需要对章节树做虚拟化（当前 `ChapterTree` 未见虚拟化证据）。
- **优先级**：P2

### 3.2 章节树疑似未虚拟化（需确认）
- **现状**：`ChapterTree` / `ChapterTreeItem` 未见 react-virtuoso 或等价虚拟列表（项目里 react-virtuoso 主要用于其它列表，见记忆）。
- **问题**：上千章时左栏章节树若全量渲染，切章/滚动会卡。
- **影响**：长篇小说是核心用户群，章节树卡顿直接伤体验。
- **建议**：确认章节树是否虚拟化，未虚拟化则补（或至少分卷懒加载）。
- **优先级**：P1（需先确认现状）

## 4. 个性化推荐 / 内容发现

### 4.1 无跨书全文检索，多书作者"查设定"成本高
- **现状**：搜索能力全部是**单书内**的——章节树搜索、章节跳转面板（`ChapterJumpPalette`）、要素搜索、灵感/笔记搜索；**没有跨全部作品的全局检索**（全仓无 `全文索引 / FTS / 跨书搜索` 命中）。
- **问题**：作者常"这本书里那个角色叫什么来着、我在哪本书写过类似的桥段"，只能逐本打开、逐本搜。
- **影响**：多书/系列作者是高频核心用户，跨书检索缺失直接抬高"查资料"成本，也削弱了"设定跨书复用"（§7.2）这个差异化能力的实际利用率。
- **建议**：做**跨书全文搜索**（作品名/章节名/角色名/设定名/正文关键词，书架级全局入口 + 结果跳转到对应章节），必要时为正文建 FTS 索引。与 §7.2 全局设定中心形成"查得到 → 用得起来"的闭环。
- **优先级**：P2

### 4.2 无推荐，但"写作工具"语境下应换成"写作洞察"
- **现状**：无任何推荐系统。书架有统计条（累计作品/累计字数/今日新增/连续码字）与"继续写作 Hero"，但无个性化内容推荐。
- **问题**：对写作工具，"推荐"的合理形态是**基于历史数据的写作洞察**（如"你通常在晚上 9 点后写作效率最高""连续码字 X 天""某书已停更 Y 天"），而非内容推荐。
- **影响**：缺激励与"回访理由"；`novel_usage_log` 已记录使用数据，却未反哺给用户任何洞察。
- **建议**：基于 `novel_usage_log` 做轻量"写作周报/洞察卡片"（回访钩子）；不套用"内容推荐"模板。
- **优先级**：P2

## 5. 付费 / 变现转化路径

### 5.1 无任何付费体系，属明确产品边界
- **现状**：全仓无订阅、无内购、无支付、无付费墙（`weixinpay` 等连接器未接入 novel 域）。这是本地离线写作工具，无变现路径。
- **问题**：若产品有商业化诉求，当前**零变现设计**；若无，则属既定免费工具定位。
- **影响**：不构成"缺陷"，但需产品明确商业化策略（见 §8 待确认）。
- **建议**：若要做商业化，优先考虑"云端同步/备份容量、AI 辅助（起名/大纲/敏感词高级版）、多端"作为增值点，而非对本地写作功能收费。
- **优先级**：P3（待产品决策）

## 6. 数据统计 / 埋点

### 6.1 有本地统计，无产品级埋点
- **现状**：有 `novel_usage_log`（今日字数、连续码字、码字速度等本地统计），服务"今日目标/连续码字"激励。**没有**任何产品级埋点（事件上报 / 漏斗 / 留存分析）。
- **问题**：产品团队无法知道"用户卡在哪一步、哪些功能没人用、留存如何"；所有改进决策缺数据支撑。
- **影响**：迭代靠猜；写作工具的用户路径（新建→写第一章→加角色→用设定→导出）无漏斗数据，无法定位流失点。
- **建议**：接入轻量埋点（本地优先、匿名、可关闭），关键事件：新建作品、写第一章、首次导入、要素建卡、设定使用、行囊/关系图打开、导出、崩溃恢复。**须尊重隐私**（写作内容敏感，只埋事件不埋内容）。
- **优先级**：P1

### 6.2 内容审核 / 敏感词
- **现状**：有**本地敏感词检测**（AC 自动机 + 词库 + 手动/自动扫描，`sensitive/` 模块），用于作者自查，非平台审核。
- **问题**：作为写作工具，无"平台内容审核"需求（不发布）；但**敏感词库的维护与更新**是持续的体验问题（内置词库是否覆盖常见平台违禁词、是否支持自定义词库导入——已有 import-template）。
- **建议**：持续维护内置词库 + 明确"这是作者自查工具、不承担合规审核责任"的产品定位文案。
- **优先级**：P2

## 7. 写作辅助能力闭环（本工具特有的"功能完整性"）

### 7.1 能力矩阵已较完整，但存在"孤岛"风险
- **现状**：写作辅助能力齐全——要素（角色/地点/势力/道具）建模、正文高亮标注、要素详情卡、关系网络图、行囊（主角随身盘点）、设定中心（等级/境界体系）、全局设定中心（跨书共享）、灵感笔记、起名器、敏感词、快照回滚、模板库。
- **已打通（代码实证，无需补）**：正文选区右键 →「新建资料卡 / 绑定现有卡 / 记入行囊」（`EntityContextMenu` + `useNovelData.markSelection`，无卡秒建、有卡关联别名）；要素详情卡 → 出场章节跳转列表（`EntityDetail`，虚拟化）；关系图 ↔ 主窗口「打开要素资料卡」（`entity-jump.ts`，含跨书意图判定）；关系图写回关联后主窗口 M 自动 +1（跨窗口广播）。
- **问题**：能力多但**闭环联动仍有 4 处断裂点**（代码实证，非猜测）：
  1. **要素改名 → 正文标注不反写**：正文出场章数靠 `useAppearanceStore.syncAppearances` 全量扫描**只读派生**，详情卡改要素名/别名后，正文里已绑定的标注文本**不会自动改名**，词库/标注失配，需手动重新绑定。
  2. **关系图是独立窗口数据孤岛**：`RelationWindow` 靠跨窗口消息与主编辑器通信，关系图里新增/改名要素后，正文标注层**不会热更新**（词库重扫有延迟），存在短暂不同步窗口。
  3. **设定体系 → 正文反哺缺失**：境界/等级名在设定中心改名后，正文要素已绑定的境界显示**是否自动跟随**待确认（与①同源的"只读引用 vs 实时同步"问题）。
  4. **跳转收口点不一致**：正文标注→详情、详情→正文、关系图→详情是**多套实现**（`openEntityDetail` / 出场跳转 / 跨窗口消息），易各自演进、行为漂移。
- **影响**：功能各自好用，但"生态闭环"（写→标→查→联→用）在**改名/同步**这个高频动作上断链——作者一旦给角色改名，就要逐处手动重绑，成本随书长线性上升，直接影响"离不开的工作台"定位。
- **建议**：以"要素/设定改名 → 全链自动同步"为最高价值闭环优先打通：① 引入**唯一 id 驱动**的标注引用（而非按文本名匹配），改名即同步重扫；② 关系图写回走与主窗口同源的词库刷新通道（消除延迟窗口）；③ 收口跳转逻辑为单一入口，避免多套实现漂移。
- **优先级**：P1

### 7.2 全局设定中心的"跨书共享"是差异化，但扩散认知不足
- **现状**：`GlobalSettingWindow` 实现跨书共享设定库（引用实时同步、上架/复制、删除就地固化），是同类工具的差异化能力。
- **问题**：入口较深（书架 → 全局设定中心独立窗口），新用户难以发现其价值。
- **建议**：在引导/帮助中强化"跨书复用世界观设定"的价值点，提升功能利用率。
- **优先级**：P2

## 8. 待产品确认问题清单（不臆测，需拍板）

1. **产品定位**：novel 域长期是"本地写作工具"还是"会演化为带云同步/多端的写作平台"？——决定 §2.1 云同步与 §5 付费的优先级。
2. **是否规划移动端**：当前为 Electron 桌面应用，无移动端。若规划，正文区/三栏/右键菜单/hover 卡需重新设计（设计师报告已标注）。
3. **是否规划书城/阅读器/付费/评论等"平台化"模块**：当前代码库完全不存在，请确认是"不在此阶段范围"还是"遗漏"。
4. **备份/迁移的官方形态**：是否接受"导出结构化 JSON + 导入恢复"作为 novel 域备份的第一版方案？
5. **云服务选型**：若做多端同步，是否走 WorkBuddy 云服务（`cloud-service` skill），还是用户自选网盘目录同步？
6. **埋点与隐私边界**：写作内容高度敏感，埋点是否只采事件、绝不采正文内容？（建议明确并写进合规说明）
7. **章节树虚拟化**：是否有万章级作品的真实用户场景，需要据此决定是否投入虚拟化？
8. **删除兜底形态**：优先做"回收站（软删除 + 30 天可恢复）"还是"删除后短暂可撤销（undo toast）"？（影响 DB 层 `deleteWork` 是改软删字段还是保留物理删除 + 前端补偿）
9. **要素改名同步**：要素/设定改名后，正文标注是否要"自动改名同步"，还是保留"按文本名匹配 + 手动重绑"的现状？（决定是否引入 id 驱动标注引用，工程量较大，需权衡）

|---|--------|----------|--------|------|
| 1 | novel 域一键全量备份/恢复（zip `novel.db` 或结构化 JSON） | 新增 `novel-backup` handler | **P0** | 数据安全兜底，最致命缺口 |
| 2 | 删除回收站 / 撤销（软删除 + 可恢复），删除前代价预览 | `WorkManageMenu` / `deleteWork` | P1 | 误删可反悔，数据安全第二环 |
| 3 | 每章独立位置记忆 | `EditorPane` + 位置存储 | P1 | 断点续读颗粒度 |
| 4 | EPUB / 排版 DOCX 导出 | `novel-export-handlers` | P1 | 作品"出口价值" |
| 5 | 轻量产品埋点（本地优先、匿名、只采事件不采内容） | 新增埋点通道 | P1 | 迭代数据支撑 |
| 6 | 章节树虚拟化 / 万章级性能验证 | `ChapterTree` | P1 | 长篇小说体验 |
| 7 | 跨书全文搜索（作品/章节/角色/设定/正文关键词，全局入口） | 书架 + 新增 FTS 索引 | P2 | 多书作者查资料闭环 |
| 8 | EPUB / Markdown 导入 | `novel-import-parser` | P2 | 降低存量作者迁移门槛 |
| 9 | 写作洞察卡片（基于 usage_log） | 书架 | P2 | 回访钩子 |
| 10 | 能力联动盘点（标注→详情→关系图/行囊/设定） | 跨模块 | P1 | 生态闭环 |
| 11 | 要素/设定改名 → 全链自动同步（唯一 id 驱动标注引用） | `useAppearanceStore` + 词库刷新通道 | P1 | 改名不再逐处手动重绑 |
| 12 | 关系图写回与主窗口走同源词库刷新通道（消除延迟窗口） | `RelationWindow` ↔ `EditorPane` | P1 | 跨窗口标注即时一致 |
| 13 | 敏感词库持续维护 + 定位文案 | `sensitive/` | P2 | 合规与体验 |
